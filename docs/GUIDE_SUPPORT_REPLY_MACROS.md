# In-app Bug 公開回覆 Macro Library（白話範本）

> 對應 GitHub #907（M9 Support）。權威寫作規則：`.cursor/rules/user-facing-communication.mdc`、`docs/CHAT_BUG_SYSTEM.md` §3.8。
> 用途：讓任何 AI／人在 in-app bug 回報上，給回報者（老師／主任／家長）的**公開留言**白話、穩定、不暴露內部術語。
> 使用方式：複製對應情境的「公開留言」，把 `[方括號]` 變數換成實際內容，送出前跑一次「禁用詞檢查」。

---

## 0. 使用前提（每則都適用）

- **公開留言 = `is_internal_note=false`**，會通知回報者；技術細節一律放 GitHub issue 或 `is_internal_note=true` 的內部備註。
- **狀態機是順序的**：`new → triaged → in_progress → resolved → closed`，禁止跳階（跳階 = 422，見 MEMORY「bug state machine」）。
- **未部署不可標 `resolved`**：程式 merge ≠ 上線。要先確認 production `version.json` 含該修復，才用「已上線請驗收」macro 並轉 `resolved`。
- **禁用詞**（漏在公開留言 = 違規，§3.8）：欄位/表名（`StudentClass`、`schedules`、`rate_unit`…）、程式路徑（`XxxController::method()`、`XxxService`）、SQL/工具（`SELECT`、`Laravel`、`migration`、`CI`、`deploy.yml`、`Phase A/B/C`、`PR #nnn`）、內部縮寫（`B1`、`P0`、`R51`）。
- **送出前 30 秒自我檢查**：①每句老師/主任/家長看得懂嗎？②我們會做什麼講清楚了嗎？③要對方回覆的話，問題列清楚了嗎？④有沒有欄位/SQL/class 名漏出去？

## 1. Macro 索引

| # | 情境 | 對應狀態 | 是否需對方回覆 |
|---|------|----------|----------------|
| M1 | 已收到，正在看 | `new → triaged` | 否 |
| M2 | 需要截圖／更多資料 | `triaged` | 是 |
| M3 | 已確認問題，排修中 | `triaged → in_progress` | 否 |
| M4 | 已修好，等上線 | `in_progress`（**不可** resolved） | 否 |
| M5 | 已上線，請驗收 | `resolved` | 是（按「確認已修好／問題仍存在」） |
| M6 | 無法重現，需協助重現 | `triaged` | 是 |
| M7 | 不是故障，是使用方式 | `triaged → closed`（協議後） | 視情況 |
| M8 | 資料其實正確，是顯示／理解落差 | `triaged` | 是（確認理解一致） |
| M9 | 這是功能建議，已記錄 | `triaged`（轉 backlog） | 否 |
| M10 | 同一問題已有人回報（合併） | `triaged → closed` | 否 |

## 2. Macro 範本

### M1 — 已收到，正在看
**觸發**：剛分診完、附件已撈、已開 GitHub 追蹤。
**公開留言**
```
您好，已經收到您的回報，也看過附帶的畫面了。我們正在確認原因，會盡快處理。處理有進度會在這裡更新，謝謝您的回報。
```
**內部備註（is_internal_note=true）**
```
分診完成。附件 id [N] 已下載核對；reporter 歷史/跨分校已查。已開 GitHub #[NNN]。狀態 → triaged。
```
**禁用詞檢查**：無欄位/SQL/class/PR 編號 ✅

---

### M2 — 需要截圖／更多資料
**觸發**：資訊不足以判斷，需要回報者補畫面、時間、操作步驟。
**公開留言**
```
您好，謝謝回報。為了更快找到原因，想請您協助補充三件事：
1) 發生時您在哪一頁、按了什麼？
2) 大概是什麼時間發生的？
3) 方便的話附一張當下的畫面截圖。
有了這些我們會更快幫您處理，謝謝。
```
**內部備註**
```
資訊不足，已請 reporter 補頁面/時間/截圖。等回覆後再判斷是否轉 in_progress。
```
**禁用詞檢查**：無 ✅

---

### M3 — 已確認問題，排修中
**觸發**：已重現／已定位原因，進入修復。
**公開留言**
```
您好，我們已經確認這個狀況，也找到原因了，正在安排修正。修好上線後會再通知您確認，謝謝您的耐心。
```
**內部備註**
```
已重現/定位。根因：[一句話]。狀態 → in_progress。修復走 bug-fix-plan → branch → 測試 → 合併 → 部署。
```
**禁用詞檢查**：避免寫「已定位在某某 Controller」之類 ✅

---

### M4 — 已修好，等上線（⛔ 不可標 resolved）
**觸發**：程式已合併，但 production 還沒部署（例如 Actions/部署排隊中）。
**公開留言**
```
您好，這個問題我們已經修好了，正在安排更新上線。等實際更新到您的畫面後，會再請您幫忙確認，謝謝。
```
**內部備註**
```
修復已合併但尚未部署，production version.json 仍為舊 hash，禁止標 resolved。待部署成功（version.json 含此修復）後改用 M5。部署卡點追 #867/#870。
```
**禁用詞檢查**：勿寫「已 merge／等 deploy.yml」→ 改「修好了，正在安排更新上線」 ✅

---

### M5 — 已上線，請驗收
**觸發**：**已確認** production `version.json` 含此修復後才可用。
**公開留言**
```
您好，這個問題的修正已經更新上線了。麻煩您回到「Bug 回報」頁面，點「確認已修好」或「問題仍存在」讓我們知道結果。如果還有狀況，直接在這裡回覆我們，謝謝您。
```
**內部備註**
```
已確認 production version.json hash [xxxx] 含此修復。狀態 → resolved。等 reporter 驗收後 → closed（reporter-verify）。
```
**禁用詞檢查**：無 ✅

---

### M6 — 無法重現，需協助重現
**觸發**：照描述試過但無法重現。
**公開留言**
```
您好，我們照您說的情況試了幾次，目前還沒辦法重現同樣的狀況。想再請您幫個忙：下次再發生時，記下大概時間並截一張圖，告訴我們當下您在哪一頁、用手機還是電腦。這樣我們會更容易抓到原因，謝謝。
```
**內部備註**
```
無法重現。已試 [環境/角色/步驟]。請 reporter 補時間+裝置+頁面+截圖。狀態維持 triaged。
```
**禁用詞檢查**：無 ✅

---

### M7 — 不是故障，是使用方式
**觸發**：系統行為正確，回報者預期與設計不同。
**公開留言**
```
您好，謝謝回報。這部分其實是系統正常的設計：[一句白話說明正確操作或原因]。如果這樣的設計造成您使用上的不方便，也歡迎告訴我們，我們會把它記下來評估改進。
```
**內部備註**
```
非 bug，為預期行為。已向 reporter 說明。若 reporter 有改進訴求 → 轉功能建議 backlog；否則協議後 closed。
```
**禁用詞檢查**：說明用白話，勿引用設定欄位名 ✅

---

### M8 — 資料其實正確，是顯示／理解落差
**觸發**：數字/狀態其實正確，但畫面用語或呈現讓人誤會（如 #909 老師端 SYSTEM TRUST、繳費雙真相）。
**公開留言**
```
您好，我們對過資料，這個數字本身是正確的，問題在於畫面上的說明不夠清楚，容易讓人誤會。我們會把這裡的文字和呈現方式調整得更好懂。謝謝您幫我們發現這個地方。
```
**內部備註**
```
資料正確，屬顯示/文案/audience mismatch。歸 UI/UX 改善（M5）。勿改資料。對應 issue #[NNN]。
```
**禁用詞檢查**：勿寫「雙真相 OR 邏輯」「欄位顯示」→ 改「畫面說明不夠清楚」 ✅

---

### M9 — 這是功能建議，已記錄
**觸發**：可運作但回報者希望新增/改善功能。
**公開留言**
```
您好，謝謝您的建議，這是個很好的想法。目前系統還沒有這個功能，我們已經把它記錄下來，列入之後評估改進的清單。有進展會再讓您知道，謝謝。
```
**內部備註**
```
功能建議非 bug。已記 backlog / GitHub #[NNN]（type:enhancement）。狀態 triaged，不走修復流程。
```
**禁用詞檢查**：無 ✅

---

### M10 — 同一問題已有人回報（合併）
**觸發**：重複回報，已有主追蹤。
**公開留言**
```
您好，謝謝回報。這個狀況我們已經在處理中了，會一起修正。等更新上線後會通知大家確認，謝謝您一起幫忙留意。
```
**內部備註**
```
重複回報，主追蹤 in-app #[N] / GitHub #[NNN]。本筆 → closed（duplicate），狀態同步主追蹤。
```
**禁用詞檢查**：無 ✅

## 3. 套用守則（給接手的 AI／人）

1. **先選狀態，再選 macro**：macro 與 in-app 狀態一一對應，不要用 M5（驗收）卻沒實際部署。
2. **變數一定要換**：留 `[方括號]` 送出 = 不專業，且可能漏內部資訊。
3. **一則公開留言只講一件事**：要對方回覆就把問題編號列清楚（M2/M6）。
4. **公開留言送出後**，技術細節補在 GitHub issue body 或內部備註，不要塞進公開留言。
5. **改完 macro 庫**記得同步 `docs/INDEX.md` 入口與 #907；新增情境時保持「公開留言＋內部備註＋禁用詞檢查」三段格式。
