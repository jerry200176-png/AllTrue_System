## 2. 業務背景與影響

**痛點**：主任需要將吳品荅、陳儀倩的 4/25（六）課程移至 5/1（五），但調課按鈕觸發後收到錯誤訊息，無法完成基本行政操作，影響排課準確性與學生學習紀錄。

**錯誤鏈**：
1. 試聽容量守衛把 `one_on_three` 課型的學生誤算為佔用 trial 名額 → commit `9aa1f6f`（2026-04-20）已修正
2. PHP OPcache 仍服務舊版 `ScheduleController`，FR-001 `$isSameDaySubstitute` 判斷邏輯無效 → 修改原始碼檔案後 OPcache 自動失效
3. 多次失敗後 DB 產生孤兒資料（`rescheduled` 列無對應 `scheduled`，ClassSession 未移動）→ 手動 API 修補

**修復後預期行為**：
- `one_on_three` 課型不觸發 trial 容量限制
- OPcache 在部署後透過 reload 確保服務最新 bytecode
- 兩位學生的 `schedules` 均有配對的 `rescheduled`+`scheduled` 列，ClassSession 已移至 5/1

## 5. Acceptance Criteria

### AC-001：one_on_three 調課不觸發試聽容量限制
- AC-001-a：主任對 `one_on_three` 課型學生執行跨日調課，`POST /api/v1/schedules` 回傳 HTTP 201，`status=scheduled`
- AC-001-b：同一時段若已有另一位 `one_on_three` 學生（未超過課型上限 3 位），調課依然成功

### AC-002：跨日調課不觸發 FR-001 no_class_session 錯誤
- AC-002-a：`original_schedule_id` 指向日期 A 的 `rescheduled` 列，`schedule_date` 為日期 B（A ≠ B），API 回傳 HTTP 201，不回傳 `no_class_session` 422

### AC-003：調課後資料完整性
- AC-003-a：調課成功後，DB 存在成對的 `rescheduled`（原日期）+ `scheduled`（新日期）列，`scheduled.original_schedule_id` = `rescheduled.id`
- AC-003-b：`ClassSession` 的 `SessionDate` 已更新為新日期，`Status` 維持 `scheduled`

### AC-004：資料修補完成（吳品荅、陳儀倩）
- AC-004-a：Student 290（吳品荅）course 879 — `schedules` 有 ID 1205（rescheduled, 4/25）與 ID 1231（scheduled, 5/1）；ClassSession 7724 之 SessionDate = 2026-05-01
- AC-004-b：Student 284（陳儀倩）course 241 — `schedules` 有 ID 1232（rescheduled, 4/25）與 ID 1233（scheduled, 5/1）；ClassSession 1974 之 SessionDate = 2026-05-01

## 6. 功能需求 FR

### FR-001：ScheduleGuardService 不對 `one_on_three` 課型套用 trial 上限
修復後系統應該：當 `class_type = 'one_on_three'` 時，`buildTeacherDateOccupancyEntries` 不將其計入 `$existingTrialCount`，容量守衛依照 `one_on_three` 的容量上限（3）判斷。
**狀態**：已部署（commit `9aa1f6f`）

### FR-002：跨日調課 FR-001 條件正確排除
修復後系統應該：`ScheduleController::store` 中 `$isSameDaySubstitute` 僅在 `$origSched->schedule_date === $data['schedule_date']` 時為 `true`，跨日調課（原日期 ≠ 新日期）不觸發 `no_class_session` 422。
**狀態**：程式碼正確；OPcache 已因檔案修改而失效

### FR-003：部署流程保證 OPcache 刷新
修復後系統應該：每次後端部署完成後，執行 `php-fpm reload` 或透過 `/opcache_reset` 端點清除舊 bytecode，確保 PHP-FPM workers 服務最新程式碼。

### FR-004：孤兒資料防護（現有機制維持）
修復後系統應該：調課流程若中途失敗，前端顯示錯誤，且不留下無配對的 `rescheduled` 孤兒列（建議前端在 `scheduled` 建立失敗後嘗試刪除已建立的 `rescheduled` 列做補償）。

## 8. 技術方向

### 涉及檔案與方法

| 檔案 | 方法 | 修改說明 |
|---|---|---|
| `backend/app/Services/ScheduleGuardService.php` | `buildTeacherDateOccupancyEntries` | 排除 `one_on_three` 課型進入 trial 計數（已完成） |
| `backend/app/Http/Controllers/ScheduleController.php` | `store` | `$isSameDaySubstitute` 嚴格比較確保跨日調課不誤判（程式碼已正確） |
| 部署腳本 / `auto-frontend-deploy.mdc` | 部署後步驟 | 新增 `php-fpm reload` 或 opcache clear 呼叫 |
| `frontend/src/composables/course-management/useRescheduleAndMakeup.js` | `doReschedule` / `createScheduledEntry` | （選項）失敗時補償刪除已建立的 `rescheduled` 列，防止孤兒資料 |

### 架構取捨

- **OPcache 刷新策略**：選擇 `php-fpm reload`（graceful reload，不中斷現有請求）而非 `php-fpm restart`（會短暫拒絕連線）或 `opcache_reset()` 暴露端點（安全疑慮）。
- **孤兒資料補償**：選擇前端補償刪除而非後端原子事務，因後端 `schedules` 與 `ClassSession` 跨兩個 API，不在同一 DB 事務範圍；前端補償邏輯最小侵入。

### 8b. Decision Log

| 日期 | 決策 | 替代方案 | 選擇理由 |
|---|---|---|---|
| 2026-04-21 | 以 debug log 觸發 OPcache 失效，確認程式碼正確後移除 log | 重寫邏輯 | 程式碼本身正確，問題在 OPcache；最小異動 |
| 2026-04-21 | 以 API 呼叫修補孤兒資料（`POST /api/v1/schedules` + `POST /api/v1/learning-records/reschedule-session`）| 直接 SQL UPDATE | 走 API 確保 guard 與 LearningRecord 同步更新，符合業務邏輯 |
