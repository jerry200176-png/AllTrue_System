---

## 2. 目標與業務背景

**痛點：** 系統各分校工作人員在學生需續課時，未點「續報加購」（`purchase-batch`）而直接走「新增課程」流程。後者不觸發舊課程自動關閉，導致：

- 舊課程 `Stop=0`、`RemainingSessions=0`、`Paid=1` → 永久出現在各分校催繳名單
- 主任每次看到「已繳需續課」警示，但實際上學生已有新課程在上
- 累積的幽靈記錄干擾日常作業判斷，資料可信度下降
- 問題首先在新店分校被發現，但預計其他分校（興隆、大安、木柵）均有相同情況

**業務價值：**
- 清理後各分校催繳名單只顯示真實待處理案件，主任決策品質提升
- 建立正確操作引導後，減少未來各分校資料錯誤率

**KPI：**
- 全四間分校催繳名單「已繳需續課」幽靈記錄清零
- 未來因「直接新增課程跳過續報」產生的幽靈記錄新增數 = 0

---

## 3. 範圍

**In Scope：**
- 在催繳名單頁新增「已有新課程 → 結案」快速操作
- 新增課程時偵測重複（同學生同科目已有到期或即將到期付費課程）並警示
- 資料修正：透過 UI 讓主任一次性關閉現有幽靈課程

**Out of Scope：**
- 自動批次關閉（不做無人值守腳本，保留人工確認）
- 修改「續報加購」與「新增課程」的後端邏輯（既有流程不變）
- 跨分校「幽靈課程」統一批次管理介面（`super_admin` 專屬視圖列入 P2，本次 P0/P1 以各分校主任自助清理為主）

## 5. User Stories

**US-01（P0）結案幽靈課程**
> As a 主任, I want 在催繳名單中看到「已繳需續課」的記錄時，能直接確認「此學生已有新課程」並關閉舊課程, so that 催繳名單不再出現過期雜訊。

Acceptance Criteria:
- [ ] 「已繳需續課（renew_needed）」行新增「結案」按鈕
- [ ] 點擊後跳出確認 dialog，顯示：學生名、科目、原課程 ID、剩餘堂數
- [ ] 確認後呼叫後端關閉該 `StudentClass`（`Stop=1, closed_reason='settled'`）
- [ ] 成功後該行從催繳名單消失，顯示成功 toast
- [ ] 若無新課程（主任誤判）仍可關閉，但 dialog 需提示「關閉後此課程不再追蹤」

**US-02（P0）快速識別幽靈**
> As a 主任, I want 在「已繳需續課」行旁看到「同科目是否有其他課程在上」的提示, so that 我能快速判斷是幽靈記錄還是真正待續課。

Acceptance Criteria:
- [ ] 同一學生在同一分校有相同科目（`subject`）且 `Stop=0` 的**其他**課程時，顯示「已有新課程」標籤
- [ ] 標籤點擊可展開顯示新課程摘要（開課日、剩餘堂數）

**US-03（P1）防止重複新增**
> As a 工作人員, I want 在新增課程時被系統提醒「此學生此科目已有未結清課程」, so that 我知道應該用「續報加購」而非重新建課。

Acceptance Criteria:
- [ ] 在 `StudentsList.vue` 或 `CourseManagement.vue` 新增課程流程中，偵測同學生同科目已有 `Stop=0` 且 `RemainingSessions <= 2`（count mode）或最近到期（date mode）的課程
- [ ] 偵測到時彈出警示 dialog，說明「建議使用續報加購延續舊課程」，提供「前往加購」與「仍要新增」兩個選項
- [ ] 選「前往加購」時導向該課程的加購堂數 modal
- [ ] 選「仍要新增」時可繼續（保留操作彈性，但有明確記錄）

## 6. 功能需求（FR）

**FR-001**：催繳名單的 `renew_needed` 行必須顯示「是否已有相同科目活躍課程」的偵測結果（標籤）。

**FR-002**：催繳名單的 `renew_needed` 行需提供「結案」按鈕，呼叫後端將 `StudentClass` 設為 `Stop=1`, `closed_reason='settled'`。

**FR-003**：`GET /api/v1/alerts/tuition` 回應中，每個 `renew_needed` 記錄需附帶 `has_newer_course` 布林值與 `newer_course_id`（若存在）。

**FR-004**：`StudentsList.vue` 和 `CourseManagement.vue` 在新增課程流程中，提交前呼叫「重複偵測」檢查。

**FR-005**：重複偵測發現衝突時，前端彈出引導 dialog，使用者可選擇「前往加購」或「仍要新增」。

---

## 7. 非功能需求（NFR）

- 「是否已有新課程」偵測不得讓 `GET /api/v1/alerts/tuition` 回應時間超過 +200ms（使用 LEFT JOIN 或已有查詢的延伸，避免 N+1）
- 結案操作需在 transaction 內完成（`Stop`、`closed_reason`、`EndDate` 原子寫入）
- 重複偵測 API 回應 < 300ms；若偵測失敗，應 fail-open（警示不出現，流程不阻斷）

## 9. 資安與存取控制

- 「結案」操作限 `director` / `admin` / `super_admin` 角色（同現有 `pause` 端點限制），`teacher` 不可操作
- `close` 操作需驗證 `StudentClass.CampusID === 使用者所屬分校`（`require_campus` middleware）
- 重複偵測 API 同樣受 `require_campus` 限制，不回傳其他分校資料
- 結案為不可逆（需二次確認），應記錄操作者與時間（可寫入 `closed_reason` 附記或另行 log）
- STRIDE：Tampering 風險低（有 campus 隔離）；Info Disclosure 低（偵測只回傳同分校同學生資料）

## 10. QA 驗收標準

**FR-001 / FR-002 — 結案幽靈課程：**
- Happy Path：`renew_needed` 行、且同科目已有新 `Stop=0` 課程 → 顯示「已有新課程」標籤 → 點結案 → 確認 → 行消失、toast 顯示
- Edge：`renew_needed` 行但同科目無新課程 → 不顯示「已有新課程」標籤，仍可結案（含提示）
- Edge：結案後重整頁面，舊課程不再出現
- Error：後端結案失敗（網路錯誤）→ 顯示失敗 toast，行保留不消失
- Regression：參照 `docs/AI_REGRESSION_LESSONS.md`（停課語意、`closed_reason`、`purchaseBatch` auto-close 條件）

**FR-003 — 重複偵測：**
- Happy Path：同學生同科目有即將到期課程 → 彈出警示 → 選「前往加購」→ 加購 modal 開啟
- Happy Path：選「仍要新增」→ 正常新增流程繼續
- Edge：偵測 API 失敗 → fail-open，不阻斷新增流程，不顯示 dialog
- Edge：同科目課程已 `Stop=1` → 不觸發警示

**UI/UX 驗收清單：**
- [ ] 「已有新課程」badge 使用 success 色，與「已繳需續課」橘色視覺區隔明確
- [ ] 結案按鈕有 loading spinner 防重複點擊
- [ ] 確認 dialog 顯示完整課程資訊，危險操作有明確說明
- [ ] 成功 / 失敗 toast 出現位置一致、持續 3 秒
- [ ] 空狀態（清理完畢後）有圖示 + 說明文字
- [ ] 重複偵測 dialog 措辭正向引導（建議，而非阻斷）
