## 2. 目標與業務背景

### 痛點

1. **方案剩餘堂數錯誤**：學生蔡睿恩購買「一期 18 堂」方案，三科（數學 7 堂 + 物理 8 堂 + 化學 8 堂）合計已上 23 堂，但課程列表顯示「12（方案共用）」，嚴重誤導主任續課與催繳判斷。

2. **月學收漏計已結案課程**：主任在「學收月報」查 4 月學收時，若學生課程在月中結案（Stop=1），整月堂次消失，月收合計金額失真，無法對帳。

3. **兼職老師薪資以實際時間計算**：主任在備註欄微調老師到離時間（如 20:00→19:30）後，薪資被縮短為 1.5h 計費，與「契約時長固定薪資」共識相悖；反方向亦會多付。

4. **繳費日期失效**：新增課程時填入繳費日期，建立後課程列表仍顯示「未繳費」，主任需二次手動修改。

5. **課表回報管理頁面 HTTP 404**：主任開啟側欄「課表回報管理」（`schedule-discrepancy`）後，所有 API 請求均回傳 HTTP 404，管理頁完全無法使用。

### 背景

以上 2、3、4、5 均已於 2026-04-17 修復並合入 CHANGELOG，但 Claude Code 工具在後續操作中將這些修正回退，導致 regression 重現。Bug 5 的具體機制：CHANGELOG 明確記載 `backend/routes/api.php` 新增 7 條 `schedule-discrepancies` 路由，但現行 `api.php` 完全沒有這 7 條路由；Controller（`ScheduleDiscrepancyController.php`）與 Migration（`2026_04_17_200000`、`2026_04_17_200001`）均存在，僅路由註冊遺失。本 PRD 旨在重新套用並加強回歸防護。

### 業務價值

- 主任可信賴剩餘堂數數字，正確判斷催繳時機
- 月學收報表金額完整正確，降低對帳時間
- 兼職老師薪資符合契約，減少薪資糾紛
- 新增課程繳費狀態即時正確，降低行政錯誤

### 成功指標（KPI）

- 方案課程剩餘堂數與實際出席記錄一致（誤差 = 0）
- 月學收報表含 Stop=1 且當月有出席堂次的課程（漏計率 = 0）
- 兼職薪資計算以契約時長為準，不受備註時段影響（誤差 = 0）
- 新增課程時填入繳費日期後，payment_status 立即為 paid（成功率 = 100%）

## 5. User Stories

### US-01：方案剩餘堂數正確顯示

> **As a** 主任，**I want** 在課程列表看到方案學生正確的共用剩餘堂數，**so that** 我可以準確判斷何時提醒家長續費。

Acceptance Criteria：
- [ ] 方案（CoursePackage）內所有科目顯示的「方案共用剩餘堂數」= 方案總堂數 − 所有成員科目的實際出席堂次總和
- [ ] 剩餘堂數最低顯示 0，不出現負數
- [ ] 即使 PackageSessionLedger 資料不完整，顯示數值仍正確

### US-02：月學收報表包含已結案課程

> **As a** 主任，**I want** 月學收報表顯示當月所有有出席堂次的課程（含已結案），**so that** 月收金額對帳正確無漏項。

Acceptance Criteria：
- [ ] 查詢 N 月學收時，Stop=1 但當月有 attended 堂次的課程仍出現在報表中
- [ ] 已結案課程列有明顯視覺標示（badge + 降低 opacity）
- [ ] CSV 匯出包含「課程狀態」欄（進行中 / 已結課）
- [ ] Stop=1 且當月無堂次的課程不出現

### US-03：兼職老師薪資按契約時長計算

> **As a** 兼職老師，**I want** 薪資以契約排定的上課時長計算，**so that** 主任在備註欄微調到離時間不會影響我的收入。

Acceptance Criteria：
- [ ] 薪資計算優先讀取按星期的契約時長設定，次讀課程預設時長，最後才用實際簽到時間
- [ ] 主任在備註欄把 20:00 改成 19:30，薪資仍以 2h 計（不縮為 1.5h）
- [ ] 併堂加給的重疊區間計算也以契約時長為依據

### US-05：課表回報管理頁面正常載入

> **As a** 主任，**I want** 開啟側欄「課表回報管理」後能看到老師回報的清單，**so that** 我可以確認並處理現場課表出入問題。

Acceptance Criteria：
- [ ] 主任點擊側欄「課表回報管理」後，API 回傳 200（非 404）
- [ ] 管理頁顯示 pending / acknowledged / resolved 三個 tab，各 tab 可切換
- [ ] 主任可將 pending 回報標記為「已確認」（acknowledged）
- [ ] 主任可將 acknowledged 回報標記為「已修正」（resolved），且需填入 ≥10 字的處理說明
- [ ] 老師端（AttendancePage）「回報出入」按鈕與「已回報」徽章功能正常（路由恢復即可）

### US-04：建立課程繳費日期正確落地

> **As a** 主任，**I want** 建立課程時填入繳費日期後，課程清單立即顯示「已繳費」，**so that** 不需要二次手動切換狀態。

Acceptance Criteria：
- [ ] 新增課程時填入 paid_at，建立後 payment_status = paid
- [ ] 剩餘堂數計算不得修改 Paid / PayDate 欄位

## 6. 功能需求（FR）

### FR-001：方案剩餘堂數動態聚合

系統應在課程列表 API 中，對方案成員課程的剩餘堂數，使用當前實際出席堂次的聚合結果（而非 PackageSessionLedger 快照），計算方式與個別課程的觀測已用堂數邏輯一致。

### FR-002：月學收 API 移除 Stop 快照過濾

系統應讓月學收 API 以「當月有無出席堂次」作為唯一過濾條件，而非以課程當前的 Stop 旗標過濾；API response 應包含 is_stopped 欄位。

### FR-003：月學收 CSV 加入課程狀態欄

系統應在 CSV 匯出最右側新增「課程狀態」欄，值為「進行中」或「已結課」。

### FR-004：月學收前端視覺區分已結課

系統應在月學收報表頁面，對 is_stopped=true 的列套用降低 opacity 的樣式，並顯示「已結課」badge，且 badge 帶 title 說明文字。

### FR-005：兼職薪資以契約時長優先

系統應以「契約排定時長（按星期 > 課程預設時長 > 實際時間 > 2h 預設）」計算兼職老師薪資；備註欄時段調整不得影響薪資金額。

### FR-006：併堂加給以契約時長計算重疊

系統應以契約排定時長（非實際簽到時間）建構每堂的時間區間，計算是否有併堂重疊與對應加給。

### FR-008：課表回報管理 API 路由恢復

系統應在 `backend/routes/api.php` 中正確註冊以下 7 條路由，並套用對應 middleware，使課表回報管理頁面可正常呼叫後端：

- `POST /api/v1/schedule-discrepancies`（老師 + 主任可建立回報）
- `POST /api/v1/schedule-discrepancies/{id}/withdraw`（老師軟取消自己的回報）
- `GET /api/v1/schedule-discrepancies/my`（老師查自己的回報）
- `GET /api/v1/schedule-discrepancies/active-for-session`（出缺勤頁徽章用）
- `GET /api/v1/schedule-discrepancies`（主任列表，require_campus）
- `GET /api/v1/schedule-discrepancies/summary`（儀表板計數，require_campus）
- `PUT /api/v1/schedule-discrepancies/{id}`（主任更新狀態）

### FR-009：課表回報 Migration 確認執行

### 架構選擇理由

**FR-001（剩餘堂數）**：選擇「在 API 層動態聚合」而非「修復 ledger 歷史資料」，原因是：ledger 遺失的根本原因未確認（可能是課程後綁方案、也可能是歷史路徑未觸發），動態聚合能保證顯示值永遠與出席事實一致，且不需要 migration 或 backfill；代價是課程列表請求會多一次跨科成員查詢，但方案成員數通常 ≤ 10，效能可接受。

**FR-002/003（月學收 Stop 過濾）**：選擇「移除 Stop 條件，依賴 INNER JOIN 過濾零堂次」，因為 INNER JOIN 已保證只回傳有出席堂次的課程，額外的 Stop 快照條件是語意錯誤（以當前狀態過濾歷史月份事實）。

**FR-005/006（薪資時長）**：選擇「翻轉 calcHours 優先順序」而非新增欄位，因為 `resolveSessionDurationForWeekday` 已存在於 StudentClass 模型，只需改變讀取順序，不需 migration。

**FR-007（Paid 清零）**：選擇「直接移除三行程式碼」，因為 recomputeCounters 的責任邊界是教務統計（堂數），不是財務決策；移除後無資料遷移需求，可安全回滾。

**FR-008（課表回報路由）**：`ScheduleDiscrepancyController` 已存在且完整，Migration 也已存在，問題純粹是 `api.php` 中缺少路由註冊。選擇「補回路由」而非「重建 Controller」，因為 Controller 本身未被回退，只有 `api.php` 中的 7 行路由遺失。路由順序需注意：`my`、`summary`、`active-for-session` 等精確路徑必須在 `{id}` 萬用路由之前註冊，防止 Laravel route 誤判。

## 9. 資安與存取控制

- **存取控制**：月學收 API 與薪資 API 均已由現有 middleware 限制為 `role:director` 或 `role:super_admin`；課表回報路由恢復後，建立 / 撤銷 / 查詢自己的回報需 `role:director,teacher` + `require_campus`；主任列表 / summary / 更新狀態需 `role:director` + `require_campus`
- **分校隔離**：FR-001 批次成員查詢必須在 campusIds 範圍內；FR-008 的 `GET /schedule-discrepancies` 需 `require_campus` middleware，`store` 時需驗證 `branch_id` 與 token 分校一致（Controller 已實作 `canAccessBranch` 檢查）
- **PII**：課表回報欄位含 `student_name`（老師填寫的文字描述，非系統 Student 關聯），屬一般教務資料；is_stopped 為布林值，無新增 PII 疑慮
- **稽核 log**：課表回報的狀態異動（acknowledged_by/_at, resolved_by/_at）已在 `schedule_discrepancies` 資料表欄位記錄，無需額外 log
- **STRIDE 快評**：
  - Spoofing / Tampering：FR-008 的 `reporter_id` 強制由 token 注入（Controller 已實作），不接受 body 覆蓋，無 Tampering 風險
  - Information Disclosure：需確認 FR-001 批次成員查詢有 campusId 過濾；`GET /schedule-discrepancies` 需 `require_campus` 確保主任只見自己分校的回報（風險：中，Controller 已有 scope 限制，路由 middleware 需一併確認）
  - Repudiation / DoS / Elevation：N/A

**OQ-01：FR-001 分頁時方案聚合範圍**

- **問題**：課程列表分頁顯示時，若方案的 3 個成員科目分散在第 1、2 頁，第 1 頁只看到 2 科，剩餘堂數聚合是否完整？
- **業界解法**：「View-layer pagination 不得截斷 aggregate 的計算來源」（標準 CQRS 原則）。做法：在建立 `$packageMap` 時，對頁面上出現的所有 `PackageID` 一次性查詢**全部**成員（不限於當頁），再做 `batchObservedUsedSessions` 聚合。此設計確保 aggregate 永遠來自完整成員集，代價是多一次跨科成員查詢（通常 < 5ms，可接受）。
- **結論**：FR-001 的實作即採用此模式，OQ-01 已在實作中解決，無需額外決策。**關閉**。

**OQ-02：月結方案在月中結案的計費語意**

- **問題**：`CoursePackage.stop=true`（月結方案）在 4 月 15 日結案，4 月學收應計整月還是按出席？
- **業界解法**：訂閱制系統通常有兩種模型：
  1. **Pro-rata（比例計費）**：按天數比例，4/15 結案 = 半月費用。適合固定月費（如 SaaS）。
  2. **Session-based（出席計費）**：月費 = 當月實際出席堂次 × 單堂費。適合本系統已有的按堂計費邏輯（與 `branchMonthlyTuition` 的 `COUNT(attended sessions)` 一致）。
  - 本系統月結方案的 `rate_unit` 需確認是 `'monthly'`（固定月費）還是 `'session'`（按堂計）。若為按堂計，月中結案自然以出席堂次計費，無需特殊處理（`INNER JOIN sc_counts` 已確保只計有出席的月份）。若為固定月費，則需決定 pro-rata 規則。
- **建議**：本次不實作 pro-rata（超出 Bug Fix 範圍）；在月學收頁面對月結方案顯示說明文字「月結方案費用以實際出席堂次計算」。產品確認語意後，另立 P1 PRD 實作。**保持開放，Owner：PM**。

**OQ-03：月學收頁面空狀態設計**

- **問題**：月學收頁面在無資料時是否有完整的空狀態（圖示 + 說明 + 引導）？
- **業界標準**：Google Material Design、Apple HIG 均要求空狀態包含三要素：圖示（代表內容類型）、說明文字（告知原因，如「本月暫無學收資料」）、引導行動（如「請確認月份選擇」或「前往新增課程」）。純空白或「無資料」文字屬不合格空狀態。
- **解法（P1）**：若現有頁面缺少完整空狀態，由 UI/UX Designer 設計後補充。建議文案：標題「本月暫無學收資料」，說明「所選月份內沒有任何已出席的堂次記錄」，引導「可切換月份或前往課程管理確認課程狀態」。**本次 Bug Fix 不強制，列為 P1 後續任務，由 UI/UX Designer 確認後實作。**

**OQ-04：快照式月學收報表（長期架構）**

- **問題**：現行做法以「查詢當月出席堂次」即時計算，月份切換快，但若月份為歷史月且有資料異動（補登、取消），數字會變動；主任期望月結後的報表「凍結」。
- **業界解法**：財務系統標準做法為「月結快照（Monthly Close Snapshot）」：
  1. 月底（或主任手動觸發「月結」）時，將當月試算結果寫入 `monthly_tuition_snapshots` 表（含版本號、建立時間、建立人）。
  2. 查詢歷史月份時優先讀快照；查詢當月（未月結）仍即時計算。
  3. 月結後若有補登，需走「重新月結」流程（需超管授權），保留稽核軌跡。
  - 類比：ERP 的 Period Close；SaaS 訂閱系統的 Invoice Finalization。
- **結論**：本次 Bug Fix 不實作快照架構（OQ-04 為 P2 架構評估，列入技術債 backlog）。近期以「移除 Stop 快照過濾」作為最小修正，接受「補登後歷史月份數字可能變動」的已知限制，並在 UI 加 disclaimer（「歷史月份數字以實際出席記錄為準，如有補登將即時反映」）。**保持開放，Owner：CTO，P2**。

**OQ-05：`Campus.staff_line_group_id` 目前無設定值**

- **現況確認**：已確認目前所有分校的 `staff_line_group_id` 為 null，課表回報建立時 LINE 推播靜默略過（`ScheduleDiscrepancyNotifier` fail-safe 設計，不阻擋 API）。
- **影響**：404 修復（FR-008）完全不受 LINE 設定影響；修復後主任可正常使用課表回報管理，僅是老師提交回報時主任**不會收到 LINE 通知**。
- **業界解法（分三個層次）**：
  1. **立即（P0，本次隨 FR-008 一併處理）**：系統已有 graceful fallback，無需額外程式改動。在 `docs/OPERATIONS_RUNBOOK.md` 補充「設定員工 LINE 群組通知」操作步驟（如何取得 `staff_line_group_id` 並更新至 DB）。
  2. **短期（P1，下一個 Sprint）**：在主任後台「分校設定」頁新增「員工 LINE 群組設定」欄位，讓主任自助填入；儲存後顯示「設定完成，老師回報時將自動推播通知」。類似 GitHub Webhook 設定 UI，降低 IT 介入門檻。
  3. **中長期（P2）**：整合 LINE LIFF 讓主任一鍵授權，或改為使用系統內建「站內通知 + 推播（Web Push / FCM）」，不依賴 LINE 平台可用性（降低對第三方的單點依賴）。
- **本次行動**：補充 OPERATIONS_RUNBOOK 設定步驟，標記 P1 UI 設定頁任務，**OQ-05 解法已確認，後續由 PM 排入 P1 backlog**。
