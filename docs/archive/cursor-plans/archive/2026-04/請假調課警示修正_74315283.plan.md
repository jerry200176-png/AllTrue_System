# 請假調課後堂次警示修正計畫

## 問題定位
- 現況警示條件在 [frontend/src/pages/CourseManagement.vue](/home/admin/frontend/src/pages/CourseManagement.vue) 使用 `sessionUnits(c).length !== getPurchasedSessions(c)`。
- `sessionUnits(c)` 只排除 `cancelled`，但**仍包含 `leave/leave_adjusted`**，導致「請假原堂 + 補課新堂」會多 1 列，出現假陽性。
- 後端既有堂次口徑（[backend/app/Http/Controllers/StudentClassController.php](/home/admin/backend/app/Http/Controllers/StudentClassController.php) 的 `extendSessionsIfNeeded`）已明確排除 `cancelled/leave/leave_adjusted`，前後端口徑不一致是主因。

## 修正目標
- 讓「排程列數與購買堂數不一致」只在**真正異常**時顯示。
- 與既有商業規則對齊：請假不占購買堂數、取消不占購買堂數，補課應回補可用堂次。
- 不改動既有排課/扣堂核心流程，只修正警示判定與可觀測性。
- 保持「警示用計數」與「剩餘堂數/已上堂數」解耦，避免 UI 警示修正反向影響財務或扣堂口徑。
- 將「可被 QA 驗收」納入設計輸出，避免只修程式但缺乏可驗證標準。
- 維運可快速定位：當現場回報誤警示時，IT 能用日誌與腳本在 10 分鐘內判讀是否為資料、邏輯或顯示問題。

## IT/維運準則（新增）
- **先觀測後處置**：先透過診斷欄位確認計算來源，再決定是否需修碼或資料修復。
- **不直接改資料**：針對歷史異常先提供 dry-run 報表，人工確認後才執行修復。
- **最小暴露原則**：日誌僅記錄必要識別欄位（course_id、branch_id、status counts），避免姓名/電話外洩。
- **可回滾優先**：本次調整須可在短時間回退前端判定與文案，不依賴資料結構變更。

## QA 驗收標準（新增）
- **功能正確性**：對指定案例，警示顯示/不顯示結果與預期 100% 一致。
- **數字穩定性**：`已上 N / 購買 M / 剩餘堂數` 與修正前比對，不得出現非預期變動。
- **文案可判讀**：使用者可區分「真異常」與「待補課」，不再把正常請假流程視為系統錯誤。
- **角色一致性**：director 與 teacher 在可見範圍內對同一課程看到一致警示結論。
- **分校隔離**：不同 `branch_id` 下警示計算僅使用該分校資料，不可受他校列影響。

## 架構原則（新增）
- **單一真相**：狀態是否占購買堂數，只能由一組共用 helper/常數決定。
- **用途分離**：`warningCount`（警示）與 `remainingCount`（剩餘堂數）可共享基礎資料，但不共用業務語意。
- **向後相容**：保留 `excused` 作為歷史輸入兼容，輸出仍以 `leave` 語意解讀。
- **可觀測性**：對「列數不一致」拆成可解釋訊號（超排、待補、資料異常）供 PM/營運判讀。

## 實作步驟
1. 調整警示判定來源（前端）
- 在 [frontend/src/pages/CourseManagement.vue](/home/admin/frontend/src/pages/CourseManagement.vue) 把警示比較基準從 `sessionUnits(c).length` 改為 composable 提供的非請假堂次計數（`countNonLeaveSessions(c)`），或等價的新 helper（例如 `effectiveScheduledCount(c)`）。
- 保持條件 `isSessionMode(c)` 與 `purchased > 0`，避免月結課誤觸。

2. 收斂口徑到單一 helper（前端 composable）
- 在 [frontend/src/composables/course-management/useCourseSessionsDisplay.js](/home/admin/frontend/src/composables/course-management/useCourseSessionsDisplay.js) 明確定義「警示計數口徑」：排除 `cancelled/leave/leave_adjusted/(兼容 excused)`。
- 將警示、堂次序號、剩餘堂數估算共用同一口徑，避免未來再分裂。
- 新增狀態矩陣註解（或常數命名）讓工程師可一眼看出哪些狀態「占購買額度 / 不占購買額度 / 只顯示不計算」。

3. 補強警示文案與分類（前端）
- 若有效堂次 `>` 購買堂數：維持「排程列數與購買堂數不一致」。
- 若有效堂次 `<` 購買堂數且存在請假：改為「目前有請假堂次，待補課後會與購買堂數對齊」或等價文案，避免使用者誤判系統錯誤。
- 若偵測到同日重複且狀態衝突（例如 `cancelled + scheduled`）：顯示次級提示，引導使用者開啟編輯確認。

4. 補充回歸測試（至少 5 組）
- 新增前端單元測試（若目前沒有前端測試框架則先補輕量 regression 腳本/測試計畫文件），覆蓋：
  - 請假 + 補課（購買 8、顯示 9 列但有效 8）=> **不顯示警示**。
  - 單純多排一堂（有效 9 vs 購買 8）=> **顯示警示**。
  - 單純請假未補（有效 7 vs 購買 8）=> **顯示警示**（可提示尚需補課）。
  - `cancelled + scheduled` 同格並存 => 以有效堂次規則不誤報。
  - 歷史 `excused` 資料 => 不因舊狀態造成錯誤警示。
- 後端補一組 Feature regression（`ClassSession` 混合狀態輸出），確保 API 不會把不應占堂的狀態回傳成可扣堂計數來源。

5. 補齊 IT 診斷能力（後端/前端）
- 在可控範圍加入診斷輸出（開關式）：`course_id`、`purchased`、`warningCount`、各狀態堂次分佈。
- 前端 debug 資訊僅在開發或指定旗標下可見，正式環境預設關閉。
- 後端 logging 走既有 logger channel，避免大量噪音影響 Raspberry Pi I/O。

6. QA 驗證清單
- 在課程管理頁驗證 chips 顯示與警示一致：
  - 已上/請假/補請假/取消混合狀態。
  - 同日多筆（`cancelled + scheduled`）案例，確認不互相干擾。
- 交叉檢查「已上 N / 購買 M」與剩餘堂數數字未被此修正破壞。
- 補一組真實案例重演：你目前提到的「購買 8、已上 6、剩 2，且含請假/調課」要在修正後不再出現誤警示。
- 角色驗證：同案例分別用主任/老師帳號檢查警示與文案一致。
- 分校驗證：同名學生跨分校資料下，切換分校後警示不得互相污染。

## 測試資料設計（新增）
- CaseA（主案例）：購買 8、已上 6、請假 1、補課 1、剩餘 2，預期**不顯示異常警示**。
- CaseB（超排）：購買 8、有效堂次 9，預期顯示「排程列數與購買堂數不一致」。
- CaseC（待補）：購買 8、有效堂次 7 且有請假，預期顯示待補課型提示。
- CaseD（同格雙列）：同日同時段 `cancelled + scheduled`，預期不因 cancelled 誤判。
- CaseE（歷史相容）：含 `excused` 舊資料，預期與 `leave` 同口徑處理。

7. 文件更新
- 在 [docs/CHANGELOG.md](/home/admin/docs/CHANGELOG.md) 記錄「警示從總列數改為有效堂次口徑」。
- 在 [docs/AI_REGRESSION_LESSONS.md](/home/admin/docs/AI_REGRESSION_LESSONS.md) 新增一段防回歸說明：請假列不可直接拿來比購買堂數。
- 在文件中加上狀態矩陣（哪些狀態占購買堂數），作為未來改動的唯一參考。
- 在 [docs/OPERATIONS_RUNBOOK.md](/home/admin/docs/OPERATIONS_RUNBOOK.md) 加入「警示誤報排查 SOP」：查詢順序、觀測欄位、回滾與通報流程。

## IT 上線與回滾流程（新增）
- 上線前：
  - 確認 `frontend` 變更完成後執行 `cd /home/admin/frontend && npm run deploy`。
  - 執行 API health check（`/api/v1/health` 或既有健康端點）與登入後關鍵頁 smoke test。
  - 檢查 `backend/bootstrap/cache` 未殘留異常快取造成舊邏輯持續生效。
- 上線後：
  - 30 分鐘內追蹤錯誤日誌與警示觸發趨勢是否異常飆升。
  - 由值班人員抽查 2 個真實課程（含你的主案例型）確認結果。
- 回滾：
  - 若誤報/漏報超過門檻，回退前端資產至上一版本並刷新 nginx 靜態快取。
  - 保留診斷日誌與案例 ID，作為下一輪修正輸入。

## 上線 Gate 與監控（新增）
- 合併前 gate：
  - 前端回歸案例全數通過。
  - 後端混合狀態 regression 通過。
  - 主案例（CaseA）手測影片或截圖留存。
- 上線後觀測（3-7 天）：
  - 課程管理頁警示觸發率（抽樣）是否下降且無漏報。
  - 客服/營運是否仍回報「8堂顯示不一致」同類問題。
- 回滾條件：
  - 若發現「真異常被吞掉」或「剩餘堂數異常波動」，立即回滾文案與判定切換點，保留資料不回寫策略。
  - 若 24 小時內同類客服回報超過基準值（例如 >=3 件），啟動 incident 流程與熱修評估。

## 風險與防呆
- 風險：若只改 UI 條件、未統一 helper，後續功能很容易再出現不同口徑。
- 防呆：以 composable 單一函式輸出「有效堂次數」，頁面僅消費結果。
- 兼容：保留 `excused` 判定分支，避免歷史資料造成新一輪誤報。
- 產品風險：若文案不分「真異常」與「待補課」，主任會把正常業務情境誤認為系統錯誤；需同步優化提示語意。
