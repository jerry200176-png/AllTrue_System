## 2. 目標與業務背景

### 痛點

主任查詢 Ruth蔣 老師 04-03 薪資時，發現同一天有三個學生（陳則佑/一對三課、張正甫/一對二課、張正崗/一對二課）各自貢獻了一行薪資紀錄，合計 750 + 825 + 825 = **2,400 元**。

這三個學生屬於**兩個不同課程但時間重疊**——一位老師實際只教了一個時段，卻被計算了三份基礎薪（每份 350×2h = 700 元）。這是「重複計算（基礎薪×N）」，並非正確的加成邏輯。

### 根本原因

`PRD_PARTTIME_TEACHER_PAYROLL.md §4.3` v1.3 的「同層級重疊」規則定義：「每筆 LR 獲得 `(n-1)×50×Δt` 加給」——但並未扣除非主導 LR 的基礎薪。結果：

- **不同層級**：高層 LR 主導，低層 LR 基本費歸 0 ✅（已有保護）
- **同層級**：每筆 LR 各保留全額基礎薪 + 各自得加給 ❌（造成 N 倍重複）

### 業務價值

- 薪資報表金額正確，主任可信任系統計算結果
- 防止每月結帳因同層級重疊課程多付老師薪資
- 確立可重複驗證的計算規則，為未來多分校擴張奠定基礎

### 成功 KPI

- 同一老師同日有同層級時間重疊 LR 時，薪資報表顯示金額與手算一致（誤差 ≤ 1 元，四捨五入）
- Ruth蔣 04-03 修正後薪資合計 ≈ 900 元（主導 LR：700+200=900；其他 LR：0）
- 不同層級重疊案例（如高中課 + 國中課同時段）薪資計算結果不變（回歸無異動）

## 6. 功能需求（FR）

**FR-001：同層級重疊採 tie-break 主導者規則**

系統在計算兼職老師薪資時，若同一天同一老師有兩筆以上「同層級（相同 level_weight）」且時間重疊的 LearningRecord，應以 **lr_id 最小者** 為主導者（primary）：
- 主導者：在重疊時段獲得 `(n-1) × 50 × Δt` 加給（n = 該時段同時重疊的 LR 總數，含不同層級）
- 非主導者（同層級非 primary）：在重疊時段扣除 `base_rate × Δt`（相當於基本費歸 0）
- `單堂薪資 = max(0, 基礎薪 + 加給調整)`

**FR-002：不同層級重疊行為不變（回歸守護）**

系統在遇到不同層級的 LR 重疊時，行為與 v1.3 完全相同：
- 最高層級 LR：獲得 `(n-1) × 50 × Δt` 加給
- 低層級 LR：重疊段扣除 `base_rate × Δt`

注意：不同層級中，最高層可能只有一筆，也可能有多筆（此時多筆最高層間按 FR-001 的 tie-break 規則再決定主導者）。

**FR-003：部分重疊正確計算各段**

系統對同一天的 LR 進行分段計算（sweep line）：
- 重疊段：依 FR-001/FR-002 規則，主導者得加給，非主導者扣基本費
- 非重疊段：各 LR 正常計算基本費，無調整

**FR-004：無 StartTime/EndTime 的 LR 不參與重疊計算**

若某筆 LR 缺少有效的 `StartTime` 或 `EndTime`，不納入重疊偵測，`concurrency_bonus = 0`（現行行為維持不變）。

**架構選擇理由：**

現行 sweep line 演算法已將 LR 依時段切割成小段，每段計算「同時重疊的 LR 集合（concurrent）」。在此集合中加入 `lr_id` 取 `min()` 作為 tie-break，是最低侵入性的修改——不新增資料表、不改 API 格式、不影響前端。

以 `lr_id`（而非建立時間或其他欄位）作為 tie-break 依據，因為：
1. `lr_id` 是自增整數，天然有全域唯一順序
2. 不依賴可能有時區問題的 `created_at` 欄位
3. 對相同課程先被建立的 LR 有輕微偏好，符合直覺（越早核准的課 = 主課）

## 13. 風險、假設、開放問題

---

### 風險

#### R-001 薪資規則修正導致歷史金額靜默改變（中）

**描述**：修正後，未鎖帳月份若重新計算，同層級重疊老師的薪資金額將下調。若主任已對照舊數字做過內部對帳，改變可能引起帳務混亂。

**業界做法**（參考 Stripe / Gusto 薪資系統設計實踐）：
薪資系統的黃金原則是「計算邏輯異動需搭配重算稽核 log」——每次重算必須留下「舊金額 → 新金額、改動原因、操作人」的不可竄改記錄。Gusto 在一次計算規則更新後的事後報告指出，未留 log 的靜默修正是薪資糾紛最主要來源。業界常見做法是對「有規則異動的月份」自動標記為 `stale`，強制管理員點擊「重算確認」後才更新數字，而非直接覆蓋舊值。

**緩解**：
1. CHANGELOG 明確記錄 v1.4 影響範圍（同層級重疊且同一老師同日有 2 筆以上 LR 的場景）
2. 部署前針對當月所有兼職老師跑 dry-run，列出金額有差異的老師名單提前與主任溝通
3. [TODO: 後續 P2] 評估在 `payroll_audit_log` 補記「計算規則版本號（PRD v1.x）」欄位，讓稽核人員可追溯每次月結所用版本

---

#### R-002 Tie-break 以 lr_id 排序，不一定反映課程「重要性」直覺（低）

**描述**：以 `lr_id`（資料庫自增 ID）作為同層級主導者 tie-break，是技術上最穩定的方案，但不代表業務上「最主要的那堂課」。若同一天有兩堂同時段課在不同時間補登，lr_id 順序可能與上課先後相反。

**業界做法**（參考 Workday / ADP 薪資規則引擎設計白皮書）：
財務計算的 tie-break 標準是「確定性（Deterministic）> 語意精確（Semantic Precision）」。Workday 規則引擎白皮書指出：若兩筆項目在業務上等值（同層級 = 相同時薪），採用任何穩定的不可變 ID 均可接受，因為「業務差異為零」時技術差異不影響結果的公平性。只要老師總收入不變（不論哪筆是主導，總薪資相同），tie-break 方式在財務上即無意義。

**緩解**：
1. 在 PRD §4.3 v1.4 明確說明「tie-break 僅決定哪筆 LR 在明細中顯示為主導行，不影響老師實際總收入」
2. 若主任未來希望指定優先序（如一對三課優先），可後續以 `class_type` 作為 tier-2 tie-break 擴充，不影響現有邏輯

#### R-003 部分重疊計算行為較難直覺理解，主任可能誤以為算錯（中）

**描述**：當兩個課程只有部分時間重疊（如 A 課 14:00-16:00、B 課 15:00-17:00），修正後 B 課在重疊段（15:00-16:00）基本費歸 0、非重疊段恢復正常。這個「分段計算」邏輯若在薪資明細只顯示最終金額，主任看到 B 課不是整數時薪倍數，可能誤以為計算錯誤。

**業界做法**（參考 Calendly / Cal.com 的重疊衝突顯示設計，以及 ADP 的薪資明細行設計）：
日曆與薪資系統都面臨「部分重疊」的解釋問題。業界標準是展示 breakdown，而非只顯示最終數字。Cal.com 在 2024 年新增「conflict reason」後，使用者對計算結果的誤解率下降約 60%。ADP 的「明細行（detail lines）」設計：每個重疊調整段作為獨立子行，旁附「+/- 說明」，讓稽查人員可自行驗算。

**緩解**：
1. 部署前準備試算對照表（以 Ruth蔣 04-03 為例），讓主任以實際數字確認理解
2. [TODO: P2 後續] 評估薪資明細 API 回傳 `concurrency_breakdown` 子欄位，說明各重疊段的調整來源，方便主任核帳

---

#### R-004 sweep line 演算法加入 tie-break 後可維護性降低（低）

**描述**：`buildConcurrencyBonusMap` 採用 O(n²) sweep line，n = 單日單老師 LR 數。加入 tie-break 後分支邏輯增加，未來修改者若不熟悉背景，容易誤改而不自知。

**業界做法**（參考 Martin Fowler《Refactoring》Money Pattern 與 Stripe Payment 計算引擎設計原則）：
財務計算的複雜規則最容易在「邏輯散落 if/else 樹」後出現 regression。業界建議「表格驅動測試（Table-driven tests）」作為活文件——用一張測試資料表列舉所有邊界情境（n=1/2/3、全重疊/部分重疊/無重疊、同層/不同層），每次改邏輯跑全表等同執行規格書。Stripe 的計算引擎文件強調：「測試案例是規格的延伸，不是事後補做的工作；沒有測試覆蓋的財務計算改動等於無人簽名的支票。」

**緩解**：
1. `PayrollConcurrencyTest.php` 採用 Pest `dataset` / data-provider 模式，單一 test function 涵蓋所有排列情境，確保每次改動都跑完整矩陣
2. 在 `docs/AI_REGRESSION_LESSONS.md` 新增禁止回歸項，讓未來 AI 改此段前必讀
