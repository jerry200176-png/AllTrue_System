# PRD：評量表日期可視性與科目分類改善

---

## 1. 文件資訊

| 欄位 | 內容 |

| 版本 / 日期 | v1.0 / 2026-04-19 |
| 狀態 | Draft |
| 目標角色 | 主任（審核）、老師（填寫）；受益：能更快找到特定學生特定科目的評量記錄 |

## 2. 目標與業務背景

**痛點**

- **痛點 A（隱藏舊評量）**：`LearningRecordsPage.vue` 預設每頁 50 筆，按 `SessionDate desc` 排序，無預設日期範圍。若一個學生的某堂課是 2 個月前，該筆評量可能落在第 2 頁以後，老師或主任不知道要繼續點「載入更多」，容易以為「沒有資料」，甚至質疑系統邏輯正確性。
- **痛點 B（科目混排）**：同一學生同一 accordion 群組中，不同科目的評量記錄交錯排列，缺乏科目層級的分隔，與「課程管理」頁的分類呈現方式不一致，閱讀效率低。

**業務價值**

- 主任不需要猜測是否有遺漏的評量需要審核。
- 老師可在同科目脈絡下連貫查閱學生的學習進展。
- 減少「以為系統有 bug」的誤判與客服溝通成本。

**成功指標（KPI）**

- 主任「找不到特定評量」相關回報降為 0 件 / 月（目前偶發）。
- 老師在評量頁找到指定科目歷史記錄的平均操作步驟 ≤ 2 步。

## 3. 範圍

**In Scope**

- 在評量列表頁（`LearningRecordsPage.vue`，主任視角）加入「科目」篩選器。
- 學生 accordion 內改為依科目子分組，顯示科目標題列。
- 在學生 accordion 標題列顯示「共 N 筆」以及最早 / 最晚評量日期範圍，幫助老師判斷是否需要搜尋更早日期。
- 分頁「載入更多」按鈕旁加入提示文字，說明目前已顯示至哪個日期（例如「顯示至 2026-02-14，共 N 頁」）。
- 加入「日期範圍」篩選（起訖），取代現有單日篩選，讓老師可一次查詢跨月記錄。

**Out of Scope**

- 家長入口（`ParentPortal.vue`）已有科目分組，本次不動。
- 老師自己的評量填寫流程（SmartCalendar 評量卡片）不在本次改動範圍。
- 後端排序邏輯調整（維持 `SessionDate desc`）。
- 評量內容欄位調整。

## 5. User Stories

**Story 1 — 歷史評量可視性（主任）**

> **As a** 主任, **I want** 評量列表能顯示目前已載入到哪個日期，並在學生群組標頭顯示最早記錄日期, **so that** 我知道是否需要往前搜尋更早的評量，而不會誤以為資料不存在。

Acceptance Criteria：
- [ ] 學生 accordion 標頭顯示「最早評量：YYYY-MM-DD」與「最新評量：YYYY-MM-DD」。
- [ ] 「載入更多」按鈕旁顯示「目前顯示至 YYYY-MM-DD，點擊載入更早記錄」。
- [ ] 日期篩選器改為「起始日期 ～ 結束日期」（range picker），清空時顯示全部（依分頁）。
- [ ] 後端 `GET /api/v1/learning-records` 已支援 `start_date` / `end_date`，本次前端僅補齊 UI 送出 range。

**Story 2 — 科目子分組（主任 & 老師）**

> **As a** 主任, **I want** 在同一學生的評量 accordion 中看到依科目分隔的子群組, **so that** 我能快速聚焦在某科目的學習脈絡，不需要逐筆掃描判斷科目。

Acceptance Criteria：
- [ ] 同學生 accordion 內，評量記錄依 `subject_name`（`student_class_label`）分為子區塊，各有科目標題列。
- [ ] 科目子標題列顯示科目名稱 + 該科目筆數（e.g.「數學 (3)」）。
- [ ] 科目子區塊按科目名稱字母排序（zh-Hant-TW）。
- [ ] 科目名稱為空時，歸入「未分類」子區塊。
- [ ] 篩選器新增「科目」下拉，選項來自當前已載入記錄的去重科目清單。

## 6. 功能需求（FR）

- **FR-001**：系統應在學生 accordion 標頭顯示該學生已載入評量的最早與最新 `SessionDate`。
- **FR-002**：系統應在「載入更多」按鈕旁顯示目前已載入至哪個日期（最舊一筆的 `SessionDate`）。
- **FR-003**：日期篩選 UI 應改為「起始日期 ～ 結束日期」range picker；同時送出 `start_date` 與 `end_date` 參數；清空起訖時不送出日期參數（返回全量分頁）。
- **FR-004**：同學生 accordion 內，評量記錄應依 `student_class_label`（科目）分為子區塊，各子區塊有科目標題行顯示科目名稱與筆數。
- **FR-005**：篩選器應新增「科目」下拉，選項為當前 records 的去重 `student_class_label` 集合；選中後僅顯示該科目的評量行（前端過濾，不觸發 API 重送）。
- **FR-006**：科目欄位為空的評量記錄應歸入「未分類」子區塊，排在最後。
- **FR-007**：空狀態（篩選後 0 筆）應顯示插圖 + 說明文字 + 清除篩選 CTA。

## 7. 非功能需求（NFR）

- 前端計算（科目分組、日期統計）應在 < 50ms 內完成（computed property，避免阻塞渲染）。
- `GET /api/v1/learning-records` API 回應時間 < 800ms（P95，現有 SLA 不降低）。
- 當載入記錄 > 200 筆時，科目分組計算不應造成明顯卡頓；若有性能疑慮，可使用 `requestIdleCallback` defer 非關鍵 computed。
- 錯誤處理：API 失敗時顯示 toast「載入評量記錄失敗，請稍後再試」，保留上一次成功的列表狀態。

## 13. 風險、假設、開放問題

### 風險

**風險 1（中）：兩層分組重構影響範圍廣**
- 描述：`groupedRecordsByStudent` computed 改為「學生 → 科目」兩層分組後，若原有 template 依賴 flat 結構，需同步重構 template 迭代邏輯，存在遺漏場景的風險。
- 緩解：先完整閱讀 template 再動工，不整段覆寫；改後執行回歸測試確認 accordion 展開行為無異常。

**風險 2（低）：科目欄位命名不一致**
- 描述：`student_class_label`、`Subject`、`subject`、`SubjectName` 在不同 record 物件中混用，分組 key 若取錯欄位會導致科目誤歸類。
- 緩解：統一使用 `ParentPortal.vue` 已驗證的 `recordSubjectKey()` fallback 取值鏈，不額外新增取值邏輯。

**風險 3（低）：「載入更多」日期提示與實際分頁語義不一致**
- 描述：目前後端以 `SessionDate desc` 排序，第 1 頁是最新資料；若日期提示顯示「最舊一筆」，使用者可能誤解為「系統只有到這個日期的資料」而非「目前已載入到這個日期」。
- 業界參考：uxpatterns.dev 指出 Load More 模式中，按鈕文字應清楚傳達「使用者主動決定何時載入更多內容」的語意；建議措辭改為「載入更早的記錄（目前最早顯示至 YYYY-MM-DD）」以避免歧義。
- 緩解：UI 文案由 UI/UX Designer 審核後確認，QA 驗收時同步確認措辭不造成誤導。

---

### 假設

**假設 1：後端科目欄位存在於每筆 record 回應**
- 假設 `GET /api/v1/learning-records` 回應中，每筆記錄均帶有 `student_class_label`（或可 fallback 的 `Subject`）；若欄位缺漏則歸入「未分類」，不阻斷渲染。
- 依據：現有 `LearningRecordController` 已 eager-load `studentClass`，科目欄位應已存在。

**假設 2：不需要引入新日曆元件**
- 假設使用原生 `<input type="date">` 或專案現有元件即可實作 date range picker，無需引入新第三方套件。
- 若專案目前無 range picker 元件，[TODO: 需確認] 是否允許引入輕量套件（如 `flatpickr`）。Owner：CTO。

**假設 3：篩選為前端過濾（非後端重新查詢）是可接受的**
- 科目篩選基於已載入的 records 做前端 filter，若跨頁（> 50 筆）資料中某科目只出現在第 2 頁以後，科目下拉不會預先列出；使用者需先「載入更多」才會看到該科目。
- 業界參考：Nielsen Norman Group（NN/G）指出篩選器的選項應「可預期（Predictable）」，即使用者能預判篩選範圍；此假設下應在科目下拉旁加 tooltip「篩選範圍為目前已載入記錄」，避免誤解。
- `[TODO: 需確認]` 若此假設被推翻（業務需要跨全量資料篩選科目），需改為後端新增 `subject` 查詢參數。Owner：PM / CTO。

### 開放問題及業界處理方式

**開放問題 1：只有 1 種科目時，是否省略科目子標題行？**

業界做法：
- **Airtable**：無論群組內有 1 筆或 100 筆，都保持群組標題列可見，並顯示筆數摘要（Count）；理由是「一致性與可預期性」，使用者不需要記住哪個學生有幾種科目才能判斷目前的顯示邏輯。
- **Notion Database View（Group by）**：同樣保持所有 group header 可見，即使 group 只有 1 筆，不自動折疊或隱藏標題。
- **NN/G 建議**：列表分組的標題應「保持一致性」，若在有多科目時顯示、單科目時隱藏，會造成使用者的「鄰接效應混亂（adjacency confusion）」，不知道記錄屬於哪個科目。

**建議決策**：無論科目數量，一律顯示科目子標題行，以維持視覺一致性。標題列輕量設計（淡色背景、小字），不造成視覺負擔。Owner：PM / UI/UX。

**開放問題 2：老師視角（`isTeacher`）是否需要與主任一樣的科目分組？**

業界做法：
- **Canvas LMS（教師視角）**：老師在 Gradebook 看到的是「依作業群組（Assignment Group）」分類的評分列表，而不是純按學生展開；Canvas 的 Enhanced Gradebook Filters 讓老師可同時用日期範圍 + 作業類型 + 模組篩選，但科目（Course）在 Canvas 本身就是一個獨立頁面入口，因此在單一科目頁內不需再分組。
- **本系統情境**：老師的評量頁（`isTeacher`）主要顯示「自己負責課程的所有學生評量」，科目是由老師的授課科目決定；若老師只教一科，科目分組無意義；若老師教多科，分組有助於按科目批次填寫評量。

**建議決策**：老師視角套用相同科目分組邏輯，但若老師授課科目 ≤ 1 種，科目標題行依「開放問題 1」的決策一律顯示。`[TODO: 需確認]` Owner：PM。
