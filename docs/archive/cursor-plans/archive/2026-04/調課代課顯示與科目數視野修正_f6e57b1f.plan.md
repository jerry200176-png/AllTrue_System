## 2. 目標與業務背景

### 痛點

**Bug A — 調課代課後課表不更新**
黃芝琳老師的學生吳宏逸課程從 10:00–12:00 調課至 17:00–19:00 並指定李維老師代課，課程管理頁顯示「調課成功」，但：
- `TeacherHomePage` 週課表仍顯示原時段 10:00–12:00
- `SmartCalendar` 課表格的點名連結無法觸發（找不到對應 session 列）
- 代課老師（李維）在自己的課表看不到此堂

根本原因（技術層）：
1. 課程管理前端在呼叫 `reschedule-session` API 時**靜默吞錯**（`.catch(() => {})`），UI 回報成功但 `ClassSession.StartTime/EndTime` 可能未更新
2. 呼叫 `reschedule-session` 時未傳 `old_start_time`，若同日有多筆 session，API 以 `first()` 任取第一筆，可能更新到錯誤的 ClassSession
3. `ClassSession` 時間更新後，`schedules` 代課 row 的 `start_time` 仍保留舊值，導致 `ClassSessionController::index` 的 JOIN 失效，代課老師消失
4. `SmartCalendar::findSessionRowForCell` 以 **課程契約 start_time**（舊值）比對 session row，調課後找不到 row → 點名 badge 無法掛載
5. `TeacherHomePage` 的週課表只讀 `GET /api/v1/class-sessions`，無合併 `schedules` exceptions，時間不更新

**Bug B — 老師可看到所有人的科目數**
老師登入後進入「科目數統計」(`SubjectUnitsPage.vue`)，可看到：
- 全班老師的科目數數字（`subject_count_with/without`）、小時數、`share_pct` 佔比
- 分校加總 `totals`（含公司整體數字）

科目數數字屬公司內部競爭力資料，不應讓老師之間相互比較絕對值，只應讓老師知道自己的數字和自己的名次。

### 業務價值
- Bug A：老師與代課老師能即時看到正確時段並完成點名，避免課堂記錄遺失
- Bug B：保護公司內部科目數情報，同時保留排名激勵機制

### KPI
- 調課後 `ClassSession.StartTime/EndTime` 與 `schedules` 代課 row 時間 100% 一致
- 調課後老師課表與智慧排課顯示新時段，點名成功率 = 100%
- 老師登入後「科目數統計」頁看不到他人數字（覆蓋率 0%），自己數字可見，名次可見

## 3. 範圍

### In Scope
- 修正 `reschedule-session` API 以 `date + start_time` 雙鍵定位正確 `ClassSession`
- 修正前端呼叫 `reschedule-session` 時傳入 `old_start_time`，並對失敗顯示明確錯誤
- `ClassSession` 時間更新時同步更新相關 `schedules` 代課 row 的 `start_time/end_time`
- 修正 `SmartCalendar::findSessionRowForCell` 支援調課後以 **例外新時段** 找 session row
- 修正 `TeacherHomePage` 週課表合併 `schedules` exceptions，顯示調課後正確時段
- `GET /api/v1/finance/subject-units`：當 caller 為 `teacher` 角色時，回傳資料中其他老師的數字欄位（hours、subject_count、share_pct）做遮蔽，僅返回排名位置；自己的數字完整返回；分校 `totals` 不返回
- `SubjectUnitsPage.vue`：teacher 角色下只顯示全體排名（名字 + 名次）、自己的詳細數字，隱藏他人數字與分校合計

### Out of Scope
- 調課後 `PackageSessionLedger` 的重算（另票）
- 多堂調課批次操作
- 代課流程的「通知代課老師」LINE 推播改動
- 主任端科目數統計視野不變（主任仍看到全部）
- 科目數統計的排名演算法改動（維持現行以 `total_hours` 降冪排序）

## 5. User Stories

### US-01：調課後課表即時更新
> **As a** 老師，**I want** 調課完成後在智慧排課與教學工作台週課表看到新時段，**so that** 我能在正確時間進行點名，不會搞錯課堂時間。

Acceptance Criteria：
- [ ] 調課成功後，`SmartCalendar` 週課表該格顯示 17:00–19:00（而非 10:00–12:00）
- [ ] 該格的點名按鈕可正常點擊並觸發點名流程
- [ ] `TeacherHomePage` 週課表同步顯示新時段

### US-02：代課老師看得到並能點名
> **As a** 代課老師（李維），**I want** 在自己的課表看到指定代課的堂次（包含調課後的新時段），**so that** 我知道何時去上課並能完成點名。

Acceptance Criteria：
- [ ] 代課老師的智慧排課在新時段（17:00–19:00）顯示代課堂次
- [ ] 代課老師可在該堂次觸發點名
- [ ] 原班導師（黃芝琳）的課表同一日期不顯示重複的原時段

### US-03：調課失敗時使用者收到明確錯誤
> **As a** 主任，**I want** 調課 API 失敗時看到明確的錯誤提示，**so that** 我知道要重試而不是誤以為調課已成功。

Acceptance Criteria：
- [ ] `reschedule-session` API 失敗時，課程管理頁顯示紅色錯誤 toast（非靜默失敗）
- [ ] 錯誤訊息說明失敗原因（找不到該堂次 / 時間衝突等）

### US-04：老師只看到自己的科目數數字與全體排名
> **As a** 老師，**I want** 在科目數統計頁看到自己的科目數、小時數和所有老師的名次排序，**so that** 我能了解自己的相對位置，但不洩漏同事的具體數字。

Acceptance Criteria：
- [ ] 老師自己的行顯示完整數字（科目數、小時數）
- [ ] 其他老師的行只顯示名次、姓名，數字欄位為「—」或空白
- [ ] 分校加總區塊（totals）對老師隱藏
- [ ] 主任登入後仍看到完整資訊

## 6. 功能需求（FR）

### FR-001：reschedule-session 以 date + start_time 雙鍵定位 ClassSession
系統的 `POST /api/v1/learning-records/reschedule-session` API 在接收 `student_class_id`、`old_date`、`old_start_time` 時，應以這三個欄位精確定位目標 `ClassSession` 行，而非僅以日期取 `first()`。若找不到對應行，應回傳 422 並附說明。

### FR-002：前端調課呼叫傳入 old_start_time
系統的課程管理前端（課程編輯彈窗）在呼叫 `reschedule-session` API 時，應將原時段的 `start_time` 作為 `old_start_time` 一併傳入，確保 API 定位到正確的 ClassSession。

### FR-003：reschedule-session 失敗顯示明確錯誤
系統的課程管理前端不得靜默吞掉 `reschedule-session` 的失敗回應；API 回傳非 2xx 時，必須顯示紅色錯誤 toast（內含後端 `message` 欄位），讓主任知悉調課未完成。

### FR-004：ClassSession 時間更新後同步更新 schedules 代課 row
系統應在 `ClassSession.StartTime/EndTime` 因調課而更新時，同步將該 `ClassSession` 對應的所有 `schedules` 代課行（`status = 'scheduled'`、`original_schedule_id IS NOT NULL`）的 `start_time/end_time` 更新為新值，維持 JOIN 條件的一致性。

### FR-005：SmartCalendar 以例外新時段匹配 session row
系統的 `SmartCalendar.vue` 在該日期存在 `rescheduled-to` 例外時，應以**例外的新 `start_time`**（而非課程契約 start_time）去匹配 `sessionDatesByCourseId` 中的 session row，確保點名 badge 能正確掛載到調課後的格子。

### FR-006：TeacherHomePage 週課表合併調課例外時段
系統的 `TeacherHomePage.vue` 週課表在顯示各課程時段時，應優先使用當日對應 `ClassSession.StartTime/EndTime`（已由後端更新），使調課後的新時段能在教學工作台週課表反映。

### FR-007：代課老師的課表顯示代課堂次
系統的 SmartCalendar 週視圖應確保：代課指定後，代課老師（`schedules.teacher_id = substitute`）可在自己的課表看到新時段的代課格子，且可觸發點名。

### FR-008：subject-units API 對 teacher 角色遮蔽他人數字
系統的 `GET /api/v1/finance/subject-units` 在請求者角色為 `teacher` 時，回傳的 `teachers` 陣列中，非本人的每筆 entry 應遮蔽以下欄位（設為 null 或移除）：`one_on_one_hours`、`one_on_two_hours`、`one_on_three_hours`、`tutoring_hours`、`total_hours`、`subject_count_with`、`subject_count_without`、`share_pct`；同時不返回 `totals` 與 `level_breakdown_totals`。本人 entry 的所有欄位保持完整。另應在每筆 entry 加入 `rank` 欄位（1-based 整數），並在回應根層加入 `total_teachers` 計數。

### FR-009：SubjectUnitsPage.vue teacher 視野
系統的 `SubjectUnitsPage.vue` 在 `userRole === 'teacher'` 時，應：
- 隱藏分校 totals 摘要卡片區塊
- 表格所有非自身行的數字欄顯示「—」
- 自身行以高亮底色 + 「(你)」標籤標示
- 表格仍顯示全體老師的名次序號與姓名（排名可見）

## 7. 非功能需求（NFR）

- **效能**：FR-004 的 `schedules` 同步更新應在 `reschedule-session` 同一資料庫事務中完成，不增加額外 API round-trip；總 API 回應時間 < 500ms
- **一致性**：`ClassSession.StartTime` 與對應 `schedules` 代課 row 的 `start_time` 必須同值，由 API 層保證，前端不做獨立修補
- **降級**：若 `schedules` 代課 row 同步更新失敗，應 transaction rollback 整個調課操作並回傳 500，不允許部分成功（避免資料不一致）
- **資料遮蔽**：FR-008 的遮蔽邏輯必須在 **後端** 執行，前端不得僅依靠 CSS/v-if 隱藏（防 DevTools 存取 API JSON）
- **回歸防護**：本次修改 `reschedule-session`、`ClassSessionController::index`（JOIN 邏輯）、`SubjectUnitsPage` 等高風險模組，必須有對應 Feature Test 守護

### 架構選擇理由

**FR-001/002/003（reschedule 精確定位）**：現行後端以「`student_class_id` + `old_date` 取第一筆」存在歧義；加入 `old_start_time` 作為第三鍵可在不增加欄位或 migration 的前提下解決。前端已在課程編輯流程中持有原時段資訊，傳入代價極小。

**FR-004（schedules 同步）**：`ClassSession` 與 `schedules` 之間的 JOIN 條件以 `start_time` 為 key，更新 `ClassSession` 時必須在同一 transaction 中同步更新 `schedules`。選擇 transaction 而非事後 reconciliation，因為事後修補會產生短暫的資料不一致視窗，對點名功能影響更大。

**FR-005/006（時段匹配）**：`findSessionRowForCell` 目前只用 `course.start_time`（契約值）匹配 session row；調課後 `ClassSession.StartTime` 已是新值，只要 FR-004 完成，直接比對 `ClassSession.StartTime` 即可正確找到。`TeacherHomePage` 的週課表已是直讀 `ClassSession`，FR-004 完成後自動正確，可能無需額外改動。

**FR-008（API 遮蔽）**：選擇在後端 `subjectUnits` controller 中以 `$authUser->type` 判斷角色並遮蔽欄位，而非新增獨立的 teacher 專屬 endpoint，理由是共用同一 query 邏輯較易維護；遮蔽在 response 組裝階段執行（map 階段設為 null），不影響排序和 rank 計算。`rank` 欄位的計算在遮蔽前以 `total_hours` 排序完成，確保排名準確。

### Migration 需求
本次無新增 migration。`schedules` 與 `ClassSession` 既有欄位已涵蓋所有所需資料。

## 9. 資安與存取控制

- **調課 API（FR-001）**：`role:director,teacher` + `require_campus`，與現行一致；`old_start_time` 為可選字串欄位，無 SQL injection 風險（使用 ORM query builder）
- **subject-units 遮蔽（FR-008）**：`role:director,teacher` + `require_campus`，與現行一致；遮蔽邏輯在後端 controller 層執行，前端無法繞過；`rank` 與 `total_teachers` 屬競爭力指標但非財務敏感資料，列入 PII 低風險
- **schedules 同步（FR-004）**：僅更新與本次 `ClassSession` 直接關聯的 `schedules` row（以 `student_course_id = StudentClassID AND DATE(schedule_date) = new_date`），無跨課程更新風險
- **STRIDE 快評**：
  - Tampering：FR-001 的 `old_start_time` 若傳入偽造值，最壞情況是找不到 session（回 422），不會更新到其他課程的 ClassSession
  - Information Disclosure：FR-008 主要風險點；在後端遮蔽後，其他老師的絕對數字不出現在 JSON 回應，降低為低風險
  - 其餘 STRIDE 項目：N/A

## 13. 風險、假設、開放問題

### 風險

| 等級 | 描述 | 緩解方案 |
|---|---|---|
| 高 | FR-004 的 schedules 同步邏輯可能影響現有「非代課」的 reschedule 流程（同一 transaction 新增副作用）| Code Review 時確認 schedules 同步只在 `original_schedule_id IS NOT NULL`（代課行）觸發，不碰一般 `rescheduled` row；regression test 覆蓋 |
| 高 | `findSessionRowForCell` 修改後可能影響 SmartCalendar 的其他 badge 掛載邏輯（同一函式用於多種 badge）| 修改範圍嚴格限制：only when exception `rescheduled-to` 存在於當格時才走新路徑，其餘維持原邏輯；`PayrollConcurrencyTest` 等不依賴此路徑的測試同步確認 |
| 中 | `reschedule-session` 加 `old_start_time` 為新參數，若現有其他呼叫方未傳此參數，可能命中 `first()` fallback | Fallback 以「不傳 `old_start_time` 時維持現行 `first()` 行為」保持向後相容；同時記 `warning` log 提醒調用方升級 |
| 低 | subject-units 遮蔽後若後端有快取（目前未見 Redis 快取此端點），不同角色可能取到同一份快取 | 確認該端點無快取層；若有，Cache Key 需含 `user_id` 或 `role` |

### 假設
- `schedules` 代課行的 `start_time` 欄位格式為 `HH:MM`（不含秒），與 `ClassSession.StartTime` 前五碼（`SUBSTRING(StartTime, 1, 5)`）格式一致
- 課程管理前端的 `useRescheduleAndMakeup.js` 中，調課表單資料已包含 `original_start_time`（或可從 `form.session_start_time` 取得）；若無，需確認取值路徑 `[TODO: 需確認]`
- `subjectUnits` controller 可從 `$request->user()` 取得 `type`（`'T'` = teacher, `'D'` = director）進行角色判斷

- **解法**：`[FEATURE]` agent 在實作 FR-004 後，先以 smoke test 確認 `TeacherHomePage` 是否自動更新，若是則 FR-006 工期可縮短至 0
