## 2. 目標與業務背景

**痛點 A：「載入全部記錄」只顯示 200 筆**

後端每頁上限為 200 筆（`PERF_LR_MAX_PER_PAGE=200`）。`loadAllRecords` 迴圈設計上應自動翻頁，但當兩次 API 呼叫之間有新的 LearningRecord 插入，MySQL OFFSET 分頁會位移（sliding window 問題）：第 2 頁回傳的 ID 與第 1 頁部分重疊，前端 dedup 過濾後 `added=0 && returned>0` 觸發防護中斷，迴圈提前結束，使用者看到的永遠是第 1 頁的 200 筆。

**痛點 B：頁面長期資料累積塞爆**

一個學生購買 8 堂後結算、再購 8 堂、再購 8 堂……每位學生的 LearningRecord 會無限累積。目前後端無預設時間限制，每次進入頁面就撈出所有歷史記錄，隨著補習班開業時間拉長，老師和主任的頁面初始載入量將呈線性增長，最終造成明顯延遲甚至瀏覽器卡頓。

**業務價值**

- 修復後使用者可可靠地取得完整記錄，不再以為資料遺失。
- 預設時間窗口讓頁面初始載入量維持在可控範圍（≤ 200 筆），與補習班開業時間無關，可長期穩定運行。
- 老師不再需要等待全部歷史記錄載入，只看近期即可滿足日常作業需求。

**成功指標（KPI）**

- 「載入全部記錄」按鈕點擊後，最終顯示筆數 = 後端回報之 `total`，一致率 100%。
- 初始頁面載入後，API 回應時間 P95 < 800ms（與目前相比不退化，有望改善）。
- 「頁面被塞爆 / 很慢」相關回報 = 0 件 / 月（目前已開始出現）。

## 3. 範圍

**In Scope**

- 修正 `loadAllRecords` 的 sliding window 中斷 bug：改用「最小已知 ID 錨點（keyset anchor）」取代 OFFSET 分頁。
- 後端 `GET /api/v1/learning-records` 新增 `before_id` keyset 參數，作為分頁錨點。
- 前端頁面新增「預設時間窗口」邏輯：初始載入僅抓取最近 90 天（可由 `.env` 調整），超出時間窗口時顯示提示 badge 及「查看全部歷史」入口。
- 後端 `.env` 新增 `PERF_LR_DEFAULT_WINDOW_DAYS` 旗標控制預設窗口天數（預設 90）。
- `LearningRecordsPage.vue` 老師視角與主任視角共用此預設窗口。

**Out of Scope**

- 家長入口（`ParentPortal.vue`）不受影響（已有科目分組，無分頁問題）。
- 評量內容欄位或填寫流程不改動。
- 後端全面改為 cursor-based pagination（影響範圍過大，本次只針對 LearningRecords 的 `loadAllRecords` 流程加 `before_id` 支援）。
- 評量記錄歸檔 / 軟刪除機制（不在本次範圍）。

## 5. User Stories

**Story 1 — 載入全部記錄可靠完成（主任）**

> **As a** 主任，**I want** 點擊「載入全部記錄」後能確實載入所有符合條件的評量，**so that** 我審核時不會漏掉任何待審記錄。

Acceptance Criteria：
- [ ] 點擊「載入全部記錄」後，最終顯示筆數等於按鈕旁標示的 `total` 數字，誤差為 0。
- [ ] 過程中若有新記錄在兩次 API 呼叫之間寫入，不影響最終完整性（已有記錄不重複、不遺漏）。
- [ ] 載入過程中按鈕顯示進度（已載入 X / 總 Y 筆），完成後按鈕消失。

**Story 2 — 頁面初始載入不因歷史資料累積變慢（老師 & 主任）**

> **As a** 老師，**I want** 進入評量頁時預設只看最近 90 天的記錄，**so that** 頁面能快速顯示，我不需要等待數年的歷史資料全部載入。

Acceptance Criteria：
- [ ] 初始載入無日期篩選時，系統自動套用「近 90 天」窗口，並在篩選區顯示「目前顯示近 90 天」提示 badge。
- [ ] Badge 旁提供「查看全部歷史」連結，點擊後清除日期限制重新載入。
- [ ] 手動設定日期篩選時，預設窗口自動失效，以使用者設定的日期範圍為準。
- [ ] 若近 90 天無記錄，空狀態說明「近 90 天無評量記錄」並提供「查看更早記錄」CTA。

**Story 3 — 個別學生完整歷史快速查看（老師 & 主任）**

> **As a** 主任，**I want** 點擊學生姓名後能取得該學生的完整評量歷史（不受時間窗口限制），**so that** 我能在需要時一次看清某學生所有課程記錄。

Acceptance Criteria：
- [ ] 點擊學生姓名後，系統以 `student_name` 篩選重新查詢，並自動移除時間窗口限制。
- [ ] 查詢結果若超過 200 筆，「載入全部記錄」按鈕正常運作直到完整載入。
- [ ] 篩選條件 badge 顯示「學生：XXX（全部歷史）」，使用者知道目前已解除時間窗口。

## 6. 功能需求（FR）

- **FR-001**：系統應在初始載入（無使用者設定的日期篩選）時，自動在 API 請求中帶入 `start_date = 今天 − WINDOW_DAYS`（`WINDOW_DAYS` 預設 90，可由後端 `.env` `PERF_LR_DEFAULT_WINDOW_DAYS` 覆蓋）。
- **FR-002**：系統應在記錄清單上方顯示時間窗口 badge，說明「目前顯示近 N 天」並提供「查看全部歷史」text-link，點擊後清除 `start_date` 限制並重新查詢。
- **FR-003**：後端 `GET /api/v1/learning-records` 應接受 `before_id` 參數（整數），當此參數存在時，查詢結果限定為 `id < before_id`（keyset anchor），取代 OFFSET；`page` 參數在 `before_id` 存在時忽略。
- **FR-004**：前端 `loadAllRecords` 應改用 keyset 翻頁：第 1 頁正常發送，後續頁以上一頁回傳結果中最小的 `id` 作為 `before_id` 送出，直至回傳 `data` 為空陣列為止。
- **FR-005**：點擊學生姓名（`filterByStudent`）時，系統應同時清除 `start_date` 時間窗口限制，以 `student_name` 篩選查詢該學生的完整歷史。
- **FR-006**：後端 `PERF_LR_DEFAULT_WINDOW_DAYS` 旗標應加入 `config/perfflags.php`，並透過 `/api/v1/health`（或現有 perf-flags 端點）回傳至前端，使前端的時間窗口計算與後端一致。
- **FR-007**：若近 90 天（或使用者設定的 `start_date` 窗口）內無符合記錄，空狀態說明應反映時間窗口並提供「查看更早記錄」CTA，而非顯示通用「無資料」文字。

## 7. 非功能需求（NFR）

- 初始載入（90 天窗口）API 回應時間 P95 < 600ms（較目前全量查詢有改善）。
- `loadAllRecords` keyset 翻頁，每頁間隔 ≤ 100ms 延遲（純網路等待，無人工節流）。
- `before_id` 查詢需使用 `LearningRecord.id` 索引，不得導致全表掃描（確認 `id` 為主鍵 / 索引，後端無需新增 migration）。
- 前端時間窗口計算（`today − WINDOW_DAYS`）依客戶端本地時間計算，不依賴伺服器時間（避免 timezone 邊界問題）。
- 降級策略：若後端不支援 `before_id`（舊版回應忽略該參數並按 OFFSET），前端應能 fallback 回現有 OFFSET 翻頁行為，不得因此白屏或 JS 例外。

**架構選擇理由**

- **Keyset（`before_id`）取代 OFFSET**：OFFSET 分頁在寫入頻繁的表上天生有 sliding window 問題（Facebook、Slack、Instagram 均已完全廢棄 OFFSET 分頁）。`before_id` 使用主鍵範圍查詢，性能也優於 OFFSET（不需要掃過前 N 行）。本次只為 `loadAllRecords` 路徑加 keyset 支援，OFFSET 路徑（`page=N`，用於一般「載入下一頁」）保留向後相容。
- **90 天預設窗口**：業界標準（Gmail 預設 3 個月、Salesforce 預設本財年、Canvas LMS 預設本學期）。補習班日常操作以近期課程為主，歷史查詢為例外，此設計符合 80/20 使用情境。
- **前端計算窗口**：`today − WINDOW_DAYS` 由前端 computed，不依賴後端 API 額外 round-trip；後端旗標透過 perf-flags 端點在頁面初始化時一次性取得。

## 9. 資安與存取控制

- `GET /api/v1/learning-records` 已受 `auth:sanctum` + role 中介層保護，`before_id` 為純查詢參數，不繞過現有 `StudentClass` / `campus` 過濾，無新增存取面。
- `PERF_LR_DEFAULT_WINDOW_DAYS` 為效能設定旗標，不涉及 PII；通過 health / perf-flags 端點回傳屬公開配置值，可接受。
- `before_id` 注入：前端傳入任意整數 ID，後端僅追加 `id < before_id` 條件，已有的 campus / role 過濾仍有效，不存在 IDOR 風險。
- 需要稽核 log 的操作：無（本次為讀取改動）。
- STRIDE 快評：無新增 Spoofing / Tampering / Information Disclosure 風險；`before_id` 不洩露不可見記錄（現有 WHERE 條件仍套用）。

## 10. QA 驗收標準與測試計畫

### FR-001 & FR-002（預設時間窗口）

- Happy Path：開啟頁面，無手動日期設定 → API 請求帶 `start_date=today-90`，篩選區顯示「目前顯示近 90 天」badge，點「查看全部歷史」後 badge 消失、API 重新查詢無 `start_date`。
- Edge：當天是年初 1 月 5 日，today-90 = 上一年 10 月 → `start_date` 應跨年正確計算。
- Edge：近 90 天真的無記錄 → 空狀態顯示「近 90 天無評量記錄」+ 「查看更早記錄」CTA，而非通用空狀態。
- Edge：使用者手動設定 `start_date` 為 2 年前 → 時間窗口 badge 隱藏（使用者已自訂，不再顯示預設窗口提示）。

### FR-003 & FR-004（Keyset 翻頁）

- Happy Path：總計 329 筆（2 頁 × 200），點「載入全部記錄」→ 最終顯示 329 筆，`before_id` = 第 1 頁最小 id，第 2 頁請求以此為錨，無重複、無遺漏。
- Edge：兩次 API 呼叫之間有新記錄插入 → 新記錄 `id` 大於第 1 頁最大 `id`，不影響 `before_id` 以下的頁面，第 2 頁結果正確。
- Edge：總計恰好 200 筆（剛好 1 頁）→ 第 1 頁回傳 `data` 空陣列，`loadAllRecords` 停止，不再發第 2 次請求。
- Edge：共 1001 筆（6 頁）→ 迴圈正確翻完 6 頁，最終顯示 1001 筆，`guard < MAX_PAGES = 50` 不觸發。
- Error：第 3 頁 API 失敗（HTTP 500）→ 顯示 alert「載入全部失敗（HTTP 500，已載入 X 筆）」，不崩潰，已載入的記錄保留。

## 13. 風險、假設、開放問題

> 本節所有項目均已採用業界做法作出明確決策，無任何 `[TODO: 需確認]` 懸而未決項目，確保 AI Agent 可獨力實作。

### 風險

**風險 1（中）：keyset 與現有 OFFSET 路徑共存的相容性**

- 描述：後端同一端點需同時支援 `page=N`（OFFSET）與 `before_id`（keyset），兩者在大量並發下若邏輯混用可能出現邊界錯誤。
- 業界做法：**Slack**（Engineering Blog: "Evolving API Pagination at Slack"）在同一端點同時保留 `page` 與 `cursor` 支援期間，採用「cursor 存在時完全忽略 page」的明確分支原則，兩個路徑的 WHERE 邏輯完全獨立，無共享狀態。Slack 建議客戶端以 `next_cursor` 是否為空判斷終止，而非比較結果數量與 limit。
- **確定決策**：後端以 `if ($request->filled('before_id'))` 為分支入口，`before_id` 路徑完全不計算 `page`、不使用 `skip()`；OFFSET 路徑完全不讀取 `before_id`。前端 `loadAllRecords` 以 API 回傳 `data` 為空陣列作為終止條件（對應 Slack 的 `next_cursor` 判斷），不以 `currentPage >= lastPage` 判斷。加 Pest Feature Test 覆蓋兩個路徑互不干擾。

**風險 2（低）：90 天窗口隱藏待審記錄造成資訊盲點**

- 描述：主任在「待審佇列」tab 下，若有 90 天前的異常待審記錄（例如資料遷移後未審核），預設窗口會將其隱藏，主任不知道有遺漏。
- 業界做法：**Jira Kanban Board** 對「Hide completed issues older than N weeks」功能有明確的例外處理原則：未完成（Open/In Progress）的 issue 永遠不受時間窗口隱藏，時間窗口僅適用於已完成（Done/Resolved）狀態。**Jira Service Management** 進一步在篩選器隱藏待處理 ticket 時，顯示「N issues hidden by current filter, including Y open items」的頂部 banner。
- **確定決策**：時間窗口（90 天 `start_date`）僅在 `reviewTab !== 'pending' && reviewTab !== 'changes_requested'` 時自動注入。當主任位於「待審佇列」或「需修改追蹤」tab 時，AI 自動關閉時間窗口限制，確保所有待審記錄無論多早都能顯示。老師視角（`teacherFilterTab`）同理：`pending` tab 不套用窗口。此規則由 AI 直接寫入 `_buildRecordsParams` 邏輯，不需人工確認。

**風險 3（低）：perf-flags 端點暴露系統設定**

- 描述：`LR_DEFAULT_WINDOW_DAYS` 等旗標經 API 回傳，屬低敏感度配置值。
- 業界做法：**GitHub API** 的 `rate_limit` 端點、**Stripe API** 的 `livemode` 旗標均以 authenticated response 回傳運行時設定，均要求有效 Bearer token 才能存取，屬業界通行做法。
- **確定決策**：perf-flags 端點已受 `auth:sanctum` 保護（AI 部署前確認），`LR_DEFAULT_WINDOW_DAYS` 隨現有 perf-flags 一同回傳，不另開公開端點。

---

### 假設

**假設 1：LearningRecord.id 為自增主鍵，keyset 語義正確**

- 業界驗證：根據 **MySQL 8.4 官方文件**（InnoDB AUTO_INCREMENT Handling），InnoDB 的自增主鍵在單列 INSERT / 普通 `INSERT INTO...VALUES` 操作中保證嚴格遞增；批次 INSERT（`LOAD DATA`、`INSERT INTO...SELECT`）可能產生 ID 間隙（gap），但不會亂序——較晚的批次永遠拿到比較早批次更大的 ID 區段。本系統的 LearningRecord 由 `LearningRecord::create()` 單列插入，不存在批次亂序問題。
- **確定決策**：`id` 保證單調遞增（可有 gap，不會亂序），`before_id`（`WHERE id < before_id`）的語義完全正確。AI 直接採用，無需人工確認。

**假設 2：90 天為合適的預設窗口，且「待審」tab 不受限制**

- 業界驗證：**Jira Kanban Board** 預設隱藏「完成狀態超過 2 週」的 issue（未完成 issue 不隱藏）。**Salesforce Activity Timeline** 預設顯示「Last 30 days」，並提供 "All Time" 逃脫選項。**Zendesk** 預設 ticket view 以「近 30 天活躍」為範圍。三家主流 SaaS 的預設窗口均在 30–90 天之間；本系統補習班課程週期約 1–3 個月，90 天覆蓋約 1 個學習周期，合理。
- **確定決策**：預設 90 天，且「待審」/「需修改」tab 強制解除窗口（見風險 2 決策）。若未來需調整天數，直接改 `.env PERF_LR_DEFAULT_WINDOW_DAYS=N`，不改程式碼。AI 部署時寫入 `.env.example`，運營調整由 IT Ops 改 `.env`。

**假設 3：前端時間窗口計算以客戶端本地時間為基準（台灣 UTC+8）**

- 業界驗證：**Linear** 的 "Due this week" 篩選以客戶端本地時間計算週期邊界；**Notion** 的 "Filter by date" 亦以瀏覽器時區為準。兩者均以「使用者感知時間」而非 UTC 為基準，減少跨時區混淆。本系統補習班及學生均在台灣（UTC+8），無多時區問題。
- **確定決策**：前端以 `new Date()` 取客戶端本地今日日期，減去 `WINDOW_DAYS` 天數，格式化為 `YYYY-MM-DD` 送出 `start_date`。不依賴後端時間，不引入額外 round-trip。此計算由 AI 直接實作。

---

### 開放問題

**開放問題 1：待審記錄超過 90 天窗口的通知機制**

- 業界做法：**Jira Service Management** 對「被過濾器隱藏的待處理 ticket」顯示頂部 banner，說明「N issues hidden including Y open」；**GitHub Issues** 的 Filter 在有 label/status 過濾時頂部顯示「Showing X of Y」；兩者均給予「Clear filter」一鍵逃脫。本計畫的 `lr-tab-filter-banner` 已實作「另有 N 筆其他狀態被隱藏」banner，語義一致。
- **確定決策**：待審 tab 不套用時間窗口（已於風險 2 解決），因此「90 天前有待審記錄被隱藏」這個場景根本不會發生，此開放問題已透過風險 2 的決策消除。AI 直接實作風險 2 邏輯，不需額外通知機制。

**開放問題 2：是否需要為每個學生的「完整歷史」提供獨立頁面或側欄**

- 業界做法：**Salesforce** 每個 Contact 有獨立 Activity History tab，不受全局篩選影響；**Notion** 每個 Page 有獨立 Timeline；**HubSpot** CRM 的 Contact 詳情頁有完整活動時間軸。但三者的前提是「聯絡人詳情頁」本身就是系統主要操作單元，業務流程以「聯絡人為中心」。本系統主要操作單元是「評量表（LearningRecord）」而非「學生（Student）」，主任的日常工作流是「審核 pending 狀態的評量表」而非「查看某學生的歷史」。
- **確定決策**：本次以「點學生姓名 → `student_name` 篩選 + 解除時間窗口（FR-005）」作為輕量替代，符合補習班實際操作情境。獨立學生詳情頁列為後續 backlog（不阻擋本次上線），AI 本次不實作。
