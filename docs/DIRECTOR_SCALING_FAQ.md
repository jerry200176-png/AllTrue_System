# 大分校資料處理 — 主任 FAQ

## 系統可以處理多少學生與課程？

單一分校 **數百位學生、上千筆課程** 是系統設計的正常範圍。資料庫（MySQL）存放這些資料量沒有問題；效能取決於「一次載入多少」以及硬體規格。

## 智慧排課是否能看到分校全部課程？

**可以。**  
智慧排課（日檢視／週檢視／切換老師）會載入該分校的 **完整課程清單**。系統會以多筆小請求並行載入、合併後呈現，進頁時會顯示「載入中」進度提示，載完後即可正常操作日曆與切換老師。

## 課程管理（列表頁）為什麼要翻頁？

課程管理頁採用 **分頁** 設計（每頁 50 筆），搭配 **姓名、老師、班型、狀態** 等篩選條件。這是為了確保在大分校時 **畫面不卡頓、載入速度快**。

- 頁面頂部會顯示 **總筆數**（例如「共 320 筆課程（第 1 頁）」），不會漏資料。
- 若要找特定學生的課程，在「學生」欄位輸入姓名即可快速定位。

## 同時多少人可以上線？

系統目前部署在 **Raspberry Pi 單機**，同時上線人數取決於：

- **使用模式**：教職員日常查詢、偶爾操作——通常沒問題。
- **極端併發**：若非常多人 **同一秒** 密集操作（例如月底集體查帳單），可能會變慢。

**建議**：上線後觀測 CPU 與回應速度；若有明顯卡頓再評估升級硬體或分離資料庫。

## 資料正確性如何保證？

- 所有列表頁面都帶有 **分校篩選**（`branch_id`），不會跨校看到其他分校的資料。
- 繳費提醒、堂數統計在後端 SQL 層即做篩選，確保規則一致。
- 課程堂次查詢使用 **分段請求**，避免超大請求失敗。

## 歷史資料會不會越來越慢？

- 請假/調課記錄只載入 **近幾個月的範圍**，不會把多年歷史一次下載。
- 後端已設定安全上限，避免單次無限制查詢。
- 若未來資料量極大，可評估歸檔舊資料或增加索引。
