# Building a Scratch Card in Jetpack Compose

An article about scratch-to-reveal mechanic, solution and how to use it

Press enter or click to view image in full size

Scratch cards look simple, but implementing one cleanly in Compose is trickier than it appears. The naive approach buries gesture handling, path drawing, and coverage math inside a single @Composable, turning your UI function into one hard-to-test knot.

This article walks through the approach used in the ScratchMechanic sample: a ScratchState class owns the scratch/reveal logic, while ScratchOverlay handles layout, gestures, offscreen drawing with BlendMode.Clear, and the vanish animation. The composable stays mostly wiring; the rules live in plain Kotlin.

### The core idea: separate what you draw from what you know

A scratch card has two concerns:

1. Rendering — show a top layer the user can “erase” along their drag so content behind shows through.

2. Logic — track how much area counts as scratched and decide when to reveal (and optionally fade the top layer out).

These are not the same concern. Mixing them makes it awkward to test reveal rules and easy to break coverage when you tweak the brush.

ScratchState holds:

- The list of drawn points (for path reconstruction via buildScratchPath).

- A grid-based coverage model (distinct bucket ids in a HashSet).

- Reveal thresholds and flags such as hasUserStartedScratching and isRevealThresholdReached.

The UI (ScratchOverlay) calls updateLayerSize, updateParams, the drag handlers, and buildScratchPath inside a drawWithContent block — not a raw Canvas — then draws a transparent stroke with BlendMode.Clear on an offscreen graphicsLayer.

Scratch state:

radius) / coverageCellSizePx).toInt().coerceAtLeast(0)        val maxCol = floor((x + radius) / coverageCellSizePx).toInt().coerceAtMost(coverageColumns - 1)        val minRow = floor((y - radius) / coverageCellSizePx).toInt().coerceAtLeast(0)        val maxRow = floor((y + radius) / coverageCellSizePx).toInt().coerceAtMost(coverageRows - 1)        val region = clipRegion        for (row in minRow..maxRow) {            val cy = (row + 0.5f) * coverageCellSizePx            val dySq = (cy - y).let { it * it }            for (col in minCol..maxCol) {                val cx = (col + 0.5f) * coverageCellSizePx                val distSq = (cx - x).let { it * it } + dySq                if (distSq <= radiusSq) {                    if (region == null || region.contains(cx.toInt(), cy.toInt())) {                        scratchedBuckets.add(row * coverageColumns + col)                    }                }            }        }    }    private fun updateRevealState() {        if (!isRevealThresholdReached &&            scratchedBuckets.size >= revealBucketTarget        ) {            isRevealThresholdReached = true        }    }}

### Coverage tracking without pixel counting

The obvious approach to “how much did the user scratch?” is pixel counting — inspecting alpha after each stroke. That often implies readback and tight coupling to rendering.

ScratchState uses a coverage grid instead.

The scratch surface is divided into cells. Cell size is derived from the brush width (clamped to min/max pixel bounds):

```
coverageCellSizePx = (brushWidthPx * COVERAGE_CELL_SIZE_RATIO)    .coerceIn(MIN_COVERAGE_CELL_SIZE_PX, MAX_COVERAGE_CELL_SIZE_PX)
```

When the user drags, we stamp which grid cells intersect the brush circle and record distinct cell ids in scratchedBuckets. The reveal target is derived from the fraction of visible cells and compared in updateRevealState:

```
private fun recalculateRevealTarget() {    revealBucketTarget = max(        1,        ceil(visibleBucketCount * revealThreshold).toInt()    )}private fun updateRevealState() {    if (!isRevealThresholdReached &&        scratchedBuckets.size >= revealBucketTarget    ) {        isRevealThresholdReached = true    }}
```

No GPU readback for coverage. No alpha-channel integration over the layer — mostly integer bookkeeping.

### Handling shape-clipped surfaces

Real scratch cards are not always rectangular. ScratchOverlay takes an optional clipShape on ScratchOverlayConfig. On layout, that shape becomes a Compose path at the layer’s pixel size; ScratchState optionally converts it to an Android Region.

```
clipRegion = clipPath?.let { path ->    val bounds = RectF()    path.asAndroidPath().computeBounds(bounds, true)    Region().apply {        setPath(            path.asAndroidPath(),            Region(                bounds.left.toInt(),                bounds.top.toInt(),                bounds.right.toInt(),                bounds.bottom.toInt()            )        )    }}
```

When counting visible buckets (the denominator for your threshold), only cell centers inside the region count. When stamping coverage, buckets outside the region are ignored. The same vanishThreshold (e.g. 50% of visible area) stays meaningful for circles, rounded rects, and other clips.

### Continuous coverage along a drag segment

Fast movement produces sparse touch samples. If you only stamp at each reported point, you can leave gaps in the grid.

markCoverageAlongSegment interpolates between the previous and current point. Step count scales with segment length:

```
val steps = max(    1,    ceil(        max(abs(dx), abs(dy)) /            max(1f, coverageCellSizePx * COVERAGE_SAMPLING_STEP_RATIO)    ).toInt())for (i in 0..steps) {    val t = i / steps.toFloat()    stampBrushAt(        start.x + dx * t,        start.y + dy * t    )}
```

So coverage stays continuous even when events are far apart.

### The @Stable annotation

ScratchState is annotated @Stable. That tells the Compose compiler the class is safe to treat as stable for optimization purposes, provided you honor the usual contract: observable state should change through mutableStateOf` / mutableStateListOf (or other snapshot-aware APIs) so readers recompose when values change.

Public flags such as isRevealThresholdReached and hasUserStartedScratching use mutableStateOf. The scratch polyline uses mutableStateListOf () (with null separating strokes) so structural edits participate in the snapshot system.

@Stable is not fully “enforced” by the compiler — you still need to keep the type honest as you evolve it.

### Geometry recalculation on size change

When the scratch layer’s size or brush geometry changes, updateLayerSize / applyGeometry rebuilds the grid and clipRegion, recomputes visibleBucketCount and revealBucketTarget, and clears scratch data. Old points and bucket ids referred to the previous pixel grid; after rotation or resize, starting fresh is the consistent behavior.

### What the composable does (and what ScratchState does)

ScratchState (internal constructor; created by rememberScratchState() inside ScratchOverlay) focuses on math and gesture state.

ScratchOverlay narrows UI work to:

```
/** * Scratch-to-reveal composable. * * **Visual stack (bottom → top)**   * 1. Optional [revealedContent] — what appears after scratching.   * 2. [scratchableContent] — the foil/image on top, drawn inside an offscreen layer where drags *    “erase” pixels using [BlendMode.Clear], so the layer behind shows through. * * **Why offscreen?**   * Clearing pixels must not punch holes through unrelated parents. [CompositingStrategy.Offscreen] * isolates the scratch surface so only this layer is affected. * * **End-to-end flow**   * 1. Layout gives the scratch surface a non-zero size ([ScratchState] needs real pixels for coverage).   * 2. [onSizeChanged] feeds that size (+ optional [ScratchOverlayConfig.clipShape]) into [ScratchState].   * 3. Drags append points; we draw a stroke with clear blend on top of the scratch content.   * 4. In parallel, [ScratchState] estimates how much area was scratched (grid “buckets”).   * 5. When enough buckets are hit → reveal flag → [onRevealed], then we animate overlay alpha to 0 (“vanish”). * * **Sizing modes** ([ScratchAreaSpec])   * - [ScratchAreaSpec.Fixed]: you pass an explicit [androidx.compose.ui.unit.DpSize].   * - [ScratchAreaSpec.MatchScratchable]: we measure [scratchableContent] first, then build the overlay *   at that size so you do not duplicate width/height. ```
```

- ScratchOverlayConfig — e.g. vanishThreshold, strokeWidthPx, clipShape, and ScratchAreaSpec (MatchScratchable by default, or Fixed(DpSize))

- SideEffect — updateParams when brush/threshold change

- onSizeChanged — updateLayerSize with pixel IntSize and optional clip path from clipShape

- pointerInput + detectDragGestures — handleDragStart, handleDrag, handleDragEnd

- graphicsLayer — CompositingStrategy.Offscreen and Animatable alpha for the vanish

- drawWithContent — drawContent() , then drawPath with BlendMode.Clear from buildScratchPath

- LaunchedEffect — invoke onScratchStarted / onRevealed when flags change, and animate vanishAlpha when the threshold is reached.

- SubcomposeLayout (when scratchArea is MatchScratchable) — measure scratchableContent, then lay out the real overlay at Constraints.fixed(w, h) so size matches content without duplicating Dp values.

So: logic and coverage live in ScratchState; ScratchOverlay is the integration layer.

### Using it in your UI

Minimal pattern (default sizing follows scratchableContent measurement):

```
ScratchOverlay(    config = ScratchOverlayConfig(        clipShape = RoundedCornerShape(16.dp),    ),    revealedContent = { /* under layer */ },    scratchableContent = { /* foil on top — set Modifier.size here */ },)
```

Pass scratchArea = ScratchAreaSpec.Fixed(DpSize(width, height)) when you want an explicit overlay size.

### Key takeaways

Grid-based coverage beats pixel readback for this “how much surface” question — updating a HashSet of bucket ids on drag is cheap compared to reading alpha from a surface.

Interpolate between gesture samples so fast drags do not undercount coverage.

Region (from a clip path) keeps denominators and stamping consistent for non-rectangular scratch areas.

Isolate clear blending with an offscreen graphicsLayer so BlendMode.Clear does not punch holes through unrelated parents.
