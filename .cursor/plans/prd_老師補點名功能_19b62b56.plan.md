# PRD 計畫：老師帳號補點名（過去上課紀錄）

## 目標
- 解決老師登入後在出缺勤頁看不到「待補點名（已結束節次）」的功能缺口。
- 提供 PM 可評估排程的規格：MVP 功能、權限邏輯、驗收標準、風險與里程碑。

## 現況與缺口（As-Is）
- 前端在 [`/home/admin/frontend/src/pages/AttendancePage.vue`](/home/admin/frontend/src/pages/AttendancePage.vue) 以 `v-if="!isTeacher"` 隱藏「待補點名」區塊，老師完全無 UI 入口。
- 同檔案 `onMounted` / `watch` 內僅在 `!isTeacher` 時執行 `fetchMakeupSessions()`，導致老師不會載入過去待補資料。
- 後端 [`/home/admin/backend/app/Http/Controllers/AttendanceController.php`](/home/admin/backend/app/Http/Controllers/AttendanceController.php) 已有 `endedSessions()` 且支援 teacher 角色（含代課與 `Stop=0` 防呆），代表核心 API 能力已存在。
- 路由 [`/home/admin/backend/routes/api.php`](/home/admin/backend/routes/api.php) 已開放 `GET /api/v1/attendance/ended-sessions` 給 `director,teacher`。

## 使用者與場景
- 使用者：`teacher`。
- 場景：老師忘記即時點名，需在課後回補過去堂次狀態（到班/遲到/請假/缺席），確保堂數與學務紀錄一致。

## MVP 範圍
- 僅調整老師端出缺勤頁，讓老師可看見並操作「待補點名（已結束節次）」。
- 沿用現有 API：`GET /api/v1/attendance/ended-sessions`、`POST /api/v1/attendance`。
- 維持既有資料隔離：老師僅可見自己合約授課或代課節次。

## 需求定義（PM 規格）
- `FR-1` 老師可見補點名區塊
  - 老師登入出缺勤頁時，顯示「待補點名（已結束節次）」卡片。
- `FR-2` 老師可查詢日期範圍
  - 預設區間最近 7 天，可調整起訖並查詢。
- `FR-3` 老師可補登狀態
  - 每筆可選 `present/late/leave/absent` 並提交。
  - 補登成功後，該筆自清單移除並顯示成功訊息。
- `FR-4` 權限與隔離
  - 不可看到他人老師節次；不可跨分校讀取未授權資料。
- `FR-5` 相容既有邏輯
  - `leave` 仍走請假順延流程；`present/late` 仍扣堂，行為與主任端一致。

## 非功能需求
- 查詢回應時間：50 筆以內目標 < 1 秒（內網環境）。
- 失敗提示要可行動（例：權限不足、查詢失敗、重複點名）。
- 手機版保留可操作性（不新增複雜交互）。

## 驗收標準（Acceptance Criteria）
- `AC-1` 老師登入後可見補點名區塊與日期篩選器。
- `AC-2` 老師可查到自己待補節次，不含他人節次。
- `AC-3` 補登 `present/late/leave/absent` 均可成功寫入，且狀態結果正確。
- `AC-4` `leave` 會維持順延語意，回傳與提示一致。
- `AC-5` 補登成功後列表即時更新，不需手動整頁刷新。
- `AC-6` 無資料時顯示空狀態文案，不出現錯誤。

## UI/UX 審閱檢查清單（給設計端 Check）
- `UX-1` 資訊架構：老師角色在出缺勤頁可清楚理解「今日待點名」與「待補點名（已結束節次）」是兩個區塊，且文案不混淆。
- `UX-2` 日期篩選：起訖日期預設合理（最近 7 天），操作步驟最少，查詢按鈕文案明確。
- `UX-3` 狀態操作：`到班/遲到/請假/缺席` 的選擇元件在桌機與手機都易點擊，避免誤觸。
- `UX-4` 回饋機制：補登成功、失敗、無資料、權限不足皆有明確提示，且位置固定、易被看見。
- `UX-5` 視覺一致：沿用既有出缺勤頁元件語彙（按鈕、表格、訊息樣式），不新增割裂風格。
- `UX-6` 響應式：手機版在不橫向捲動或最小捲動情況下可完成補登主要流程。
- `UX-7` 可近性：狀態顏色不作為唯一識別，需同時有文字標籤；對比度符合可讀性。

## 架構師審閱檢查清單（Architecture Check）
- `ARCH-1` 既有能力復用：確認優先沿用現有 `AttendanceController::endedSessions` 與 `store` 流程，不重建平行邏輯。
- `ARCH-2` 權限邊界：確認 teacher 僅可操作「合約授課 + 代課」節次，且不可越權補登。
- `ARCH-3` 多分校隔離：確認 `branch_id` / `CampusID` 驗證仍在後端主導，前端僅做體驗層處理。
- `ARCH-4` 資料一致性：確認補登後 `ClassSession.Status`、`StudentSingIn`、堂數扣除/順延狀態一致，無雙寫衝突。
- `ARCH-5` 風險控制：確認不變更高風險扣堂核心（`SessionDeductionService`）與請假 cascade 主流程。
- `ARCH-6` 可測試性：確認可用既有 Feature Test 模式覆蓋 teacher 權限、代課、Stop=0 與補登回寫。

## CTO 審閱檢查清單（CTO Check）
- `CTO-1` 商業價值：此需求可降低漏點名造成的人工修正成本，且對老師日常流程有直接效益。
- `CTO-2` 範圍控制：MVP 僅開放老師入口與互動，不擴大 API 規格，避免時程膨脹。
- `CTO-3` 上線風險：核心為前端可見性與流程串接，後端以既有能力為主，屬中低風險變更。
- `CTO-4` 監控指標：需追蹤補點名成功率、錯誤率、人工修正工單數是否下降。
- `CTO-5` 發版策略：建議先小範圍（指定分校/角色）驗證，再全分校 rollout。
- `CTO-6` 後續擴充：若使用量高再評估歷史區間預設、批次補登與提醒通知。

## QA 審視測試清單（Test Checklist）
### A. 功能正向流程
- `QA-01` 老師登入出缺勤頁可看到「待補點名（已結束節次）」區塊。
- `QA-02` 預設日期區間為最近 7 天，點擊查詢後可載入資料。
- `QA-03` 補登 `present` 成功：顯示成功訊息，該筆從列表移除。
- `QA-04` 補登 `late` 成功：狀態寫入正確，列表即時更新。
- `QA-05` 補登 `leave` 成功：顯示順延結果（若有 `extended_end_date`）。
- `QA-06` 補登 `absent` 成功：狀態寫入正確，無前端錯誤。

### B. 權限與資料隔離
- `QA-07` 老師 A 看不到老師 B 的待補節次（含同分校）。
- `QA-08` 代課老師可看到自己代課節次並可補登。
- `QA-09` 跨分校資料不外露：切換分校/branch 後僅顯示授權範圍。
- `QA-10` 無授權條件下 API 回傳 403，前端提示文案正確。

### C. 邊界與異常處理
- `QA-11` 查詢區間無資料時，顯示空狀態文案，不出現 console error。
- `QA-12` 重複補登同一節次時，應收到可理解錯誤（如已點名）。
- `QA-13` 網路中斷/timeout 時，前端顯示失敗提示且可重試。
- `QA-14` 日期輸入異常（起日 > 迄日）時，系統有防呆或錯誤提示。
- `QA-15` 大量資料分頁（page/per_page）可正常載入更多，不重複不漏資料。

### D. 回歸重點
- `QA-16` 主任端「待補點名」功能不受影響（既有流程可用）。
- `QA-17` 今日待點名（非補點名）流程不受影響。
- `QA-18` 出缺勤紀錄列表「修改狀態」流程不退化。
- `QA-19` 請假補登後堂數/順延行為與既有規則一致。
- `QA-20` 教師首頁/其他頁面不因此變更產生導覽或權限異常。

### E. 裝置與可用性
- `QA-21` 桌機版：篩選、選狀態、送出、訊息提示操作順暢。
- `QA-22` 手機版：可在不破版情況下完成完整補登流程。
- `QA-23` 色彩與文字同時可辨識狀態（非只靠顏色）。

### F. 上線前後檢核
- `QA-24` Staging 驗收通過且 Critical/Major 缺陷為 0。
- `QA-25` 上線後抽驗 3 個老師帳號：可見資料、可補登、可回寫。
- `QA-26` 追蹤指標可被蒐集：成功率、錯誤率、人工修正工單數。

## 風險與對策
- 風險：老師誤補他人堂次。
  - 對策：沿用後端 `teacher` 篩選與授課/代課驗證，不在前端做權限判斷。
- 風險：補登造成堂數錯扣疑慮。
  - 對策：沿用既有 `AttendanceController::store` + `SessionDeductionService`，避免重寫扣堂規則。
- 風險：大量歷史資料造成查詢慢。
  - 對策：預設 7 天 + 分頁（現有 `per_page/page`），先做 MVP，再評估擴窗。

## 里程碑建議
- M1（0.5~1 天）：PRD 確認 + UX 文案定稿。
- M2（1~2 天）：前端開放老師補點名入口與互動調整。
- M3（0.5~1 天）：測試驗收（老師權限、代課、請假順延、空狀態）。
- M4（0.5 天）：上線與回饋觀測（錯誤率、補登使用率）。

## 測試與數據追蹤建議
- 手動測試：老師一般授課、老師代課、跨分校切換、無資料區間。
- API 回歸：`ended-sessions` 僅回傳 teacher 可見課程。
- 上線後指標：
  - 老師補點名成功率
  - 補點名平均處理時間
  - 因漏點名產生的人工修正工單數
