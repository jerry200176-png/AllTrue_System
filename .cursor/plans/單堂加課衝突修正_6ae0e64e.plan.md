# 單堂加課衝突修正計畫

## 目標與原則
- 保留既有「歷史紀錄鎖定不可覆寫」原則，避免破壞 `ClassSession`、`StudentSingIn`、`LearningRecord` 一致性。
- 將目前單一 409 訊息升級為可行動的錯誤引導，讓主任/櫃檯知道下一步該改「時間」或改走「調課/請假」。
- 在前端送出前做衝突預檢，降低使用者反覆嘗試失敗。

## 現況重點
- 後端在 [StudentClassController.php]( /home/admin/backend/app/Http/Controllers/StudentClassController.php ) `addSession()` 內，若同日期同時間已有 `ClassSession` 且該堂次在鎖定集合（已有出缺勤或核准評量）則直接回 409（目前訊息即你截圖內容）。
- 前端 [CourseManagement.vue]( /home/admin/frontend/src/pages/CourseManagement.vue )、[StudentsList.vue]( /home/admin/frontend/src/pages/StudentsList.vue ) 的「單次加課」僅顯示後端 message，沒有預檢與替代建議。
- 單堂加課彈窗 [QuickAddSessionModal.vue]( /home/admin/frontend/src/components/course-management/QuickAddSessionModal.vue ) 目前沒有顯示衝突判斷結果。

## 修正方案（MVP）
1. **後端：提供可判斷衝突原因的結構化錯誤**
   - 目標檔案：[StudentClassController.php]( /home/admin/backend/app/Http/Controllers/StudentClassController.php )
   - 在 409 回應增加欄位（例如 `error_code`, `conflict_session_id`, `has_attendance`, `has_approved_learning_record`, `suggestion`）。
   - 訊息文案改為「該時段已有已點名/已核准堂次，請改選其他時段，或先處理原堂次（調課/請假）。」

2. **後端：新增衝突預檢 API（不寫入）**
   - 目標檔案：[api.php]( /home/admin/backend/routes/api.php )、[StudentClassController.php]( /home/admin/backend/app/Http/Controllers/StudentClassController.php )
   - 新增 `POST /api/v1/student-classes/{studentClass}/add-session/check`（或等價命名）回傳：
     - `can_add`、`conflict_type`（none/locked_existing/full_capacity 等）
     - `suggested_actions`（改時段、調課、請假）
   - 重用 `addSession()` 的核心判斷邏輯，避免雙邏輯分岔（抽成私有方法）。

3. **前端：送出前預檢 + 友善引導**
   - 目標檔案：[CourseManagement.vue]( /home/admin/frontend/src/pages/CourseManagement.vue )、[StudentsList.vue]( /home/admin/frontend/src/pages/StudentsList.vue )、[QuickAddSessionModal.vue]( /home/admin/frontend/src/components/course-management/QuickAddSessionModal.vue )
   - 使用者改日期/時間後先呼叫 `add-session/check`：
     - `can_add=true` 才允許送出
     - `can_add=false` 時在 modal 內顯示可操作建議，並禁用送出按鈕
   - 針對 409（競態）仍保留最後防線：顯示結構化錯誤 + 自動 refresh 堂次資料。

4. **測試與回歸**
   - 後端測試新增/擴充：[StudentClassUpdateScheduleReconcileTest.php]( /home/admin/backend/tests/Feature/StudentClassUpdateScheduleReconcileTest.php ) 或新增專用 `add-session` 測試檔
   - 覆蓋案例：
     - 同時段存在且含 `StudentSingIn` -> `can_add=false` / 409
     - 同時段存在且含核准 `LearningRecord` -> `can_add=false` / 409
     - 同時段存在但未鎖定 -> 可覆寫成功
     - 無同時段但堂次已排滿且無可搬移堂次 -> `full_capacity`
     - 有可搬移堂次 -> 成功並回傳 `moved_from_date`

5. **UAT 驗收流程**
   - 在課程管理與學生管理兩入口各跑一次：
     - 衝突時不再只看到「無法重覆補登」；可看到明確原因與下一步。
     - 非衝突時單堂加課可正常成功。
     - 已點名/已核准歷史資料不被覆寫。

## CTO 補強（架構治理）
1. **API 相容性策略**
   - `add-session` 現有 `message` 欄位需保留；新增欄位採增量模式，避免舊版前端壞掉。
   - `add-session/check` 回傳結構先凍結 MVP 欄位（`can_add`, `conflict_type`, `suggested_actions`, `message`），後續擴充採 optional 欄位。
   - 文件同步更新至 [docs/CHANGELOG.md]( /home/admin/docs/CHANGELOG.md ) 與 API 說明，明確標註「不改既有錯誤碼語意」。

2. **效能與資料庫治理**
   - 預檢與正式送出共用查詢組件，避免雙倍資料庫負擔。
   - 盤點查詢條件（`StudentClassID` + `SessionDate` + `StartTime`、`ClassSessionID` 關聯 `StudentSingIn` / `LearningRecord`），確認是否需補複合索引。
   - 加入壓測基準：尖峰 95th percentile API latency 目標值，作為上線 gate。

3. **可觀測性與營運回饋**
   - 後端新增結構化 log 事件：`add_session_conflict_locked`, `add_session_conflict_full_capacity`, `add_session_race_conflict`。
   - 前端記錄使用者行為漏斗（開 modal → 預檢失敗/成功 → 送出成功/失敗），確認 UX 是否真正改善。
   - 上線後 3~7 天追蹤：409 比率、重試次數、客服回報數。

4. **上線與回滾**
   - 以 feature flag 控制「前端預檢提示」與「結構化錯誤呈現」，先灰度給主任角色。
   - 若出現異常，先關閉前端預檢流程（回退至既有送出），不回退資料安全核心邏輯。
   - 明確定義 rollback 判準：錯誤率、延遲、客服工單量超過門檻即回退。

## 風險與控管
- **雙入口不一致風險**：`CourseManagement` 與 `StudentsList` 必須共用同一錯誤處理與預檢函式，避免一邊可用一邊失敗。
- **判斷邏輯分叉風險**：`check` 與 `addSession` 必須抽同一服務/方法，禁止複製貼上邏輯。
- **資料安全風險**：維持「鎖定堂次不可覆寫」為硬規則，不在本次放寬。
- **相容性風險**：任何錯誤回應改動都需保持 `message` 可用，避免既有 alert 流程中斷。
- **效能風險**：新增預檢後 API 次數上升，需透過 debounce 與後端查詢優化控管。
- **營運風險**：若僅改文案不改流程，客服仍可能收到「不知道下一步」回報，需用監控數據驗證改善幅度。

## QA 驗收計畫（新增）
### 1) 驗收範圍與策略
- 範圍：`add-session/check` 預檢、`add-session` 正式送出、雙入口 UI（課程管理/學生管理）、錯誤引導文案、競態 fallback。
- 測試層次：API 契約測試（穩定性）+ Feature 測試（商業邏輯）+ 手動 UAT（操作體驗）。
- 角色覆蓋：`director`、`teacher`（權限可見範圍）至少各一輪。

### 2) 驗收矩陣（核心案例）
1. **locked_existing（已有出缺勤）**
   - 前置：同日時段有 `ClassSession` 且有 `StudentSingIn`。
   - 預期：`check` 回 `can_add=false`；送出回 409；UI 顯示可行下一步且禁用送出。
2. **locked_existing（已有核准評量）**
   - 前置：同日時段有 `ClassSession` 且有 approved `LearningRecord`。
   - 預期：同上，且 `message` 保持存在（相容舊前端）。
3. **full_capacity（堂次已滿無可搬移）**
   - 前置：`SessionCount` 已滿、無可移動 `scheduled`。
   - 預期：`check` / `add-session` 都給一致衝突語意。
4. **可成功搬移**
   - 前置：有可移動未來 `scheduled` 堂次。
   - 預期：送出成功，回傳 `moved_from_date`，總堂數不變。
5. **競態案例**
   - 前置：A 預檢通過，B 先改狀態使其衝突。
   - 預期：A 送出收到 409，前端顯示 fallback 提示並自動 refresh。
6. **多校區/權限**
   - 前置：跨分校課程資料。
   - 預期：不得跨校成功預檢/送出，維持既有權限隔離。

### 3) 非功能驗收（NFR）
- 效能：預檢 API p95 延遲需達既定門檻（由 `qa-nfr-gates` 任務定義數值）。
- 穩定性：預檢與送出錯誤率在灰度期間不得高於基線容忍值。
- 可用性：UAT 中「看不懂下一步」主觀回饋降至可接受範圍（由客服標記工單追蹤）。

### 4) Definition of Done（QA 版）
- API 契約測試、Feature 回歸測試、雙入口 UAT 全綠。
- 409/422 錯誤皆有可操作引導文案，且不破壞既有 `message` 相容性。
- 競態 fallback 行為驗證通過（提示 + 自動刷新）。
- 灰度上線 3~7 天觀測達標（錯誤率、延遲、客服工單）。

### 5) 上線後驗收節奏
- Day 0：灰度上線後 2 小時快速檢查（API 健康、前端主流程）。
- Day 1-3：每日檢查衝突事件分布與客服回報。
- Day 7：做結案驗收，輸出「是否全面開放」決策與殘留風險清單。
