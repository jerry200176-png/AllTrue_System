## 2. 目標與業務背景

**現在的痛點**

主任在新增課程時填入繳費日期，按下「建立課程」後，課程清單的繳費狀態欄位仍顯示「未繳費」（橘色標籤）。主任必須再手動點擊「切換繳費狀態」才能改為已繳費，造成重複操作與資料可信度疑慮（帳務人員會誤以為這筆尚未收款）。

**解決後的業務價值**

- 消除主任的冗餘操作步驟（每次建立課程不再需要二次切換繳費狀態）
- 確保繳費記錄在建立時即正確落地，帳務統計不因 UI 誤判而失真
- 提高主任對系統的信任度

**成功指標（KPI）**

- 建立課程後的繳費狀態正確率：100%（填了 paid_at ⇒ 顯示已繳費）
- 主任回報「未繳費顯示錯誤」工單數量：降為 0

---

## 3. 範圍

**In Scope**
- 修正課程建立流程（`POST /api/v1/class-sessions/batch`）中，繳費標記被覆蓋歸零的問題
- 修正所有呼叫堂數重算邏輯的路徑（包含 session 狀態切換、LR 核准、加購堂次）中，繳費標記被錯誤清零的問題
- 新增回歸測試守護此行為

**Out of Scope**
- 前端 `UniversalClassScheduler.vue` 的 UI 改動（前端已正確送出 paid_at，不需修改）
- 催繳名單 (`alerts/tuition`) 的提醒邏輯（屬獨立功能）
- Invoice / 付款流程的改動

## 5. User Stories

**US-01：主任建立短期課程並填繳費日期**
> **As a** 主任，**I want** 建立課程時填入繳費日期後，課程清單立即顯示「已繳費」，**so that** 我不需要再手動切換繳費狀態，帳務紀錄一次完成。
>
> Acceptance Criteria：
> - [ ] 建立課程時填入繳費日期（paid_at），提交後 `GET /api/v1/student-classes` 回傳 `payment_status: "paid"`
> - [ ] 課程購買堂數為 1 堂或 2 堂時，上述行為同樣成立
> - [ ] 建立課程未填繳費日期，`payment_status` 仍為 `"unpaid"`

**US-02：主任在補登模式下建立多堂已上課程並填繳費日期**
> **As a** 主任，**I want** 補登歷史課程（確認多堂已完成）後，繳費狀態仍反映我填入的繳費日期，**so that** 帳務不因補登操作而被誤清。
>
> Acceptance Criteria：
> - [ ] 補登模式下，建立課程並指定多堂已完成（導致剩餘堂數 ≤ 2），paid_at 填入後 `payment_status` 仍為 `"paid"`
> - [ ] 補登後呼叫 GET /api/v1/student-classes，繳費標記不被重置

## 6. 功能需求（FR）

**FR-001**：系統應確保「堂數重算」邏輯**只異動** `UsedSessions` 與 `RemainingSessions`，不得寫入或覆蓋 `Paid` / `PayDate` 欄位。

**FR-002**：`Paid` 欄位只能透過以下三條路徑寫入，其他地方一律禁止：
1. 課程建立 API（`POST /api/v1/class-sessions/batch`）帶入 `paid_at`
2. 課程編輯 API（`PUT /api/v1/student-classes/:id`）帶入 `paid_at` 或 `payment_status`
3. Invoice 付款記錄 API（`POST /api/v1/invoices/:id/payments`）

**FR-003**：建立課程時帶入 `paid_at`，無論 `RemainingSessions` 最終計算結果為何（0、1、2 或更多），`payment_status` 回傳值均應為 `"paid"`。

**FR-004**：已存在 `Paid = 1` 的課程，在執行任何堂數扣點（簽到、請假處理、LR 核准、補登）後，`Paid` 不得被重算邏輯清為 0。

## 9. 資安與存取控制

- **存取角色**：`payment_status` 的讀寫僅限通過 `auth:api` middleware 的已登入使用者；主任（`type=A`）與超級管理員（`type=S`）可寫入；本次修改不新增或放寬任何 role 檢查
- **PII**：`PayDate` 為繳費日期，屬財務記錄，系統已有 campus-scoped 存取控制保護
- **稽核 log**：現有的 `payroll_audit_log` / Invoice 付款記錄機制不受影響；本次移除的邏輯沒有寫入 log，移除後無需補建
- **STRIDE 快評**：
  - Tampering：移除錯誤清零邏輯後，`Paid` 只由三條明確路徑寫入，Tampering 面縮小
  - 其他 STRIDE 面向：本次純移除邏輯，無新增 API、無新增 PII 欄位，無新增風險

## 10. QA 驗收標準與測試計畫

### FR-001 / FR-003 — 課程建立 + paid_at

| 類型 | 場景 | 期望結果 |
|---|---|---|
| Happy Path | 建立 8 堂課程（`SessionCount=8`），填 `paid_at`，無補登日期 | `payment_status = "paid"` |
| Edge | 建立 2 堂課程（`SessionCount=2`），填 `paid_at` | `payment_status = "paid"`（不得因 RemainingSessions=2 ≤ 2 被清為 unpaid） |
| Edge | 建立 1 堂課程（`SessionCount=1`），填 `paid_at` | `payment_status = "paid"` |
| Happy Path | 建立課程，**不**填 `paid_at` | `payment_status = "unpaid"` |
| Error | `paid_at` 格式錯誤（非日期字串）| API 回 422 Validation Error |

### FR-002 / FR-004 — 堂數扣點後繳費標記不被清除

| 類型 | 場景 | 期望結果 |
|---|---|---|
| Edge | 課程 `Paid=1`，補登多堂導致 `RemainingSessions=1`，呼叫堂數重算 | `Paid` 仍為 1 |
| Edge | 課程 `Paid=1`，學生簽到後剩餘堂數降至 2 | `Paid` 仍為 1 |
| Regression | 課程 `Paid=0`，堂數重算後 | `Paid` 仍為 0（不應被錯誤抬高） |
