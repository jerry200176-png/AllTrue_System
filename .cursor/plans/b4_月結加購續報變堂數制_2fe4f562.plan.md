| 欄位 | 內容 |

## 2. 業務背景與影響

月結制是補習班重要收費模式（`ScheduleMode = 'date'`），以 `settlement_day`（每月結算日）與 `monthly_sessions`（每月預排堂數）為核心。當月結課到期需「續約」時，主任透過「加購」入口操作，卻得到一筆全新的**堂數制**課程，帶來：

1. **計費錯誤**：新課用「堂數×費率」算費，不符月結邏輯（月費固定，與堂數無強制關係）。
2. **排課錯誤**：`buildSessionsForCount` 生成固定堂次預排，與月結的按月自動排課不同。
3. **重複課程**：舊月結課不被結案，學生同一科目出現兩筆課程並存，影響點名、評量、科目數統計。
4. **UI 混亂**：月結課從「月結」區跳到「堂數制」，主任察覺後需手動刪除錯誤課程。

**修復後預期行為**：

- 月結課加購入口改為「月結續約」：延長現有課程的 `EndDate`（或調整 `settlement_day`／`monthly_sessions`），不另開新課程列。
- 前端對月結課隱藏「加購堂數」流程，改以「月結續約」modal 替代，收集月數或新 `EndDate`。
- 後端新增（或拆分現有）月結續約邏輯，維持 `ScheduleMode = 'date'`。
- 堂數制課程的「加購堂數」流程完全不受影響。

## 3. 範圍

### In Scope

- `StudentClassController::purchaseBatch`：偵測來源課程模式，月結課走新分支（延長既有課程），堂數制走現有分支
- `StudentsList.vue`：加購按鈕對月結課改為觸發「月結續約 modal」
- `CourseManagement.vue`：加購選單對月結課改為觸發「月結續約 modal」

- `purchaseBatch` 月結分支：更新原課程 `EndDate`（`PUT` 既有 `StudentClass`），不建立新筆

### Out of Scope

- 堂數制（`payment_type === 'session'`）現有加購流程：不改動

- `AlertController` 月結繳費提醒邏輯：不改
- DB migration：不需新欄位（`EndDate`、`settlement_day`、`monthly_sessions` 均已存在）
- 家長 Portal、老師工作台：不涉及加購

## 5. Acceptance Criteria

### AC-001：月結課加購入口改為月結續約

- AC-001-a：director 對 `payment_type = 'monthly'` 課程點「加購」，系統顯示**月結續約 modal**（而非原加購堂數 modal）
- AC-001-b：`payment_type = 'session'` 課程點「加購」，系統顯示原加購堂數 modal，行為與修改前完全相同

### AC-002：月結續約延長原課程

- AC-002-a：填寫新 `EndDate`（或延長月數）送出後，原 `StudentClass` 的 `EndDate` 更新，**不新增** `StudentClass` 資料列
- AC-002-b：原課程 `ScheduleMode` 維持 `'date'`（`payment_type` 維持 `'monthly'`），`settlement_day`、`monthly_sessions` 不變
- AC-002-c：原課程 `status` 維持 `'active'`，不被設為 `inactive`

### AC-003：後端 purchaseBatch 保護

- AC-003-a：對月結課呼叫 `POST /api/v1/student-classes/{id}/purchase-batch` 時，後端回傳 **`422 Unprocessable Entity`** 或執行月結延長邏輯（視最終設計），不建立 `ScheduleMode = 'count'` 的新課程列
- AC-003-b：對堂數制課程呼叫 `purchase-batch`，行為與修改前相同

### AC-004：月結續約計費欄位正確

- AC-004-a：月結續約後，課程的 `Charge`、`Pay`、`Paid` 欄位依月結邏輯計算（或由主任手動填寫），不使用堂數×費率公式

### AC-005：無重複課程

- AC-005-a：月結續約後，同一學生同一科目只有 **一筆** `status = active` 的月結課（舊課延長，無新課並存）

## 8. 技術方向

### 涉及檔案與方法

| 檔案 | 方法 / 位置 | 修改說明 |
|---|---|---|
| `backend/app/Http/Controllers/StudentClassController.php` | `purchaseBatch`（約 1336 行） | 在方法開頭偵測 `$studentClass->ScheduleMode`：若為 `'date'`，回傳 `422`（建議）或轉入月結續約邏輯；若為 `'count'`，走現有路徑 |
| `backend/app/Http/Controllers/StudentClassController.php` | 新增 `renewMonthly`（建議方法名） | 接收 `end_date`；以 `UPDATE StudentClass SET EndDate = ? WHERE ID = ?` 更新；不建立 `ClassSession`；回傳更新後的課程資料 |
| `backend/routes/api.php` | 新增路由（約 294 行附近） | `POST student-classes/{studentClass}/renew-monthly` → `renewMonthly` |
| `frontend/src/pages/StudentsList.vue` | `openAddSessionsForCourse`（約 2173 行） | 加判斷：`course.payment_type === 'monthly'` → 開月結續約 modal；否則走原邏輯 |
| `frontend/src/pages/CourseManagement.vue` | `openPurchaseModal`（約 1348 行） | 加判斷：`isSessionMode(c)` 為 false → 開月結續約 modal |
| `frontend/src/components/course-management/` | 新增 `RenewMonthlyModal.vue`（或在既有 modal 加月結 tab） | 欄位：延長月數（預設 1）或直接填新 EndDate；顯示現有 `settlement_day`、`monthly_sessions`；送出呼叫 `POST /renew-monthly` |

### 架構取捨理由

- **選擇新增 `renewMonthly` 方法 + 路由**（而非在 `purchaseBatch` 加 if-else 分支）：月結續約與堂數加購語意差異大（`UPDATE` vs `INSERT`），混在同一方法增加維護複雜度；新路由語意清晰，前後端都容易測試。
- **`purchaseBatch` 對月結回傳 `422`**（而非靜默轉向）：防止未來直接呼叫 API 的路徑繞過前端保護，確保堂數制加購邏輯永遠不被誤用於月結。
- **延長 EndDate（不新建課程）**（業界慣例）：Stripe 等主流訂閱系統續約均採「更新 `currentPeriodEnd`」（單一訂閱記錄 + 獨立發票），不為每期建立新訂閱資料，符合月結不新開課程 id 的語意；堂數制「新建批次」對應 Stripe 的「一次性購買」語意，兩者分離。

### 8b. Decision Log

| 日期 | 選項 | 選擇 | 理由 |
|---|---|---|---|
| 2026-04-21 | A. 在 `purchaseBatch` 加 if-else 處理月結 | 否 | 月結與堂數語意差異大，混用增加複雜度 |
| 2026-04-21 | B. 新增 `renewMonthly` 路由 | ✅ | 語意清晰，可獨立測試，符合業界慣例 |
| 2026-04-21 | C. 月結新開一筆課程（維持現有 purchaseBatch 流程，僅改 ScheduleMode） | 否 | 舊課不結案風險；新課 id 破壞連續性；違反「同一課程延伸」語意 |
| 2026-04-21 | D. 月結加購使用 `PUT /student-classes/{id}` 更新 EndDate | 否 | 現有 `update` 端點含大量欄位驗證，風險高；專用端點更安全 |

## 13. 風險 / 假設 / 開放問題

> WebSearch 查詢結果（2026-04-21）：查詢 monthly subscription renewal extend end date vs new record 業界慣例。Stripe / MongoDB subscription 設計均採「單一訂閱記錄 + 更新 `currentPeriodEnd`（EndDate）」，另建不可變的獨立 Invoice 做帳務紀錄。本修正方向（延長既有課程 EndDate）符合此慣例；堂數制的新建批次對應「一次性購買」語意，兩者分離。

| 類型 | 內容 |
|---|---|
| 風險 | 現有月結課若過去已被誤加購過（產生了堂數制課程），需要人工清理舊的錯誤課程批次；本計畫不提供自動清理。 |
| 風險 | 月結課「延長 EndDate」後，`AlertController` 的月結繳費提醒邏輯（`monthly_due_soon`）是否能正確計算新 EndDate，需驗收；本計畫列為 Out of Scope，但建議於 AC 驗收後確認。 |
| 假設 | 月結續約「延長 EndDate」不需重新建立 `ClassSession` 預排堂次（月結排課依 `settlement_day` / `monthly_sessions` 動態生成，非一次性預排）。 |
| 假設 | `monthly_sessions` 與 `settlement_day` 在續約時不需更改（如需更改，走現有「編輯課程」流程即可）。 |
| 開放問題 | 月結續約的計費（Charge／Pay）更新：是否由主任在「編輯課程」中手動更新，還是 `renewMonthly` 同步更新？建議由主任確認後再實作，本計畫預設「`renewMonthly` 只更新 `EndDate`，計費另由主任編輯」。 |
