## 0. 根因確認（Root Cause）

| 欄位 | 內容 |

| 嚴重度 | P2 |

## 2. 業務背景與影響

**現況痛點：** 備份排程（nightly / 6h）執行正常，但 dump 檔案從未被實際還原驗測。若檔案損毀、mysqldump 參數變更、或 schema 遷移造成還原失敗，維運人員將在真實 DR 事件時才發現問題。

**修復後預期行為：**
- 每月 1 日 02:00，最新 dump 自動還原至 `AllTrue_test`
- 四張核心表（Student、User、Campus、ClassSession）的 row count 逐一比對
- 比對結果（成功 or 差異清單）透過 Telegram 推送，人員無需登入伺服器即可確認

## 5. Acceptance Criteria

### AC-001：找到最新備份並驗証完整性
- AC-001-a：腳本執行時，優先選取 `backups/monthly/` 最新月備；若不存在則選 `backups/` 最新日備
- AC-001-b：選取的 `.sql.gz` 通過 `gzip -t` 完整性檢查後才繼續；損毀檔案導致腳本以非 0 exit code 終止並發送 Telegram 錯誤通知

### AC-002：還原至 AllTrue_test
- AC-002-a：腳本 DROP + CREATE `AllTrue_test`，再以 `gunzip | mysql AllTrue_test` 完整還原 dump
- AC-002-b：若 DROP / CREATE / 還原任一步驟失敗，腳本以非 0 exit code 終止並發送 Telegram 錯誤通知；生產 `AllTrue` 不受任何影響

### AC-003：row count 比對
- AC-003-a：比對 Student、User、Campus、ClassSession 四張表，AllTrue 與 AllTrue_test 各表 COUNT(*) 相同時，Telegram 通知標示「✅ 全數一致」並列出各表 row count
- AC-003-b：任意一張表 row count 不同時，Telegram 通知標示「⚠️ 差異」，並列出各表的生產數 vs 還原數及差值

### AC-004：crontab 排程
- AC-004-a：admin crontab 含 `0 2 1 * *` 條目，指向 `monthly-restore-drill.sh`，腳本輸出 append 至 `restore-drill.log`

## 6. 功能需求 FR

- **FR-001**：腳本讀取 `backend/.env` 取得 DB 憑證（沿用 `nightly-backup.sh` 的 `get_env()` 模式）；讀取 `/home/admin/.env.monitor` 取得 Telegram 憑證
- **FR-002**：腳本以 `ls -1t` 選取最新月備（`monthly/alltrue_monthly_*.sql.gz`）或最新日備（`alltrue_nightly_*.sql.gz`）作為還原來源
- **FR-003**：還原前以 `gzip -t` 驗証備份完整性；驗証失敗時 `send_telegram` 錯誤訊息並 `exit 1`
- **FR-004**：還原至 `AllTrue_test`：執行 `DROP DATABASE IF EXISTS AllTrue_test` → `CREATE DATABASE AllTrue_test CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` → `gunzip -c DUMP | mysql AllTrue_test`
- **FR-005**：還原完成後，對 Student、User、Campus、ClassSession 分別執行 `SELECT COUNT(*) FROM AllTrue.<table>` 及 `SELECT COUNT(*) FROM AllTrue_test.<table>`，記錄各表生產數與還原數
- **FR-006**：比對結果全數一致時，透過 `curl` 呼叫 Telegram Bot API 發送成功訊息，包含各表 row count 及所用備份檔名
- **FR-007**：任意表 row count 不一致時，發送差異明細訊息（表名 / 生產數 / 還原數 / 差值），並 `exit 1` 讓 cron 產生非 0 exit code（可被未來監控捕捉）
- **FR-008**：全部步驟含時間戳記寫入 `restore-drill.log`（同 `nightly-backup.sh` 的 `log()` 模式）
- **FR-009**：crontab 條目：`0 2 1 * * /home/admin/scripts/monthly-restore-drill.sh >> /home/admin/backups/restore-drill.log 2>&1`

## 8. 技術方向

**涉及檔案：**
- 新增：[`/home/admin/scripts/monthly-restore-drill.sh`](/home/admin/scripts/monthly-restore-drill.sh)
- 修改：admin 使用者 crontab（`crontab -e` 或寫入 `/etc/cron.d/alltrue-restore-drill`）
- 追加：[`/home/admin/docs/CHANGELOG.md`](/home/admin/docs/CHANGELOG.md) + [`/home/admin/docs/AI_REGRESSION_LESSONS.md`](/home/admin/docs/AI_REGRESSION_LESSONS.md)

**架構取捨：**

- **DROP + 重建 vs. 逐表 truncate**：選 DROP + 重建。逐表 truncate 需解 FK constraint 並依序清除；DROP + 重建與生產 dump 還原行為完全一致，更貼近真實 DR 場景。
- **月備優先 vs. 日備優先**：選月備優先（`monthly/` 最新）。月備是 nightly-backup.sh 在每月 1 號產生的完整全備，與還原演練同在月首觸發，語義一致；若月備不存在（例如首月）才 fallback 至最新日備。
- **Telegram via curl vs. Laravel notification**：選 curl。還原演練腳本獨立於 Laravel，避免 PHP 應用層錯誤影響通知；與 `monitor-alert.sh` 一致。
- **cron.d vs. user crontab**：選 `/etc/cron.d/alltrue-restore-drill`（root 可讀，易版控）；若 admin 無 sudo，改用 `crontab -e` 方式。

## 10. QA 驗收

### Happy Path
- [ ] 手動執行 `bash /home/admin/scripts/monthly-restore-drill.sh`，`restore-drill.log` 出現「還原成功」及各表 row count
- [ ] Telegram 收到「✅ 全數一致」訊息，含備份檔名、四表 count 及執行時間戳

### Edge Cases
- [ ] 刪除 `backups/monthly/` 所有檔案後執行，腳本 fallback 至最新日備並成功完成
- [ ] 以損毀的 `.sql.gz`（`dd if=/dev/urandom`覆寫）測試 FR-003，Telegram 收到完整性錯誤通知，`restore-drill.log` 記錄 exit 1

### Error Cases
- [ ] 暫時移除 `TELEGRAM_BOT_TOKEN`，確認腳本仍完成還原，僅 Telegram 發送失敗（`log WARN`，不 abort）
- [ ] `AllTrue_test` 不存在時（先手動 DROP），確認 `CREATE DATABASE` 步驟自動重建

### Revert-proof 驗證
- [ ] `git stash` 後腳本不存在，`crontab -l | grep monthly-restore-drill` 應找不到條目或腳本無法執行，確認 DoD 命令反映真實覆蓋

## 13. 風險 / 假設 / 開放問題

> WebSearch 已查詢「MySQL backup restore drill automation row count validation bash script best practices 2026」。

**風險：**
- **R1 AllTrue_test 有其他用途**：若開發者在 `AllTrue_test` 中有臨時資料，月首 DROP 會清除。緩解：腳本在 DROP 前 log 警告；若需保護，可改為固定名稱 `AllTrue_restore_drill`（Out of Scope for v1）
- **R2 還原期間 CPU/IO spike**：Pi 硬體資源有限，`gunzip | mysql` 在凌晨 2:00 執行，預期 I/O 影響低；但若 DB 未來成長至數 GB，需評估時間視窗
- **R3 row count 不一致的假性差異**：若 nightly 備份恰好在一個 transaction 中途，row count 可能有 1 筆誤差（`--single-transaction` 已降低此風險）；建議允許容差閾值（未在 v1 實作，列為 v2 改進）

**假設：**
- admin MySQL 使用者對 `AllTrue_test` 有完整 DROP/CREATE/ALL 權限（待部署時以 `SHOW GRANTS` 確認）
- 備份檔案名稱格式維持 `alltrue_nightly_*.sql.gz` 與 `alltrue_monthly_*.sql.gz`（與現有腳本一致）

**開放問題：**
- v2 是否擴充為比對 checksum（`CHECKSUM TABLE`）而非僅 row count？（業界建議，但 Pi 上執行時間可能偏長）
