# 輔導（tutoring）科目數統計顯示為 0 — 修正計畫

## 問題陳述

`GET /api/v1/finance/subject-units` 回傳的每位老師 `tutoring_hours` 均為 `0`，導致 `subject_count_with`（含輔導）= `subject_count_without`（不含輔導），使欄位形同虛設。

## 根因分析（程式碼已確認）

### 計算路徑

```
SubjectUnitsPage.vue
  → GET /api/v1/finance/subject-units
    → FinanceController::subjectUnits()
      → 只撈 LearningRecord WHERE Status='approved'
        → 讀 studentClass.ClassType → 分入 tutoring bucket
```

### 關鍵發現：3 個潛在根因

**根因 A（最可能）— 輔導課無 approved LearningRecord**

- `subjectUnits` 完全依賴 `Status='approved'` 的 LearningRecord（[`backend/app/Http/Controllers/FinanceController.php`](backend/app/Http/Controllers/FinanceController.php) L179）
- `ensurePastRecords` 確實會為輔導課的 ClassSession 自動建立空白 pending LR
- 但若老師從未填寫、或主任從未核准輔導課的 LR，`tutoring_hours` 永遠是 0
- 輔導課性質較彈性（補考、作業輔導），老師可能習慣不填評量表

**根因 B（次可能）— ClassType 儲存值不為 `'tutoring'`**

- DB Migration 的 `ClassType` 欄位 default 值是 `'regular'`（[`backend/database/migrations/2026_02_07_000020_add_class_type_to_student_class_table.php`](backend/database/migrations/2026_02_07_000020_add_class_type_to_student_class_table.php)），不是 `'one_on_one'`
- `FinanceController::subjectUnits` 遇到不在白名單的 ClassType 時，**靜默 fallback 成 `'one_on_one'`**（L240–241），不會報錯
- `PUT /api/v1/student-classes/{id}`（`update`）路徑 **沒有** `in:one_on_one,...` 驗證，歷史或編輯資料可能留有 `'regular'` 或其他異常值
- 若儲存為 `'regular'`，小時數會跑進 `one_on_one` bucket，導致一對一虛高、輔導顯示 0

**根因 C（需排除）— ClassSession 未建立 / 未標 attended**

- 輔導課若從未排堂或排堂後未點名，`ensurePastRecords` 無法建 LR，自然無 approved LR

## 診斷步驟（QA 執行）

QA 請在後端執行下列 tinker 語句或直接查 MySQL，回報數字後再決定修法：

```php
// Step 1: 確認輔導 StudentClass 存在
StudentClass::where('ClassType', 'tutoring')
    ->whereIn('StudentID', Student::where('CampusID', <敦化校區ID>)->pluck('id'))
    ->count();

// Step 2: 這些課是否有 attended ClassSession（有排堂且有上課紀錄）
ClassSession::whereIn('StudentClassID', StudentClass::where('ClassType','tutoring')->pluck('ID'))
    ->where('Status', 'attended')
    ->count();

// Step 3: 這些 Session 是否有對應 LearningRecord
LearningRecord::whereIn('ClassSessionID',
    ClassSession::whereIn('StudentClassID', StudentClass::where('ClassType','tutoring')->pluck('ID'))
        ->where('Status','attended')->pluck('id')
)->selectRaw('Status, count(*) as cnt')->groupBy('Status')->get();

// Step 4: 確認是否有 ClassType 不在白名單的資料（根因 B）
DB::table('StudentClass')
    ->whereNotIn('ClassType', ['one_on_one','one_on_two','one_on_three','tutoring','trial'])
    ->select('ClassType', DB::raw('count(*) as cnt'))
    ->groupBy('ClassType')->get();
```

**判讀**：
- Step 1 = 0 → 帳面上根本沒有輔導課，前端設定流程有問題
- Step 1 > 0, Step 2 = 0 → 有課但無出席記錄，排堂/點名流程未走完
- Step 1 > 0, Step 2 > 0, Step 3 全部 pending → **根因 A**，需調整計算方式或核准流程
- Step 4 出現 `regular` 或其他異常值 → **根因 B**，需資料修正 + 後端防呆

## 修正方案

### 方案 1：針對根因 A — 將輔導計算改為出席（ClassSession）基底（建議）

輔導課性質不同，強制要求 approved LearningRecord 才能計入科目數是不合理的業務邏輯。

**後端 `FinanceController::subjectUnits`** 增加輔導課的獨立計算路徑：

```
現在：僅從 approved LearningRecord 統計所有 ClassType 的時數
修改後：
  - one_on_one / one_on_two / one_on_three：仍從 approved LR 統計（維持現況）
  - tutoring：改從 ClassSession WHERE Status='attended' 統計，
              時數來源 = ClassSession.(EndTime - StartTime)，
              fallback = studentClass.SessionDuration / 60，再 fallback = 2.0
```

受影響檔案：
- [`backend/app/Http/Controllers/FinanceController.php`](backend/app/Http/Controllers/FinanceController.php)（`subjectUnits` 方法，約 L168–384）

前端不需要修改，回傳結構與欄位名稱不變。

### 方案 2：針對根因 B — 修正異常 ClassType 資料

若 Step 4 診斷顯示有 `'regular'` 或其他異常值：

1. **資料修正 migration**：將 `ClassType='regular'` 的既有資料依 `by1` 欄位推算正確 ClassType（`by1`：1=one_on_one, 2=one_on_two, 3=one_on_three, 4=tutoring）並更新
2. **後端防呆**：`StudentClassController` 的 `mapFrontendPayload` 加入 `ClassType` 白名單驗證，拒絕未知值

受影響檔案：
- [`backend/app/Http/Controllers/StudentClassController.php`](backend/app/Http/Controllers/StudentClassController.php)（`mapFrontendPayload`，L2010 附近）
- 新增 migration 檔

> 注意：方案 1 與方案 2 **不互斥**，即使診斷主因是 A，也建議同步執行方案 2 的後端防呆。

## 測試項目（QA 驗收）

1. 建立一個輔導課程（ClassType='tutoring'），排入過去 2 堂並標 attended
2. 若走方案 1，直接呼叫 `/api/v1/finance/subject-units`，確認 `tutoring_hours > 0`
3. 若走方案 1 + 方案 2，確認 `subject_count_with > subject_count_without`（差距 = tutoring_hours × 0.5 ÷ 8）
4. 確認 `share_pct` 合計仍為 100%
5. 確認「不含輔導」欄位數字確實沒有計入輔導時數
6. 確認試聽（trial）課程仍不計入任何欄位

## 執行順序

1. QA 先跑診斷查詢（~15 分鐘），回報結果給 CTO
2. CTO 確認根因後決定走方案 1、方案 2、或兩者並行
3. 若走方案 1，預估後端改動範圍為 30–60 行（僅 `subjectUnits` 方法）
4. 部署後 QA 再次驗收，對照截圖確認輔導欄位有數字且含/不含兩欄有差異
