## 1. 文件資訊

| 欄位 | 內容 |

---

## 2. 目標與業務背景

### 痛點

**Bug A — 課程回報管理分校視野過寬**
目前「課程回報管理」頁（`ScheduleDiscrepancyPage.vue`）的列表資料來自 `GET /api/v1/schedule-discrepancies`，後端 `resolveCampusScope` 對一般主任回傳 `auth_campus_ids` **聚合多校**（若主任被指派到多個分校則列表同時顯示多校回報）、對總部管理員（super_admin）則完全不過濾（看所有分校）。從業務角度：
- 單一分校的回報只應歸該分校的主任處理，避免跨校主管無意中看到別校私密細節（學生姓名、老師姓名、時段爭議）
- 目前依賴前端把 `branch_id` 帶入 query，一旦前端漏帶就會自動退化為「看全部指派分校」，屬於**前端邊界依賴**，不是後端強制
- 使用者明確要求：「**課程是哪個分校，就只有那個分校的主任可以看到**」

**Bug B — 老師回報「時間不正確」時無法指出正確時間**
老師用 `ReportDiscrepancyModal` 回報 `discrepancy_type = wrong_time`（上課時間有誤）時，目前只有：
- `time_range` 欄位：系統記錄的舊時段（從 session context 自動帶入）
- `notes` 欄位：自由文字備註

老師若知道「正確時間應為 14:00-16:00」，只能塞進 `notes` 自由文字或電話/LINE 私訊主任，造成：
- 主任處理時需反覆與老師確認「那實際應該是幾點」
- 回報→修正的循環時間拉長
- `notes` 內混合抱怨 + 正確時間，後端難以結構化分析

### 業務價值
- Bug A：強制資料隔離，符合 PDPA 最小必要原則，避免跨校資料非必要曝光
- Bug B：縮短「發現時段錯誤 → 主任修正」循環；老師提交時即附正確時間，主任可直接一鍵修正或 1 次確認後處理

### KPI
- 分校隔離：非 super_admin 主任的 `GET /schedule-discrepancies` 回傳結果中 `branch_id` 不屬於目前選取分校的筆數 = 0
- 正確時間填寫率：`wrong_time` 類型回報中 `corrected_time_range` 有填的比例 ≥ 60%（上線 2 週內）
- 平均處理時長：`wrong_time` 類型回報從 create 到 resolved 的中位時間縮短 ≥ 30%（對比上線前 4 週基線）

## 3. 範圍

### In Scope
- `GET /api/v1/schedule-discrepancies`：director 角色強制單一分校 scope（預設以 `currentBranch` / `branch_id` query；未指定時以 `auth_campus_ids[0]` 作 fallback 或回 422）
- `super_admin` 角色保留跨校視野（維持現行行為，使用者明確選擇選項 B）
- `schedule_discrepancies` 資料表新增 `corrected_time_range` varchar(32) nullable 欄位
- `POST /api/v1/schedule-discrepancies` 接受並驗證 `corrected_time_range`
- `ReportDiscrepancyModal.vue` 新增「正確時間應為」輸入欄位（選填、全類型可用、`wrong_time` 類型強調引導填寫）
- `ScheduleDiscrepancyPage.vue` 列表與詳細彈窗顯示「正確時間應為」（以對照格式呈現）
- `ScheduleDiscrepancyNotifier`：LINE 推播訊息加入「正確時間」一行（若有填）
- Feature Test 覆蓋分校隔離與正確時間兩項需求

### Out of Scope
- 「一鍵修正時段」功能（主任依 `corrected_time_range` 直接觸發 `reschedule-session`）—— 列入下一 Sprint
- `corrected_time_range` 的秒級精度（本次維持分鐘級 HH:MM）
- 其他 `discrepancy_type`（`student_no_show` / `wrong_student_list` …）的結構化欄位擴充
- 歷史回報 backfill（現有無 `corrected_time_range` 的舊 row 維持 null）
- 主任端 `updateStatus` 的 UI/API 改動

## 5. User Stories

### US-01：主任只看到自己分校的回報
> **As a** 分校主任，**I want** 在「課程回報管理」頁只看到屬於自己分校的老師回報，**so that** 我不會被其他分校的爭議訊息干擾，也避免非必要地看到別校學生姓名與時段。

Acceptance Criteria：
- [ ] 單一分校主任：列表只顯示 `branch_id = 自己分校` 的回報
- [ ] 多分校主任（例：跨校督導）：需明確選擇一個分校才載入對應資料；切換分校時重新載入
- [ ] 若主任硬改 URL 把 `branch_id` 改成別校，API 回 403（後端強制）
- [ ] super_admin（總部管理員）仍可不選分校時看到全站所有回報

### US-02：老師回報「時間不正確」可直接寫上正確時間
> **As a** 老師，**I want** 回報「上課時間有誤」時能直接填寫正確時間應為多少，**so that** 主任收到回報當下就看到完整資訊，不用再私訊問我。

Acceptance Criteria：
- [ ] 回報彈窗有「正確時間應為」輸入欄位（placeholder 顯示「例：14:00-16:00」）
- [ ] 選擇類型 `wrong_time`（上課時間有誤）時，該欄位以強調樣式顯示並自動聚焦
- [ ] 留空送出不會被阻擋（選填）
- [ ] 填寫非法格式（如「下午兩點」）送出時顯示 inline 錯誤訊息
- [ ] 成功送出後，主任端列表可看到該欄位

### US-03：主任一眼看出正確時間
> **As a** 主任，**I want** 在回報管理列表清楚看到「系統時段 vs 老師建議的正確時段」，**so that** 我不用點進去就能判斷下一步動作（修改時段 / 打電話確認）。

Acceptance Criteria：
- [ ] 列表時段欄若老師有填 `corrected_time_range`，顯示為「10:00-12:00 → 14:00-16:00」對照格式
- [ ] 原時段以 `text-muted` 色、正確時段以系統主色，中間箭頭 icon 分隔
- [ ] 若未填則僅顯示原時段（不要留空或顯示 —）
- [ ] LINE 通知訊息（若該分校有設定 staff 群組）同步包含「正確時間應為」一行

## 6. 功能需求（FR）

### FR-001：GET /schedule-discrepancies 對 director 強制單一分校 scope
系統應在 `GET /api/v1/schedule-discrepancies` 收到 `auth_role = 'director'` 的請求時，**強制回傳單一分校**的資料：
- 若 query 帶 `branch_id` 且該值屬於 `auth_campus_ids` → 使用該值
- 若 query 帶 `branch_id` 但不屬於 `auth_campus_ids` → 回 403
- 若 query 未帶 `branch_id` 且 `auth_campus_ids` 僅一筆 → 使用該單一分校（向下相容）
- 若 query 未帶 `branch_id` 且 `auth_campus_ids` 多筆 → 回 422 並附訊息「請指定分校（branch_id 必填）」

### FR-002：super_admin 跨校視野保留
系統應在 `auth_role = 'super_admin'` 的請求時，維持現行「不過濾 branch」行為；若該角色 query 帶 `branch_id`，僅做單一分校過濾（方便查特定校）。super_admin 不受 FR-001 的 422 規則影響。

### FR-003：schedule_discrepancies 新增 corrected_time_range 欄位
系統應於 `schedule_discrepancies` 資料表新增欄位 `corrected_time_range varchar(32) NULL`，位置緊接於現有 `time_range` 欄位之後，以 migration 新增並具備 `down()` 方法。

### FR-004：POST /schedule-discrepancies 接受 corrected_time_range
系統的 `POST /api/v1/schedule-discrepancies` 應接受 payload 欄位 `corrected_time_range`（選填、字串、最多 32 字元）。若提供：
- 必須符合 regex `/^\d{1,2}:\d{2}-\d{1,2}:\d{2}$/`
- 起始時間需早於結束時間（同日）
- 格式不符回 422 + 訊息「正確時間格式應為 HH:MM-HH:MM」

`GET /index`、`GET /mine`、`GET /active-for-session` response 對應 row 均需回傳此欄位。

### FR-005：ScheduleDiscrepancyNotifier LINE 訊息加入正確時間
系統的 `ScheduleDiscrepancyNotifier` 在組 LINE push message 時，若 `corrected_time_range` 非空，訊息內文新增一行「正確時間應為：{corrected_time_range}」，插入於現有「時段：{time_range}」下方。若為空則不顯示該行（避免誤導）。

### FR-006：ReportDiscrepancyModal 新增輸入欄位
系統的 `ReportDiscrepancyModal.vue` 應新增「正確時間應為」輸入欄位（type=text、placeholder 示範 HH:MM-HH:MM），位置緊接 `time_range` 下方。表單送出時：
- 若欄位非空 → 走 FR-004 的格式驗證（前端 inline 提示 + 後端二次驗證）
- 若欄位為空 → 不帶此欄位或帶 null；不阻擋送出
- 類型從其他值切換到 `wrong_time` 時自動聚焦

### FR-007：ScheduleDiscrepancyPage 顯示正確時間
系統的 `ScheduleDiscrepancyPage.vue` 列表時段欄應：
- `corrected_time_range` 有值時顯示為「原時段 → 正確時段」對照格式
- `corrected_time_range` 為空時顯示原時段（不顯示箭頭與空 placeholder）

若該頁有詳細彈窗（未來擴充），以獨立區塊「老師建議修正為」顯示。

### FR-008：ScheduleDiscrepancyPage 分校守門
系統的 `ScheduleDiscrepancyPage.vue` 應在 `currentBranch` 為空時**不呼叫 API**，而顯示「請先選擇分校」空狀態 + CTA；`currentBranch` 有值時永遠以該值作為 `branch_id` query 帶入。super_admin 視情境可提供「所有分校」模式（選擇 branch_id=0 或特殊選項，本次不新增 UI，維持跟隨 currentBranch 行為）。

## 7. 非功能需求（NFR）

- **效能**：新增 `corrected_time_range` 為輕量 varchar，對 list query 無額外 join；API p95 < 300ms（維持現行水準）
- **一致性**：分校隔離邏輯**必須在後端強制**；前端 guard 僅為 UX 強化，不得作為唯一防線
- **降級**：migration 失敗時（極少見，如 disk full），POST API 不能直接寫入新欄位；需確保 Controller 對「欄位不存在」情境回退為不寫入（以 `Schema::hasColumn` 判斷）
- **相容**：existing payload 未帶 `corrected_time_range` 的呼叫（含 mobile app、第三方整合）不得被破壞；欄位為選填
- **輸入安全**：`corrected_time_range` 為使用者輸入，儲存前 trim；顯示端 Vue template 預設 escape；後端 validation 用 regex 限制字元集，避免 XSS payload 進入 DB
- **回歸防護**：修改 `resolveCampusScope` 為高風險；必須有 Feature Test 涵蓋 director 單/多校、super_admin、跨校 403 四種路徑

### 架構選擇理由

**FR-001 分校隔離在後端強制**：選擇在 `resolveCampusScope` 內加入「director 多校需明確 branch_id」邏輯，而非前端強制，因為：
- 前端強制會被 DevTools 繞過（API JSON 仍可見他校）
- 後端強制符合「最小必要原則」與 PRD §9 資安要求
- 422 而非 silent fallback 讓呼叫方（前端）明確感知需補齊參數，避免長期隱性 bug

**FR-002 super_admin 保留跨校**：依使用者明確決策（問答選項 B）。此設計使「總部管理員」角色仍能用於跨校監督，不破壞現有工作流。實作上 `resolveCampusScope` 對 super_admin 保持 early return `[]`。

**FR-003 schema 擴充選擇 varchar 單欄位而非拆兩欄**：依使用者明確決策（問答選項「選填引導式」）。單欄位 `corrected_time_range` 與既有 `time_range` 格式一致（`HH:MM-HH:MM`），Migration 成本最低；若未來需要結構化解析（如自動觸發 reschedule-session），可在 Service 層做字串 parse，不需改 schema。

**FR-004 格式驗證採用 regex + 起訖順序檢查**：使用 Laravel validation rule `regex:/^\d{1,2}:\d{2}-\d{1,2}:\d{2}$/` 加 custom rule（或 controller 內一段 parse + compare）做起訖順序；不採用自訂 FormRequest class（現行 ScheduleDiscrepancyController 各 action 使用 inline `$request->validate()`，保持風格一致）。

**FR-008 前端分校 guard**：在 `ScheduleDiscrepancyPage.vue` 的 `onMounted` / `watch(currentBranch)` 加入「為空則不 fetch」短路；空狀態採用既有 empty-state 元件樣式。

## 9. 資安與存取控制

- **list API（FR-001）**：`role:director,teacher` + `require_campus`（既有）；本次加強為 director 強制單一分校 scope；teacher 的 `mine` / `active-for-session` 不受影響（已按 reporter_id 過濾）
- **cross-branch 防護**：`branch_id` 不屬於 `auth_campus_ids` → 403；不得回傳他校任何欄位
- **super_admin 例外**：經 PM 明確決策保留跨校視野（業務需求 > 最嚴資料最小化），以 audit log 補強（`updateStatus` 既有 audit 記錄 `acknowledged_by` / `resolved_by`）
- **輸入驗證（FR-004）**：`corrected_time_range` regex 限制為數字與冒號短槓；長度上限 32；無法注入 HTML/SQL payload
- **稽核 log**：`store` 既有記錄 `reporter_id`、`branch_id`、`created_at`；無需新增 log
- **PII**：回報內容含學生姓名（`student_name`），屬個人資料；分校隔離嚴格執行後，降低跨校主管非必要接觸的機會
- **STRIDE 快評**：
  - **Tampering**：偽造 `branch_id` 查詢他校 → FR-001 攔截 403
  - **Information Disclosure**：現行多校聚合為中風險，修正後降至低風險（super_admin 除外，屬設計接受）
  - **Spoofing / DoS / Elevation / Repudiation**：N/A（既有 auth 與 rate limit 不變）

## 11. 上線與維運

### 部署步驟
1. 後端程式碼合併
2. `php artisan migrate`（執行 `add_corrected_time_range_to_schedule_discrepancies` migration）—— 先於 opcache reset
3. 驗證 `schedule_discrepancies` 資料表已有 `corrected_time_range` 欄位（`php artisan tinker` 或 DB client）
4. `php artisan opcache:reset`
5. `cd frontend && npm run deploy`
6. 確認 `backend/public/index.html` 與 `assets/` chunk hash 同步
7. Smoke test：
   - 多校 director 登入 → 課程回報管理 → 確認不傳 `branch_id` 時回 422（DevTools Network）
   - 單校 director 登入 → 確認自動 scope 單一分校
   - super_admin 登入 → 確認仍可看全站
   - 老師登入 AttendancePage → 打開 ReportDiscrepancyModal → 選 `wrong_time` → 填正確時間送出 → 主任端看到對照格式

### 監控
- Laravel log：觀察 `schedule-discrepancies` 的 422 率，若初期升高代表前端未及時帶 `branch_id`
- DB：每週抽查 `corrected_time_range` 填寫率（`wrong_time` 類型比例）
- LINE 推播：確認 notifier 不因新欄位格式異常失敗

### 回滾方案
- **前端**：`git revert` 後重跑 `npm run deploy`；欄位後端仍存在但前端不顯示 / 不送出
- **後端 API**：`git revert` 後 `php artisan opcache:reset`；新 column 仍在 DB 但未被讀寫
- **Migration**：若需 rollback schema，執行 `php artisan migrate:rollback --step=1`（down() 會 drop 欄位）；但已存在資料會遺失，**不建議 rollback 除非欄位設計有致命錯誤**
- **分校隔離邏輯 revert**：director 回到多校聚合行為（低風險但與本 PRD 目標相悖）

## 13. 風險、假設、開放問題

### 風險

| 等級 | 描述 | 緩解方案 |
|---|---|---|
| 高 | FR-001 的 422 規則若遇到 production 中已有多校 director 但前端舊版本未帶 `branch_id`，會立即變 422 白屏 | 前端先部署（FR-008 guard + 強制帶 branch_id），後端再部署 422 規則；或後端保留 7 天的 softer fallback（log warning 但仍取 `auth_campus_ids[0]`）|
| 中 | `corrected_time_range` 的格式驗證若過嚴（如不允許 `14:00-16:00` 含空白 `14:00 - 16:00`）可能造成老師手機輸入挫折 | validation 前做 `trim` 與 `str_replace(' ', '', ...)` 寬容處理；regex 允許 `\s*` |
| 中 | Migration 在 production 執行時若 `schedule_discrepancies` 表資料量大（不太可能，目前為新 feature），`ALTER TABLE` 可能鎖表 | 該表屬新 feature 資料量小；仍建議於離峰時段部署 |
| 低 | super_admin 帳號可能被誤用來繞過分校隔離（社交工程） | 既有 super_admin 授予流程不變；本次僅重申 super_admin 為特權角色 |

### 假設
- 老師與主任均以 `AuthToken` 認證，`auth_role` 與 `auth_campus_ids` 來自 `AttachAuthUser` middleware（已驗證）
- 現行 `ScheduleDiscrepancyPage.vue` 的 `currentBranch` 來自 `App.vue` 全域狀態，切換分校會觸發 props 更新（已驗證）
- `schedule_discrepancies` 資料表目前資料量小（新 feature 於 §2026-04-18 上線），Migration 新增欄位成本極低
- 前端既有 ReportDiscrepancyModal 的 `time_range` 格式穩定為 `HH:MM-HH:MM`（無秒數），新 `corrected_time_range` 沿用此格式
- super_admin 使用者極少（≤ 3 位），業務流程上不會頻繁切換 `branch_id`
