# 待補點名無法請假修正計畫

## 問題結論
- 錯誤訊息來源是 [backend/app/Services/CourseLeaveCascadeService.php](backend/app/Services/CourseLeaveCascadeService.php) 的 `applyLeaveCascade()`；當目標日期找不到可請假堂次時會拋出「找不到可請假的堂次」。
- 「待補點名（已結束節次）」資料來源 [backend/app/Http/Controllers/AttendanceController.php](backend/app/Http/Controllers/AttendanceController.php) `endedSessions()` 目前僅排除 `attended/completed/late`，仍會把 `cancelled/leave_adjusted/leave` 這類不可再走一般請假順延的堂次帶給前端。
- 前端 [frontend/src/pages/AttendancePage.vue](frontend/src/pages/AttendancePage.vue) `submitMakeupMark()` 會對所有待補堂次都提供 `請假`，直接打 `POST /api/v1/attendance`，因此在不可請假堂次上必然失敗（與你截圖一致）。

## 修正策略（MVP）
- **後端先收斂候選集（主修）**
  - 在 `endedSessions()` 的查詢條件中，明確只回傳可補登且可操作狀態（以 `scheduled` 為主，排除 `leave/leave_adjusted/cancelled/attended/completed/late`）。
  - 回傳欄位加上 `session_status`（小寫標準化），讓前端可做顯示與防呆。
- **前端加二次防呆（保險）**
  - 在待補點名列，依 `session_status` 決定可選狀態；非可請假堂次移除或禁用 `請假` 選項。
  - 若後端回傳 422 且訊息為「找不到可請假的堂次」，改為更可理解提示：例如「此堂次已取消或已調整請假，請重新查詢清單」。
- **補上競態保護（避免清單過期）**
  - 使用者查詢後到按下「補登」前，堂次可能已被他人改狀態；對 409/422 的不可操作錯誤統一觸發清單 refresh，避免重複失敗。
- **避免影響既有補請假流程**
  - 保留 `retro-leave` 與 `leave-by-session` 既有入口，不改其商業邏輯；本次只修「待補點名候選集 + 前端操作防呆」。

## 實作步驟
1. 更新 [backend/app/Http/Controllers/AttendanceController.php](backend/app/Http/Controllers/AttendanceController.php)
   - 調整 `endedSessions()` `whereNotIn('Status', ...)` 條件為更精準白名單或黑名單。
   - 在 response transform 增加 `session_status`，並補註解說明「待補點名可操作條件」。
2. 更新 [frontend/src/pages/AttendancePage.vue](frontend/src/pages/AttendancePage.vue)
   - `fetchMakeupSessions()` 接收 `session_status`。
   - 調整「狀態」下拉可選值（至少對不可請假堂次禁用 `leave`）。
   - 優化 `submitMakeupMark()` 錯誤訊息對映，並在「堂次已不可操作」錯誤時自動刷新清單。
3. 補測試
   - 擴充 [backend/tests/Feature/MakeupAttendanceEndedSessionsTest.php](backend/tests/Feature/MakeupAttendanceEndedSessionsTest.php)：
     - 新增「`cancelled` 不應出現在 ended-sessions」。
     - 新增「`leave_adjusted` 不應出現在 ended-sessions」。
     - 新增「老師代課可見堂次」在新條件下仍可查到。
     - 保留「`scheduled` 且無有效 sign-in 應出現」現有行為。
4. 驗證
   - API 驗證：`GET /api/v1/attendance/ended-sessions` 確認不再回傳不可請假堂次。
   - UI 驗證：在待補點名選 `請假` 不再出現「找不到可請假的堂次」。
   - 回歸：確認一般到班/遲到/缺席補登與扣堂不受影響。

## 風險與注意事項
- 需避免過度過濾，導致本該可補登的 `scheduled` 堂次被排除。
- `leave` 是否要出現在待補點名需產品定義；若保留顯示，也必須前端禁止再送 `leave`。
- 老師代課可見範圍（`substitute` 邏輯）不可被條件調整誤傷，需保留既有 teacher scope。
- 多人同時操作下，清單與實際狀態可能不同步；需以「失敗後刷新」作為標準回復機制。

## QA 驗收測試計畫
### 驗收目標
- 待補點名清單只顯示可補登的堂次，避免使用者對不可請假堂次送出 `leave`。
- 在待補點名執行請假時，不再出現「補登失敗：找不到可請假的堂次」此類錯誤。
- 調整後不影響既有補登到班/遲到/缺席、補請假、代課可見性與分校權限。

### 測試範圍
- API：`GET /api/v1/attendance/ended-sessions`、`POST /api/v1/attendance`
- 前端頁面：[frontend/src/pages/AttendancePage.vue](frontend/src/pages/AttendancePage.vue)
- 後端邏輯：[backend/app/Http/Controllers/AttendanceController.php](backend/app/Http/Controllers/AttendanceController.php) 與 [backend/app/Services/CourseLeaveCascadeService.php](backend/app/Services/CourseLeaveCascadeService.php)

### 驗收案例（UAT）
1. 正常路徑（主任）
   - 前置：存在 `scheduled` 且已結束、尚未點名的堂次。
   - 步驟：待補點名查詢 → 將該筆改為 `請假` → 送出。
   - 預期：成功訊息顯示請假順延；該筆自清單移除；無「找不到可請假的堂次」。
2. 正常路徑（老師）
   - 前置：老師有自己課程的可補登堂次。
   - 步驟：以老師身份在待補點名執行 `present/late/absent/leave`。
   - 預期：各狀態可成功送出；只看得到授課/代課可見堂次。
3. 不可請假堂次不應入清單
   - 前置：建立 `cancelled`、`leave_adjusted`、`leave`、`attended` 堂次且已結束。
   - 步驟：查詢待補點名。
   - 預期：上述堂次不出現在清單中。
4. 競態案例（清單過期）
   - 前置：A 使用者查到可補登堂次；B 使用者先把同堂次改成不可補登狀態。
   - 步驟：A 直接送出 `leave`。
   - 預期：前端顯示可理解錯誤並自動刷新清單；過期堂次不再顯示。
5. 權限與分校隔離
   - 前置：使用者僅有分校 X 權限，另有分校 Y 資料。
   - 步驟：以 `branch_id=Y` 查詢 ended-sessions 或送補登。
   - 預期：回傳 403/禁止；不洩漏他校資料。

### API 驗收檢核點
- `ended-sessions` 回傳 `data[]` 每筆含 `session_status`，且狀態值符合白名單規則。
- `POST /attendance` 送 `leave` 時，僅在可請假堂次成功；不可操作時回傳明確錯誤。
- 錯誤碼一致性：權限錯誤 403、資料不可操作 422、重複點名 409。

### 回歸測試清單
- 待補點名 `present/late/absent` 送出與扣堂邏輯正常。
- `retro-leave` 與 `leave-by-session` 流程不受影響。
- 老師代課（substitute）堂次仍可被 `ended-sessions` 正確查出。
- 既有 Feature 測試 [backend/tests/Feature/MakeupAttendanceEndedSessionsTest.php](backend/tests/Feature/MakeupAttendanceEndedSessionsTest.php) 全綠，且新增案例通過。

### 驗收通過標準（Definition of Done）
- 使用者在待補點名操作請假，不再重現截圖錯誤訊息。
- QA 案例 1~5 全通過。
- 相關自動化測試與新增回歸測試通過。
- 權限、分校隔離、代課可見性無回歸問題。
