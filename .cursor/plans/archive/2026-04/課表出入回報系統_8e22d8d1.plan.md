---

## 2. 目標與業務背景

**現在的痛點**

主任負責在系統中維護學生課程與排課（ClassSession）。當課程臨時調課、改時段、換學生時，主任慣用 LINE 或紙本記錄，但往往沒有同步更新系統。老師上課前開出缺勤頁確認今日課表時，系統顯示的學生名單、上課時間與現場實際情況常常不符，導致：

- 系統有課，但學生沒來（主任已取消，但未在系統刪除）
- 學生到場，但系統找不到對應堂次（無法正常點名）
- 系統時段與實際上課時間不同
- 學生名單錯誤

老師目前只能用 LINE 或電話聯絡主任確認，缺乏正式的系統內回報管道，主任也沒有集中的待辦清單可追蹤未修正的課表問題。

**解決後的業務價值**

- 老師遇到出入時有標準化、可存檔的回報方式
- 主任有集中的待辦清單，知道哪些課表資料需要補正
- 問題處理有記錄，可追溯與統計出入頻率，長期幫助主任改善排課習慣

**成功指標（KPI）**

- 上線後 30 天內，課表出入回報單使用率 ≥ 70%（有出入當天老師填單 vs. 僅用 LINE 反映）
- 主任平均處理（acknowledged）回報單時間 < 24 小時
- 老師問卷：「點名時課表正確率」月度滿意度提升 ≥ 20%

---

## 3. 範圍

**In Scope**

- 出缺勤頁（`AttendancePage.vue`）：每筆堂次旁新增「回報出入」按鈕與填表流程
- 出缺勤頁：新增「此課不在系統中」快捷回報（無對應 ClassSession 時使用）
- 主任儀表板（`DirectorDashboard.vue`）：新增「課表回報待處理」摘要區塊
- 新增獨立「課表回報管理」頁（主任專用）：列表、篩選、處理
- 後端新增 `schedule_discrepancies` 資料表與 CRUD API
- LINE 通知：新回報送出時推播給主任（使用 LINE Messaging API push message，取代已於 2025/03/31 停服的 LINE Notify）

**Out of Scope**

- 不改動現有排課（SmartCalendar）、課程管理（CourseManagement）的操作流程
- 不自動更新 ClassSession 資料（主任仍手動修正；此功能只是「通知管道」）
- 不限制主任必須填寫課程才能儲存（改變主任操作習慣超出本次範圍）
- 家長端不開放回報
- 行動 App 原生推播（非 LINE 通知）

## 5. User Stories

**US-01（老師 - 有堂次但課表與實際不符）**

> **As a** 老師，**I want** 在出缺勤頁每筆堂次旁點擊「回報出入」，填寫出入類型與說明，**so that** 主任能即時收到通知並修正系統資料，我無需再用 LINE 個別聯絡。

Acceptance Criteria：
- [ ] 出缺勤頁每筆「已排課」堂次卡片右下角有「回報出入」按鈕（icon + 文字標籤）
- [ ] 點擊後展開填表 modal：出入類型（單選）＋備註（選填，最多 200 字）
- [ ] 出入類型選項：學生未到場、學生名單有誤、上課時間有誤、課程已取消、其他
- [ ] 送出後顯示成功 toast，堂次卡片出現「已回報」橘色 badge
- [ ] 同一堂次已回報且待處理時，再次點擊「回報出入」按鈕顯示現有回報內容（唯讀）而非重複建立

**US-02（老師 - 學生到場但系統無堂次）**

> **As a** 老師，**I want** 在出缺勤頁有一個「此課不在系統中」快捷入口，**so that** 我可以描述現場實際有課但系統找不到的情形，讓主任知道需要補建堂次。

Acceptance Criteria：
- [ ] 出缺勤頁「今日待點名」區底部有固定「有課不在列表中？點此回報」連結
- [ ] 點擊後展開 modal：科目（下拉）、學生姓名（文字輸入）、時段（時間選擇器）、備註
- [ ] 回報不綁定任何 ClassSession（`class_session_id` 為 null）
- [ ] 送出成功後 toast 通知，主任端收到同一待辦

**US-03（主任 - 查看與處理回報）**

> **As a** 主任，**I want** 在儀表板看到待處理的課表出入回報清單，並可標記已確認／已修正，**so that** 我知道哪些系統資料需要補正，且老師能看到我已收到。

Acceptance Criteria：
- [ ] 主任儀表板出現「課表回報」卡片，顯示「N 筆待處理」，點擊跳轉管理頁
- [ ] 管理頁列出所有回報，欄位：回報時間、老師、分校、學生、堂次資訊、類型、備註、狀態
- [ ] 狀態流程：`pending` → `acknowledged`（主任已看到）→ `resolved`（已修正系統）
- [ ] 主任可在列表行內展開備註欄並填寫「處理說明」
- [ ] `resolved` 後該回報移至「已處理」tab
- [ ] 老師在「已回報」badge 點擊後可看到主任填的處理說明

**US-04（主任 - LINE 通知）**

> **As a** 主任，**I want** 每次老師送出新回報時收到 LINE 通知，**so that** 即使我不在系統前也能第一時間知道。

Acceptance Criteria：
- [ ] 送出回報時，後端觸發 LINE Messaging API push message，推播至對應分校的 LINE 群組（所有主任/admin 同收）
- [ ] 通知格式：「[分校名] 老師姓名 回報課表出入：出入類型 / 學生 / 時段 → 請至系統處理」
- [ ] LINE Messaging API 呼叫失敗不影響回報送出主流程（async queue 降級）
- [ ] 若分校尚未設定 LINE 群組 token，靜默跳過（不 error）

> **技術背景**：LINE Notify 已於 2025/03/31 終止服務。本功能改用 LINE Messaging API（Push Message），以分校 LINE 群組 token 發送；群組需預先加入官方帳號。系統 `Campus` 表已有 `Client_ID` / `Client_Secret` 欄位可擴充儲存群組 channel token。

## 6. 功能需求（FR）

- **FR-001**：系統應在出缺勤頁每筆 `status=scheduled` 的堂次卡片上提供「回報出入」按鈕。
- **FR-002**：老師點擊「回報出入」後，系統應展示含出入類型（必填）與備註（選填，≤200 字）的 modal；送出成功後後端建立一筆 `schedule_discrepancies` 記錄（`status=pending`）。
- **FR-003**：同一 `class_session_id` 已有 `pending` 或 `acknowledged` 狀態的回報時，老師再次點擊「回報出入」，系統應顯示現有回報內容（唯讀），不得重複建立新記錄。
- **FR-004**：出缺勤頁底部應固定顯示「有課不在列表中？點此回報」入口；點擊後展示 modal 讓老師填入科目、學生姓名、時段與備註，送出後建立 `class_session_id=null` 的回報記錄。
- **FR-005**：老師送出回報後，系統應透過 LINE Messaging API 推播 push message 至對應分校 LINE 群組；呼叫失敗不得阻斷回報建立（async queue 降級，retry 3 次後記 log）。
- **FR-011**：老師可對自己建立、尚未被主任 `acknowledged` 的回報執行「撤銷」操作，系統將狀態改為 `withdrawn`（軟取消）而非實際刪除，保留稽核記錄；`acknowledged` 或 `resolved` 狀態的回報不得被老師撤銷。
- **FR-006**：主任儀表板應顯示「課表回報」卡片，呈現 `pending` 回報數量；點擊跳轉管理頁。
- **FR-007**：主任管理頁應列出本分校所有回報，支援依狀態（pending / acknowledged / resolved）篩選，並支援依回報日期排序。
- **FR-008**：主任可將回報狀態從 `pending` 更新為 `acknowledged`（已看到），或從 `acknowledged` 更新為 `resolved`（已修正），後者需填寫處理說明（≥10 字）。
- **FR-009**：老師在出缺勤頁「已回報」badge 點擊後，系統應展示該回報的目前狀態與主任填寫的處理說明（resolved 後可見）。
- **FR-010**：主任管理頁應顯示每筆回報的回報老師、分校、堂次資訊（科目、學生、時段）、出入類型、備註與狀態歷程。

## 7. 非功能需求（NFR）

- **效能**：`POST /api/v1/schedule-discrepancies` 回應時間 < 500ms（P95）；管理頁列表 API < 800ms（含分頁，每頁 20 筆）
- **可靠性**：LINE Messaging API 呼叫採 async job（queue），失敗後 retry 3 次，retry 失敗記 log，不影響主流程；LINE Notify 已停服（2025/03/31），禁止使用
- **資料保留**：`resolved` / `withdrawn` 狀態的回報自動於 **12 個月後**封存（`archived_at` 欄位標記）；封存後仍可查詢但不計入儀表板數量；永久刪除需 IT 手動執行
- **可用性**：功能不影響現有出缺勤點名流程；老師端不得因此功能新增必要操作步驟（點名仍可不填回報）
- **降級策略**：若 `schedule_discrepancies` 表查詢逾時，出缺勤頁仍正常載入（回報功能 fallback 隱藏，不崩潰整頁）

## 8. 技術方向（給 CTO）

**新增資料表**

- `schedule_discrepancies`：`id`, `class_session_id`（nullable，外鍵 `ClassSession.id`）, `reporter_id`（外鍵 `User.id`）, `branch_id`（外鍵 `Campus.id`）, `discrepancy_type` (enum)、`notes` (text nullable)、`session_date`、`subject`、`student_name`（用於 session_id=null 的自由填寫情境）、`status` (pending / acknowledged / resolved / withdrawn)、`withdrawn_at`、`acknowledged_by`、`acknowledged_at`、`resolved_by`、`resolved_at`、`resolution_note`、`archived_at`（12 個月封存時間戳）、`created_at`、`updated_at`
- 需新增 migration
- 新增 `line_group_tokens` 欄位至 `Campus` 表（或獨立 `campus_line_settings` 表），儲存 LINE Messaging API channel token（取代已廢棄的 `LineNotifyID`）

**受影響頁面**

- `frontend/src/pages/AttendancePage.vue`（老師回報入口）
- `frontend/src/pages/DirectorDashboard.vue`（主任摘要卡片）
- 新增 `frontend/src/pages/ScheduleDiscrepancyPage.vue`（主任管理頁）

**新增 API 端點**

- `POST /api/v1/schedule-discrepancies`（老師建立回報）
- `GET /api/v1/schedule-discrepancies`（主任列表，含分頁與篩選）
- `GET /api/v1/schedule-discrepancies/my`（老師查詢自己的回報）
- `PUT /api/v1/schedule-discrepancies/{id}`（主任更新狀態）

**架構選擇理由**

- 獨立資料表（不污染 ClassSession / schedules）：回報是「通訊記錄」而非「課表資料」，兩者語意不同
- 軟取消（`withdrawn`）而非硬刪除：對齊 Linear / Zendesk 業界標準，保留稽核軌跡；主任仍可查閱已撤銷的回報歷程
- 12 個月自動封存（`archived_at`）：對齊 EdTech SaaS 資料最小化原則，避免無期限保留 PII，同時保持可追溯性
- 非即時推播（LINE Messaging API queue）：LINE Notify 已於 2025/03/31 停服；改用 LINE Messaging API Push Message 至分校 LINE 群組，群組 token 儲存於 `Campus` 設定；同分校多位主任自動同收，無需個別路由
- 不設計回報自動修正課表：保持主任的系統修改主動權，避免非受控的自動化資料變更

**子任務 Agent 派發**

## 9. 資安與存取控制

| 項目 | 規格 |
|---|---|
| **回報建立** | 僅 `teacher` / `admin` / `director` 角色可 `POST`；後端從 token 取 `reporter_id`，前端不可傳入 |
| **回報列表** | `GET /schedule-discrepancies`：`director`/`admin`/`super_admin` 可見；自動以 `require_campus` middleware 限制分校範圍，主任只見本校回報 |
| **我的回報** | `GET /schedule-discrepancies/my`：teacher 只見自己建立的回報 |
| **狀態更新** | `PUT /schedule-discrepancies/{id}`：僅 `director`/`admin`/`super_admin` 可操作 |
| **PII** | `student_name`（自由填寫欄）屬 PII；回應中不得曝露超出必要範圍的學生資料；`resolution_note` 亦需 scope 保護 |
| **稽核 log** | `acknowledged`、`resolved` 狀態變更需記錄操作者 id 與時間戳（`acknowledged_by`、`resolved_by`） |
| **STRIDE 快評** | Spoofing：token 驗證已有；Tampering：`reporter_id` 由後端注入，前端不可覆寫；Info Disclosure：`require_campus` 防跨校讀取；Denial of Service：單一老師每日每堂次最多 1 筆回報（FR-003 guard）已防止洗版 |

## 10. QA 驗收標準與測試計畫

### FR-001 / FR-002（建立回報）

- Happy Path：老師點擊「回報出入」→ 選擇類型 → 填備註 → 送出 → DB 有新紀錄、老師看到成功 toast 與橘色 badge
- Edge Case：備註剛好 200 字可送出；201 字按鈕 disabled
- Error Case：網路中斷送出 → inline 錯誤訊息「送出失敗，請稍後再試」；服務端 500 → 同上

### FR-003（重複回報防護）

- Happy Path：同堂次已有 pending 回報 → 再點「回報出入」顯示現有內容（唯讀），無新記錄產生
- Edge Case：已有 resolved 回報的同堂次 → 可建立新回報（前一個已結案）

### FR-004（無堂次回報）

- Happy Path：今日無任何排課 → 連結仍顯示 → 填表送出成功
- Edge Case：未填科目送出 → 按鈕 disabled

### FR-005（LINE 通知）

- Happy Path：送出回報後 queue job 執行、對應分校 LINE 群組收到 push message
- Error Case：LINE Messaging API 返回 4xx/5xx → job retry 3 次後記 log，回報記錄狀態不受影響
- Edge Case：分校未設定 LINE 群組 token → 靜默跳過，不 error，log 一筆 warning

### FR-011（老師撤銷回報）

- Happy Path：老師對 `pending` 回報點擊「撤銷」→ 二次確認 → 狀態改為 `withdrawn` → 堂次卡片 badge 消除
- Edge Case：`acknowledged` 狀態 → 撤銷按鈕不顯示
- Error Case：並發（老師撤銷與主任同時 acknowledged）→ 後端以 status check 拒絕，回傳 409，前端顯示「主任已確認，無法撤銷」

### FR-006 ~ FR-010（主任端）

- Happy Path：pending 回報出現在儀表板 badge → 點進管理頁 → 標記 acknowledged → 填處理說明 → 標記 resolved → 移至已解決 tab
- Edge Case：處理說明 9 字 → 「已修正」按鈕仍 disabled；10 字解鎖
- Error Case：主任操作他校回報（URL 猜測）→ 後端 403

## 11. 上線與維運

**部署步驟**

1. 後端執行 `php artisan migrate`（新增 `schedule_discrepancies` 表；`Campus` 表新增 LINE Messaging API token 欄位）
2. 各分校主任至 LINE Developers 建立 Messaging API channel，將 channel token 填入系統 Campus 設定；並將官方帳號加入分校 LINE 群組
3. 確認 queue worker 在 Raspberry Pi 上持續運行（`php artisan queue:work`）
4. 設定 Laravel Scheduler 執行每月封存 job（`php artisan schedule:run` 加入 cron）
5. 前端 `cd frontend && npm run deploy`（build + copy 至 backend/public）
6. 確認 `GET /api/v1/schedule-discrepancies` 回傳 200（health check）

**監控新增**

- queue failed jobs 監控：LINE Messaging API job 失敗率 > 10% 需告警（LINE Notify 已停服，禁止繼續使用）
- 封存 job 每月執行確認：檢查 `archived_at` 標記是否正常寫入

**回滾方案**

- 若部署後出缺勤頁出現異常，回滾前端 build（還原 backend/public 靜態檔）
- `schedule_discrepancies` 表為新表，回滾不影響現有資料；可 `php artisan migrate:rollback --step=1`

## 13. 風險、假設、開放問題

**風險**

- 高｜老師習慣用 LINE 而不用系統回報，採用率低
  - 業界研究（2025 Scientific Reports）顯示：63% 教師工具導入前有疑慮，但試用超過一個月後 71% 回報省時；關鍵障礙是「低風險試用機會不足」而非工具品質。
  - 緩解策略（ADKAR 框架）：**A**wareness—上線前由主任在老師群組說明「為什麼要改用系統」，強調 LINE 回報主任容易漏掉的痛點；**D**esire—入口設計為一鍵填完（≤ 30 秒），不增加額外負擔；**K**nowledge—首次打開時附帶 tooltip 引導；**A**bility—首週由主任主動詢問「有出入嗎？記得在系統填單」；**R**einforcement—主任儀表板的處理說明讓老師看到有回應，形成正向回饋。
  - 早期採用者策略：目標第 1 個月達到 16–18% 使用率門檻，之後口碑傳播自然加速。

- 高｜**LINE Notify 已於 2025/03/31 永久停服**，不可再用
  - 緩解：本 PRD 已改用 LINE Messaging API Push Message；系統 `Campus` 表需新增群組 channel token 欄位；IT 須協助各分校完成 LINE 官方帳號設定與群組綁定（見第 11 節部署步驟 2）。
  - 若分校尚未完成設定：LINE 通知靜默跳過，系統儀表板仍為主要收件管道（不影響核心功能）。

- 中｜LINE Messaging API 免費方案每月僅 200 則訊息；若分校回報量高可能超額
  - 緩解：NT$800/月升至 3,000 則；每筆回報才一則通知，四間分校月均 200 則以內風險低；超額時自動降級（不發通知但 log 記錄），主任改從儀表板收件。

- 低｜回報量過大造成主任管理頁效能問題
  - 緩解：分頁（每頁 20 筆）＋複合索引 `(branch_id, status, created_at)`；12 個月封存機制自動縮減活躍資料量。

**假設**

- 每間分校主任願意在上線期間完成 LINE Messaging API channel 設定（約 30 分鐘/校，IT 可協助）
- `require_campus` middleware 已正確限制分校範圍（現有機制）
- 主任每天至少登入系統一次查看儀表板（LINE 通知為輔助，非主要依賴）
- Laravel Scheduler（cron）已在 Raspberry Pi 上啟用，以執行月度封存 job

**開放問題（已依業界標準給出建議答案，供 PM 最終確認）**

- `[建議已定：軟取消]` 老師能否刪除自己未處理的回報？
  - 業界標準（Linear、Zendesk）：允許「軟取消 / withdraw」而非硬刪除，保留稽核軌跡。本 PRD 已採用此方案（FR-011，`withdrawn` 狀態）。主任仍可查閱撤銷記錄，老師無法永久刪除。若業務需要允許硬刪除，需 PM 書面確認後另開規格。

- `[建議已定：12 個月封存]` 回報記錄保留多久？
  - 業界標準（EdTech SaaS 資料保留最佳實踐）：`resolved`/`withdrawn` 狀態的回報於 **12 個月後**自動封存（`archived_at` 標記），封存後從儀表板隱藏但仍可供 IT 查詢稽核；永久刪除由 IT 手動決定。此設計兼顧資料最小化原則與稽核需求。若需縮短至 6 個月或延長至 2 年，請 PM 確認後調整封存 job 參數。

- `[建議已定：群組同收]` 多位主任（同分校）收到 LINE 通知時，是否都要收？
  - 業界標準（LINE Messaging API 最佳實踐）：同分校所有主任/admin 加入同一個 LINE 群組，系統發一則通知至群組，所有成員同收，無需個別路由；最簡單且最不容易漏。若需「只通知特定主任」，需在 `Campus` 設定中指定接收者 User ID 並改用 multicast API，複雜度較高，建議 v2 再議。
