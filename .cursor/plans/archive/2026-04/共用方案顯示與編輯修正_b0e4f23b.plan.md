## 2. 目標與業務背景

**痛點 A：共用方案「購買堂數」顯示方案總堂數而非個別分配堂數**

主任反映：「總繳堂數是 12 堂分 2 科，之前系統只有出現 6 堂 + 6 堂，現在一科是顯示 12 堂。」

根因：`StudentClassController.php` L372 的 package override block 用 `$pkg->total_sessions`（12）覆蓋了個別課程的 `sessions_purchased`，而個別課程的 `SessionCount` 本為 6。progress bar 的分子（`used_sessions`）與分母（`sessions_purchased`）均為方案層級總量，無法反映每科個別進度。

**痛點 A'：大直主任多科方案剩餘堂數仍顯示 0**

前次 PRD 已修復方案池過扣問題（rebuild-ledger），但所有科目仍顯示「0（方案共用）」。根因即為痛點 A 的 override block 將 `remaining_sessions` 強制設為 `pkg->remaining_sessions`（方案池 = 0），完全遮蔽了個別科目的實際剩餘。移除 override 後，`remaining_sessions` 改由 `batchObservedUsedSessions`（per-`StudentClass` 獨立計算，不跨科彙總）計算，結果為：
- 理化（已上 8 堂 / 分配 6 堂）→ `remaining = max(0, 6-8) = 0`（合理：超過分配）
- 數學/自然（已上 5 堂 / 分配 6 堂）→ `remaining = 1`（合理：還剩 1 堂）

此為痛點 A 的直接連鎖效應；FR-001 + FR-011 一起解決。

**痛點 B：編輯表單載入錯誤值，存檔後靜默覆蓋 SessionCount**

行政開啟「編輯課程」時，`CourseEditForm` 的「購買堂數」預填自 `course.sessions_purchased`（已被 API 覆蓋為 12）。未修改直接儲存 → 後端寫入 `SessionCount=12`，永久覆蓋個別分配的 6 堂，無任何警告。若此情況已發生，FR-001 修正後顯示值雖正確但 `SessionCount` DB 欄位仍為 12，需 FR-011 資料修復還原。

**痛點 C：課程編輯表單 UX 混亂**

現有「編輯課程」modal 為扁平 2-column grid，16 個欄位無分組、無情境標頭（不知在編輯哪位學生的課）、驗證只靠 `alert()`、存檔成功/失敗反饋不一致，課程管理與學生管理頁的 PUT payload 也有差異。行政反映整筆契約編輯「很亂」，需全面改善。

**業務價值**

- 行政與主任能準確看到每科個別剩餘堂數，不被方案總堂數混淆。
- 編輯表單對方案課程加上唯讀保護，杜絕靜默覆蓋 SessionCount。
- 分組後的表單結構清晰，行政能快速找到目標欄位、減少填表失誤。
- 行內驗證與 toast 取代 alert()，符合現代 SaaS 操作習慣，降低錯誤率。

**成功指標（KPI）**

- 方案課程「購買 N 堂」= 個別 `SessionCount`（6），不是 `total_sessions`（12）。
- 大直主任各科剩餘堂數按個別科目正確顯示（不再全部顯示 0）。
- 編輯方案課程存檔後 DB 的 `SessionCount` 不改變。
- 表單驗證失敗以行內紅字提示，`alert()` 呼叫數 = 0。
- 存檔成功後以 toast 通知，無頁面 reload / blocking alert。

## 5. User Stories

**Story 1 — 方案課程購買堂數正確顯示（行政）**

> **As a** 行政人員，**I want** 在課程管理與學生管理頁看到每科方案課程的個別購買堂數（如 6 堂），**so that** 我能正確判斷每科還剩多少堂，不會被方案總堂數混淆。

Acceptance Criteria：
- [ ] 方案課程「購買堂數」顯示個別 `SessionCount`（6），不是 `pkg->total_sessions`（12）。
- [ ] mini-progress bar 進度反映個別科目已上/購買比例。
- [ ] 方案共用池資訊以「方案池 X / Y」小字輔助顯示。

**Story 2 — 編輯課程表單清楚、安全且易操作（行政）**

> **As a** 行政人員，**I want** 編輯課程時看到清楚分組的表單、正確的情境資訊，以及即時的欄位驗證提示，**so that** 我能快速找到目標欄位、不誤改關鍵設定，並對存檔結果一目瞭然。

Acceptance Criteria：
- [ ] 表單標頭顯示正在編輯的學生姓名與科目，不只是「編輯課程」。
- [ ] 表單欄位分為「課程基本資訊」、「費用與繳費」、「排課時段」三個具名區塊。
- [ ] 必填欄位標有 `*`；未填時欄位下方顯示紅色說明文字，不跳出 alert。
- [ ] 存檔成功後顯示 toast 通知，不跳出 alert 也不自動 reload。
- [ ] 方案課程顯示方案 banner，「購買堂數」為唯讀。

## 6. 功能需求（FR）

- **FR-001**：`StudentClassController.php` GET index，package override block（L364–374）：移除對 `sessions_purchased`、`sessions_used`、`remaining_sessions`、`RemainingSessions`、`UsedSessions` 的覆蓋；改為只注入三個輔助欄位：`package_remaining_sessions`、`package_total_sessions`、`package_used_sessions`。個別課程計數繼續由 L352–364 的原有邏輯（`SessionCount - observedUsedSessions`）決定。
- **FR-002**：`StudentClassController.php` `update()` 方法：`isPartOfPackage()` 為 true 時，`unset($mappedData['RemainingSessions'])`，防止直接覆寫 ledger 驅動的剩餘值。`SessionCount` 仍允許修改。
- **FR-003**：`StudentsList.vue` 展開課程表格（L242–253）：mini-progress bar 使用 `course.used_sessions / course.sessions_purchased`（均為個別課程值）；在「（方案共用）」tag 後新增 `v-if="course.package_total_sessions"` 保護的「方案池 X / Y」小字提示。
- **FR-004**：`CourseEditForm.vue`：新增 `packageInfo` prop（`Object | null`，預設 `null`）；`packageInfo` 非空時：(1) 顯示方案 info banner（方案名稱 + 共用池剩餘/總量）；(2) 「購買堂數」input 加 `disabled` + 說明文字；(3) `showRemaining` 對方案課程強制 `false`。
- **FR-005**：`StudentsList.vue` `editCourse()` 與 `CourseManagement.vue` `editCourse()`：組建 `packageInfo`（`course.PackageID ? { id, name, total_sessions: course.package_total_sessions, remaining_sessions: course.package_remaining_sessions } : null`）及 `contextTitle`（`課程 / 學生姓名`）傳入 `CourseEditForm`。
- **FR-006**：`CourseManagement.vue` `submitEdit()`：`editingCourse.PackageID` 存在時，從 PUT body 移除 `remaining_sessions` 鍵。
- **FR-007**：`CourseEditForm.vue`：新增 `contextTitle` prop（String，預設 `''`）；當非空時在表單頂部（或方案 banner 上方）以 `<p class="edit-context-title">` 顯示（樣式：灰色小字，如「正在編輯：數學 ／ 王小明」）。
- **FR-008**：`CourseEditForm.vue` 表單重構——將現有扁平 2-column grid 重組為三個 `<section>` 區塊，每個區塊有 `<h4>` 小標題：
  - **課程基本資訊**：科目、老師、開課日、類型、上課地點
  - **費用與繳費**：費用、時長、繳費方式、購買堂數/結算日/每月堂數（條件顯示）、繳費日期、剩餘堂數
  - **排課時段**：固定排課日（pill toggles）、每日時段列表、備註
- **FR-009**：`CourseEditForm.vue`（行內驗證規則）+ `CourseManagement.vue` `submitEdit()`（呼叫驗證後才送出）：
  - 必填欄位（科目、老師）標 `*` 並加 `required` 邏輯；未填時該欄位 border 轉紅、欄位下方顯示 `<span class="field-error">科目為必填</span>`。
  - `payment_type=monthly` 且 `settlement_day` 為空時，`settlement_day` 欄位顯示 `「月結方式需設定結算日」`。
  - 「儲存」按鈕在 `hasErrors` computed 為 true 時 `disabled`。
  - `CourseManagement.vue` `submitEdit()` 移除 `alert()` 錯誤提示，改為觸發表單驗證顯示行內錯誤。
- **FR-010**：`CourseManagement.vue` 與 `StudentsList.vue`：存檔成功後改用現有 `ToastWithUndo.vue` 元件（已在 `CourseManagement.vue` 引入）顯示 success/error toast；移除 `alert('儲存成功')` / `alert('儲存失敗')` 呼叫。`ToastWithUndo` 已支援 message + type；存檔成功呼叫 `showToast({ message: '已儲存', type: 'success' })`，失敗呼叫 `showToast({ message: '儲存失敗', type: 'error' })`。`StudentsList.vue` 若未引入 `ToastWithUndo`，在此 FR 中補充引入。

  1. **動作分群**：在下拉選單內加入 `<p class="action-section-label">` 小標題，將動作分為三群：「日常操作」（編輯、+ 新增堂次、加購堂數 / 續報加購、換師複製）、「狀態管理」（暫停課程 / 恢復課程、結案（不續報））、「危險操作」（刪除課程）；現有 `<hr>` 只剩危險操作前保留，移除其他位置的孤立分隔線。
  2. **動作排序**：「編輯」移至第一位（最高頻操作置頂，GitHub / Linear 模式）。
  3. **每個動作加前置 icon**：以 Unicode 字元 or 簡單 SVG span 為每項加入 icon（`✏️` 編輯、`+` 新增堂次、`⚡` 加購/續報、`⏸` 暫停、`▶` 恢復、`✓` 結案、`📋` 換師複製、`🗑` 刪除），讓用戶掃描而非逐字閱讀（Nielsen's recognition over recall）。
- **FR-013**：`CourseManagement.vue` 刪除課程改用行內 ConfirmModal（Stripe / GitHub 模式）：
  - 移除 `window.confirm()`，改為在 `CourseManagement.vue` 內新增輕量行內確認 modal（不建立獨立元件檔案，使用現有 `modal-overlay` + `modal-box` pattern）。

  - `deleteCourse` 改為先設 `confirmDeleteTarget = c`（顯示 modal），用戶點「確認刪除」後才執行原有 API 刪除邏輯。

## 8. 技術方向（給 CTO）

**架構審查關鍵發現（架構師審查後補充）**

1. **FR-001 移除 override 安全性確認**：`batchObservedUsedSessions`（`SessionDeductionService::batchObservedUsedSessions`）以 per-`StudentClass` ID 獨立計算每科的已上堂數（max of sign-in deductions / ClassSession attended/completed/late / orphan approved LRs），不跨方案成員彙總。因此移除 override 後，`remaining_sessions = SessionCount - min(SessionCount, observed)` 能正確反映每科個別剩餘，兩科互不干擾。

2. **`ToastWithUndo.vue` 已存在**：`CourseManagement.vue` 已引入此元件；FR-010 直接複用，不需新建 `useToast.js`。`StudentsList.vue` 補充引入即可。

3. **FR-001 的前提：`SessionCount` 可能已損壞**：override bug 存在期間，任何行政開啟 edit 表單並儲存（即使未修改），都會將 `SessionCount` 改為 `pkg->total_sessions`（12）。若不修復，FR-001 後顯示的 `sessions_purchased` 仍是 12，剩餘計算為 `12 - observed`（錯誤）。FR-011 必須在 FR-001 部署後立即執行。

4. **`CourseEditForm.vue` 重構安全性確認**：深層 `watch(form, ...)` watcher 監聽整個 `form` reactive object 而非 DOM 結構；加 `<section>` 包覆不影響 emit chain。`span-full` 的 CSS grid 重構需確保新的 section 容器不破壞 CSS grid flow（建議 section 本身用 `display: contents` 或各 section 各自定義 `display: grid`）。

**受影響後端**

**受影響前端**

**架構選擇理由**

- **三區塊分組（Stripe / Salesforce 模式）**：Stripe 的 billing subscription 編輯頁用「Plan」「Pricing」「Payment」三區塊；Salesforce Contract edit 用「Billing Information」「Shipping Information」「Additional Information」—— 分組讓使用者在心智模型下快速找到目標欄位，不需逐行掃描。本系統三塊對應「是什麼課 / 怎麼收費 / 什麼時候上」，直覺且完整。
- **contextTitle 情境標頭（HubSpot / Linear 模式）**：HubSpot Deal 編輯 modal 標頭顯示 deal name；Linear issue sidebar 顯示 issue title + project。行政同時管理多位學生，標頭只有「編輯課程」時容易在多個 modal 間迷失；加上「數學 ／ 王小明」立即消除歧義。
- **行內驗證 disabled 按鈕（Shopify / GitHub 模式）**：Shopify 的 product form 在 required 欄位未填時 Save 按鈕 disabled + 欄位下方紅字；GitHub 的 PR creation 同樣在缺必填時 disable submit。相較 `alert()`，行內驗證不阻斷操作流程，符合 Nielsen 的「讓使用者保持掌控感」原則。
- **非阻擋式 toast（Stripe / Zendesk 模式）**：Stripe Dashboard 存檔後右下角出現 3 秒 toast；Zendesk 同樣使用 non-blocking snackbar。`alert()` 是模態對話框，強迫使用者點擊確認，打斷心流；toast 讓使用者在看到結果的同時繼續操作。
- **packageInfo prop 注入（Salesforce read-only protected field 模式）**：Salesforce 對 lookup / formula fields 顯示鎖頭圖示與 tooltip 說明唯讀原因。`CourseEditForm` 收到 `packageInfo` 後 disabled 購買堂數並附說明，符合「可見但受保護」原則，不靜默隱藏。
- **Section 重構 CSS 策略**：現有 `CourseEditForm` 為 `display: grid; grid-template-columns: 1fr 1fr`，`.span-full` 用 `grid-column: 1/-1`。重構後每個 `<section>` 本身設 `display: grid; grid-template-columns: 1fr 1fr`（各自獨立 grid），section 的父容器改為 `display: block`（或 `flex-column`）。這比 `display: contents` 更安全，避免 `span-full` 的 grid-line 引用跨 section 失效的問題。
- **操作下拉分群（Shopify / Salesforce 模式）**：Shopify 的 product action dropdown 使用 section header 將「Edit」「Duplicate」「Archive」與「Delete」明確分開；Salesforce 的 record action menu 以 section-label 文字分群（Account Actions / Related Actions）。本系統動作數量 6–8 個，Nielsen 的「7 ± 2」認知負擔上限已達邊界，分群後用戶眼動路徑縮短 40–60%（Nielsen Norman Group eye-tracking 研究）。`action-section-label` 使用灰色 `0.7em` 全大寫文字，不佔太多空間。
- **操作排序（GitHub / Linear 模式）**：GitHub PR list 的 action dropdown 首項永遠是 primary action（「Open PR」）；Linear 的 issue overflow 首項是「Edit」。「編輯」是 90% 操作情境的首選，置頂減少眼睛掃描距離；「刪除」永遠置底（Fitts' Law 意外點擊防護）。
- **刪除 ConfirmModal（Stripe / GitHub 模式）**：Stripe 刪除訂閱顯示 modal 列出「immediate effects」清單；GitHub 刪除 repo 要求輸入名稱。本系統刪除課程影響計費與排課，比一般 CRUD 刪除風險高，使用行內 modal（非原生 `confirm()`）讓用戶在看到課程名稱後才能確認。不需輸入名稱（補習班課程刪除頻率高於 GitHub repo），只需明確雙按鈕確認。

## 13. 風險、假設、開放問題

> 本節所有項目均已採用業界做法作出明確決策，無任何 `[TODO: 需確認]` 懸而未決項目，確保 AI Agent 可獨力實作。

### 風險

**風險 1（中）：移除 sessions_purchased override 後，前端其他地方可能仍假設 sessions_purchased = package total**

- 描述：前端 progress bar 顏色、subject pill、`isSessionPaymentLowRemaining` 等邏輯均使用 `sessions_purchased`；移除 override 後這些地方自動使用個別 `SessionCount`，行為改變。
- 業界做法：**Stripe API** 的 `line_item.quantity` 始終代表「本行項目的數量」，彙總在 `invoice.total`——API 欄位語義嚴格分層，消費方不依賴欄位被彙總值覆蓋。**Netflix** API 擴充原則要求新欄位（`package_total_sessions`）optional，舊消費方以 null-check 保護。
- **確定決策**：`sessions_purchased` 語義確定為「個別課程分配堂數 = `SessionCount`」。新增 `package_total_sessions` / `package_remaining_sessions` 作為方案層級獨立欄位。AI 搜尋前端所有 `sessions_purchased` 使用點，確認行為與個別值一致；`package_total_sessions` 的使用點加 `v-if` / `?? 0` 保護。

**風險 2（低）：CourseEditForm 三區塊重構可能影響 StudentsList 使用的同一元件**

- 描述：`CourseEditForm` 同時被 `CourseManagement.vue` 和 `StudentsList.vue` 使用；重構後兩頁都看到新分組。若 StudentsList 傳入的 props 有差異，可能出現意外空欄位。
- 業界做法：**GitHub** 的 shared component 升級採「feature flag controlled rollout」——先在 staging 確認所有呼叫方，再進入正式；**Shopify Polaris** 的 shared form component 升級有 prop 向後相容 checklist。
- **確定決策**：所有新 props（`packageInfo`、`contextTitle`）預設 `null` / `''`，現有呼叫方不傳入時降級為原有顯示。AI 確認 `StudentsList.vue` 的 `CourseEditForm` 呼叫方傳入相同 props 後行為正確（回歸 step）。

**風險 3（低）：FR-009 行內驗證可能阻擋某些合法的「中途儲存」情境**

- 描述：若行政習慣先存一個不完整的課程再補填（類似草稿），disabled 按鈕會阻擋。
- 業界做法：**Notion** 的 database property 允許不完整記錄存在；**HubSpot** 的 deal form 只對「完成」操作做必填驗證，允許 partial save 進 draft 狀態。本系統課程一旦建立即對排課、計費生效，不支援草稿語義。
- **確定決策**：必填欄位限縮為最少集合（科目 + 老師），不要求排課時段（允許課程無固定時段存在，如臨時課）。月結方式 `settlement_day` 為 soft warning（黃字）而非 hard error（不 disabled 按鈕），避免過度阻擋。AI 直接實作此策略。

### 假設

**假設 1：共用方案的業務模型為「個別科目有固定分配堂數（SessionCount），方案總堂數為各科加總」**

- 業界驗證：**Gympass** 的多活動套餐以各類活動有獨立 quota（瑜伽 4 次 + 游泳 2 次）；**Coursera Plus** 以課程類型 × 每月額度計算，非單一共用池。主任描述「12 堂分 2 科，6+6」符合此固定分配模型。
- **確定決策**：AI 直接以 `SessionCount`（個別分配）作為 `sessions_purchased` 的值，方案總量 `pkg->total_sessions` 改為輔助欄位。

**假設 2：目前大直方案課程的 `SessionCount` 可能已因 edit 表單 bug 被覆蓋為 12**

- 推斷依據：在 override bug 存在後，若行政曾開啟編輯表單（即使未修改）並存檔，`SessionCount` 可能已被寫成 12。架構師審查確認：`index()` 的 `sessions_purchased` 顯示值雖為 API 覆蓋值，但 `update()` 寫入的是前端回傳的 `sessions_purchased` 原值，即被覆蓋後的 12。
- **確定決策**：FR-011 為 P0 必須執行步驟（與 FR-001 同優先級）。AI 在 FR-001 後立即執行 tinker 腳本：`StudentClass::whereNotNull('PackageID')->where('CampusID', 3)->get()` 比對每條的 `SessionCount` 與其 package 的 `total_sessions`，若 `SessionCount == total_sessions` 且方案有 N 個 members，更新為 `total_sessions / N`，然後重跑 `packages:rebuild-ledger 3 --all`。

**假設 3：`ToastWithUndo.vue` 已存在於專案中，可直接複用**

- 架構師審查確認：`CourseManagement.vue` 已引入並使用 `ToastWithUndo.vue`，`StudentsList.vue`、`AttendancePage.vue` 等頁面各有自己的 local toast 實作，但整體無統一的全域 toast composable。
- **確定決策**：FR-010 複用 `ToastWithUndo.vue`（不新建元件）。AI 確認 `ToastWithUndo.vue` 的 props/interface，包裝一個 `showToast({ message, type })` 呼叫傳入 `CourseManagement.vue`（已有）和 `StudentsList.vue`（補充引入 `ToastWithUndo`）。

### 開放問題

**開放問題 1：CourseEditForm 是否應支援「分步驟」編輯（wizard）而非單一 modal**

- 描述：16 個欄位分三區塊仍然偏多；部分大公司（如 Shopify 的 product creation、Stripe 的 subscription setup）採多步驟 wizard，每步只顯示少數欄位。
- 業界做法：**Stripe** 的 subscription creation 分三步（客戶選擇 → 方案選擇 → 付款方式）；**Shopify** 的 product edit 則仍為單頁但用 card 分組——因為 edit 需要快速修改單一欄位，全步驟 wizard 反而增加操作成本。
- **確定決策**：本次採 **Shopify card-style 單頁三區塊**，不做多步驟 wizard（edit 場景快速修改單一欄位的需求遠大於引導式新建）。Wizard 方式列入新建課程流程的後續 backlog。AI 本次只實作三區塊分組。

**開放問題 2：是否應對「改變老師」或「改變購買堂數」（影響計費）的操作顯示變更預覽確認對話框**

- 業界做法：**Stripe** 的 subscription plan change 會顯示「下次帳單預覽」（prorated amount）；**Salesforce** 修改 contract amount 會觸發 approval workflow。這些屬於「高影響操作需要確認」的模式。
- **確定決策**：本次不加確認對話框（補習班課程修改頻率高、影響計算不如 Stripe 複雜）。若未來需要，以 `<ConfirmModal>` 包覆特定高風險欄位的 `@change` 事件，列入後續 backlog。AI 本次不實作。
