---

---

## 2. 目標與業務背景

### 痛點

目前「多科共用方案」（`CoursePackage`）只支援**堂數制**：主任需在建立方案時決定購入幾堂，付款一次預扣。對於**長期穩定上課的學生**，每次堂數快用完就需要重新繳費、重新建立方案，管理成本高；且如果某月臨時多上或少上幾堂，還要補扣或退堂，流程繁瑣。

家長習慣**每月固定繳費**（月結，如補習班行業普遍做法），但現有系統無法讓多科方案套用此模式；主任只能對每個科目個別建「月結制」單科課程，再人工加總計費，既容易出錯，又無法享有多科共用的彈性（學生可自由補課任一科）。

### 業務價值

- 主任可為長期學生一次建立「月結多科方案」，之後每月自動提醒收費，無需重複操作
- 家長每月收到固定金額通知，財務規劃容易
- 系統保留出缺席紀錄（用於老師薪資計算），但收費不依賴堂數，課程安排更靈活

### 成功 KPI

- 主任可成功建立至少 1 個「月結制多科共用方案」，並在當月截止日前收到繳費提醒
- 月結方案學生出現在「當月學收」報表，金額 = 方案月費，不以堂數計算
- 方案下各科目的出缺席扣堂記錄（`package_session_ledger`）正常寫入，不受月結模式影響

---

## 3. 範圍

### In Scope

- `CoursePackage` 新增 `billing_mode`（`count` / `monthly`）及月結欄位（`settlement_day`、`monthly_fee`）
- 建立多科方案 API（`create-multi-subject`）支援 `payment_type = 'monthly'`
- 月結模式下各 `StudentClass` 成員的 `ScheduleMode = 'date'`、`settlement_day` 繼承自方案，`Charge = 0`（費用集中在方案層）
- 「當月學收」報表（`branchMonthlyTuition`）以方案月費為單位，避免多科各自顯示 0 而遺漏
- 繳費提醒（`alerts/tuition`）按方案 `settlement_day` 提醒，不以各科 `Charge` 過濾
- 前端「多科共用方案」建立頁新增「計費方式」切換（堂數制 / 月結制），月結制顯示月費欄與結算日欄
- 退費 / 取消方案時月結方案的處理（按比例計算剩餘天數退費說明，標注 `[TODO: 需確認]`）

### Out of Scope

- 單科月結課程的邏輯（現行行為不動）
- 月結方案的**自動扣款**（非本次範圍，由主任手動確認收款）
- 跨月未收費的催收流程（現行提醒機制已涵蓋，不新增催收功能）
- 方案內每科個別定價（本次月費為方案整體一個數字，不支援每科不同費率加總）
- 家長 LINE Notify 主動推播月費帳單（後續 P2）

## 5. User Stories

> **As a** 主任，**I want** 在建立多科共用方案時選擇「月結制」並填入月費金額與結算日，**so that** 長期學生每月固定繳費，我不需要每次堂數用完就重新操作。
>
> Acceptance Criteria：
> - [ ] 建立方案頁有「計費方式」選項：堂數制（預設）/ 月結制
> - [ ] 選擇月結制後，顯示「方案月費（元）」與「每月結算日（1–31）」必填欄位，「總堂數」欄位隱藏
> - [ ] 送出後 `CoursePackage.billing_mode = 'monthly'`，`monthly_fee` 與 `settlement_day` 正確寫入
> - [ ] 方案下每個 `StudentClass` 的 `ScheduleMode = 'date'`、`settlement_day` 與方案一致、`Charge = 0`

> **As a** 主任，**I want** 月結多科方案的學生出現在「當月學收」報表中，金額顯示為方案月費，**so that** 我可以按報表一一向家長收費，不會因 `Charge = 0` 被過濾掉而漏收。
>
> Acceptance Criteria：
> - [ ] `branchMonthlyTuition` 回傳結果包含月結多科方案學生，金額 = `CoursePackage.monthly_fee`
> - [ ] 同一方案下多個科目不重複列出（方案為單一收費行）
> - [ ] 未繳費方案在「繳費提醒」（`alerts/tuition`）中按 `settlement_day` 顯示倒數天數

> **As a** 主任，**I want** 月結多科方案的出缺席和堂數記錄仍正常扣帳（`package_session_ledger`），**so that** 老師薪資計算不受月結模式影響，仍按實際出席堂數計薪。
>
> Acceptance Criteria：
> - [ ] 學生出席時 `PackageDeductionService` 寫入 `−1` 到 `package_session_ledger`
> - [ ] 月結模式下 `RemainingSessions` 不做不足警告（不存在「快用完」概念）
> - [ ] 老師兼職薪資計算以 `LearningRecord` 出席為依據，與方案計費模式無關

## 6. 功能需求（FR）

**FR-001：CoursePackage 支援月結計費模式**

系統應在 `course_packages` 資料表新增：
- `billing_mode` 欄位，值為 `count`（預設，現行堂數制）或 `monthly`（月結制）
- `monthly_fee`（月費金額，正整數，`billing_mode = 'monthly'` 時必填）
- `settlement_day`（結算日 1–31，`billing_mode = 'monthly'` 時必填）

**FR-002：建立多科月結方案 API**

`POST /api/v1/course-packages/create-multi-subject` 應接受 `payment_type = 'monthly'`、`monthly_fee`、`settlement_day` 參數，建立方案時：
- `CoursePackage.billing_mode = 'monthly'`，寫入 `monthly_fee`、`settlement_day`
- 各 `StudentClass` 成員：`ScheduleMode = 'date'`、`settlement_day` 同方案、`Charge = 0`、`RemainingSessions = 0`
- `PackageTotalSessions`、`PackageName` 仍正常寫入（出席追蹤仍有效）

**FR-003：出缺席扣帳不因月結模式改變**

`PackageDeductionService` 在月結多科方案下，應繼續對 `package_session_ledger` 寫入 `−1` 扣帳記錄（用於老師薪資計算）；不因 `billing_mode = 'monthly'` 而跳過寫帳。

**FR-004：月結多科方案不顯示「堂數不足」警告**

當 `CoursePackage.billing_mode = 'monthly'` 時，系統不應對 `RemainingSessions` 做不足警告（`alerts/tuition` 中的低堂數警示不適用），且排課不因「剩餘堂數 = 0」而被攔截。

**FR-005：當月學收報表正確呈現月結多科方案**

`GET /api/v1/finance/branch-monthly-tuition` 回傳結果：
- 月結多科方案以**方案為單位**顯示一行，金額 = `CoursePackage.monthly_fee`
- 方案下各科目 `StudentClass`（`Charge = 0`）不獨立出現於報表總金額計算中
- 若方案 `Paid = true`（已收費）則顯示已收；`Paid = false` 顯示未收、顯示結算倒數

**FR-006：繳費提醒正確觸發月結多科方案**

`GET /api/v1/alerts/tuition` 應：
- 不以各 `StudentClass.Charge > 0` 過濾月結多科方案（現行過濾條件需調整）
- 改以 `CoursePackage.billing_mode = 'monthly'` 且未繳費（`Paid ≠ true`）且 `settlement_day` 在提醒窗口內（同現行月結規則 0–5 天前）為觸發條件
- 顯示金額為 `monthly_fee`，而非各科 `Charge`

## 7. 非功能需求（NFR）

**效能：**
- `branchMonthlyTuition` API：加入方案月費邏輯後，回應時間維持 < 500ms（單校區 < 100 名學生基準）
- `create-multi-subject` 建立方案（含 3–5 個科目）：< 2 秒

**穩定性：**
- 月結方案學生若某月未出席任何課，`package_session_ledger` 可無扣帳紀錄，但報表金額仍顯示方案月費（費用不依賴出席）
- `settlement_day = 31` 且當月無 31 日（如 2 月）：系統應 fallback 至當月最後一天計算到期日，不拋例外

**向後相容：**
- 現有堂數制多科方案（`billing_mode` 欄位為 null 時 fallback `count`）行為不變

- 月費金額屬財務敏感資料，與現有 `Charge` 欄位同等保護等級

**PII / 敏感資料：**
- `monthly_fee`、`settlement_day` 屬課程財務設定，不含個人身份資料；與現有 `StudentClass.Rate`/`Charge` 同等處理

**需稽核的操作：**
- 建立月結多科方案（寫入 `monthly_fee`、`settlement_day`）
- 修改方案月費（`PUT /api/v1/course-packages/{id}`）
- 標記方案已收費

**STRIDE 快評：**

| 威脅類型 | 評估 |
|---|---|
| Spoofing | 無新身份驗證流程，N/A |
| Tampering | `monthly_fee` 由後端驗證（正整數，> 0）；前端不可直接修改 `billing_mode`；低風險 |
| Repudiation | 月費收款操作應寫入 `payment_reports` 或現有稽核機制；`[TODO: 需確認]` 現行收款標記是否寫 log |
| Info Disclosure | 方案月費受 role:director 保護，家長端 API 不暴露此欄位；低風險 |
| Denial of Service | N/A，無計算密集邏輯 |
| Elevation of Privilege | 不新增 role 或繞過 campus 限制，N/A |

**結論：無阻擋項，Repudiation 需確認稽核 log 覆蓋。**

## 13. 風險、假設、開放問題

### 風險

**R-001：settlement_day 同步至各 StudentClass，後續修改方案時需同步（中）**
描述：若主任修改方案 `settlement_day`，各 `StudentClass` 的 `settlement_day` 若未一起更新，提醒邏輯可能依舊值觸發。
緩解：`PUT /api/v1/course-packages/{id}` 修改月結設定時，cascade 更新各成員 `settlement_day`；QA 驗收此場景。

**R-002：月結方案 Charge=0 影響其他依賴 Charge 欄位的功能（中）**
描述：現有「繳費提醒」以 `Charge > 0` 過濾（`AlertController`），月結方案成員 `Charge = 0` 會被過濾。本 PRD 已在 FR-006 要求修正，但其他依賴 `Charge` 欄位的功能（如退費計算）可能有盲點。`[TODO: 需確認]` 所有使用 `StudentClass.Charge` 的功能是否需要同步處理。
緩解：CTO 全文搜尋 `Charge` 使用點，確認月結方案行為正確。

**R-003：branchMonthlyTuition 現有對月結課程的處理方式尚未完全規格化（高）**
描述：`docs/CTO_SPEC_BRANCH_MONTHLY_TUITION_REPORT.md` 明確標注月結制處理為「開放決策」。本 PRD 定義月結多科方案以 `monthly_fee` 為報表行，但與現行月結單科（以 `Rate × monthly_sessions` 計算）的混用場景需要在 `FinanceController` 中同時處理正確。
緩解：`[TEST]` agent 需涵蓋「同學生同時有月結單科 + 月結多科方案」的測試案例；若現行月結單科報表邏輯有瑕疵，本次一併修正並記入 CHANGELOG。
