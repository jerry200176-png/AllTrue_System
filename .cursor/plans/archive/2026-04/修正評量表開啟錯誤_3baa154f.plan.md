---

## 2. 目標與業務背景

**痛點**：老師鄭翔祐反映，當學生沈宇璿同一天排了兩堂課（15:00–17:00 已填待審、17:00–19:00 未填），點「編輯評量」要填第六堂時，系統卻打開第五堂的評量表。老師無法為第六堂建立評量記錄，影響主任後續審核與科目數統計。

**業務價值**：
- 確保每堂課都能正確建立評量記錄，科目數統計與薪資計算才不會有缺漏
- 老師不需要繞路（先關掉錯誤的 modal、再找其他入口），降低操作挫折感

**成功指標（KPI）**：
- 同天同學生多堂課情境下，每一堂評量表開啟正確率 = 100%
- 修正後無需人工補填遺漏評量記錄

---

## 3. 範圍

**In Scope**：
- 修正「老師課表 tab」（LearningRecordsPage 今日 / 本週課表區塊）點堂次開啟評量表的邏輯錯誤
- 涵蓋「今日」與「本週」兩個檢視模式下同樣的問題

**Out of Scope**：
- 不修改後端 API（後端已正確回傳每堂的 `learning_record_id`）
- 不異動主任視角的評量審核流程
- 不異動評量表 modal 的 UI 外觀或欄位

## 5. User Stories

**US-01**
> **As a** 任課老師，**I want** 點課表上的第六堂（未填評量），**so that** 系統開啟的是第六堂的評量表單，而不是已填的第五堂。
>
> Acceptance Criteria：
> - [ ] 點擊第六堂（未填）的「填評量」按鈕後，modal 標題顯示「新增學習評量」且上課時間為 17:00–19:00
> - [ ] ClassSession 綁定的堂次 ID 正確對應第六堂
> - [ ] 第五堂（待審）不受影響，仍可正常「編輯評量」開啟第五堂記錄

**US-02**
> **As a** 任課老師，**I want** 儲存第五堂評量後，回到課表點第六堂依然開啟正確的空白表單，**so that** 不需重新整理頁面或繞路操作。
>
> Acceptance Criteria：
> - [ ] 儲存第五堂評量後（不重新整理），再點第六堂，仍開啟正確的 17:00–19:00 空白表單
> - [ ] 課表上的「待審」狀態標籤只出現在第五堂，第六堂仍顯示「填評量」

## 6. 功能需求（FR）

**FR-001**：同一學生同一天有多堂課時，系統應依照老師點選的「堂次」（以 ClassSession ID 為準）開啟對應的評量表，不得因日期相同而開啟其他堂的評量記錄。

**FR-002**：若某堂次已有評量記錄（`learning_record_id` 不為 null），系統應開啟「編輯」該記錄的 modal；若無評量記錄（`learning_record_id = null`），系統應開啟該堂次對應時間的「新增」空白表單。

**FR-003**：老師在同一個 session 內，先儲存第五堂評量再點第六堂，第六堂應開啟空白新增表單，且上課時間欄位顯示第六堂的正確時間（17:00–19:00）。

## 8. 技術方向（給 CTO）

**受影響頁面**：`LearningRecordsPage`（課表 tab，老師視角）

**受影響 API**：`GET /api/v1/class-sessions`（後端無需修改，已正確回傳 `learning_record_id`）

**受影響資料表**：無（純前端邏輯）

**兩個 bug 的架構選擇說明**：

- **Bug 1（主因）**：前端在建立課表事件清單時，有三層 fallback 機制尋找已知評量記錄。第三層 fallback 以「StudentClass ID + 日期」為 key，當同天有多堂課（同 StudentClass）時，此 fallback 錯誤地把其他堂的 LR ID 指定給未填的堂次。
  - 選擇：移除此 fallback 對 `recordId` 的影響（`record` 變數仍可保留用於 `formStatus` 顯示），由 API 直接回傳的欄位為唯一可信來源。
  - 理由：API（`ClassSessionController`）已針對每堂 JOIN 最新 LR 並回傳精確的 `learning_record_id`，不需要前端再做模糊比對。

- **Bug 2（次因）**：前端 Vue watch 在表單欄位變動後自動呼叫「預設值套用」邏輯，此邏輯以「今日最早一堂」為預設，覆蓋已正確設定的較晚時段。
  - 選擇：加入一個旗標，讓從課表點選開啟的表單跳過此自動套用邏輯。旗標在 watch 觸發後清除，不影響老師手動選擇學生時的自動填入體驗。
  - 理由：比修改「預設值套用」本身的邏輯更小範圍、更不容易破壞其他情境。

## 10. QA 驗收標準與測試計畫

對應 FR，列出驗收情境：

**FR-001 驗收**
- Happy Path：老師有 A 學生當天兩堂課（15:00、17:00），點 17:00 堂次 → modal 顯示 17:00–19:00 空白表單
- Edge Case：三堂以上（同一學生同一天）→ 每堂分別點選都開啟對應時段
- Edge Case：只有一堂課 → 行為與修正前相同，無退化
- Error Case：`learning_record_id` 從 API 回應缺失（undefined）→ 開啟空白新增表單，不崩潰

**FR-002 驗收**
- Happy Path：第五堂有 `pending` 評量 → 點「編輯評量」開啟第五堂記錄，標題為「編輯評量」
- Happy Path：第六堂無評量 → 點「填評量」開啟空白表單，標題為「新增學習評量」
- Edge Case：第六堂 `recordId` 被 fallback 錯誤指向第五堂 LR（修正後此情況不應再出現）

**FR-003 驗收**
- Happy Path：儲存第五堂評量 → 不重新整理 → 點第六堂 → 開啟 17:00–19:00 空白表單
- Regression：確認主任視角的評量審核流程不受影響
- Regression：確認「今日」與「本週」兩個課表檢視都已修正

**回歸（對照 `docs/AI_REGRESSION_LESSONS.md`）**：
- 確認評量作廢後（`VoidedAt`）的堂次仍正確顯示為「請假」，不被誤開啟（原有修正 2026-04-17 不退化）

**UI/UX 驗收清單**：
- [ ] 點選課表堂次後 modal 開啟 < 300ms，無閃爍或跳動
- [ ] modal 標題正確顯示「新增學習評量」（新增路徑）或「編輯評量」（既有 LR 路徑）
- [ ] 上課時間欄位顯示正確時段，且欄位為唯讀（由課表帶入，不可手動改）
- [ ] 課表 tab 各堂狀態標籤（待審 / 已核准 / 填評量）顯示正確，無錯位
- [ ] 行動裝置（平板）：按鈕觸控目標 ≥ 44px，課表 modal 無水平 overflow
