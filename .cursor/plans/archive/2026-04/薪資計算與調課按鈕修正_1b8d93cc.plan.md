## 2. 目標與業務背景

### 痛點

**Bug A — 兼職薪資計算錯誤**

興隆主任反應：「只有 Ruth 蔣的薪資是對的，其他老師的邏輯不一樣、薪資算少了。」

根本原因（技術層）：
- 現行併堂薪資公式以「契約時長端點」判斷是否重疊
- 當兩堂課開始時間不同（如 09:30 與 10:00），但契約時長（120 分鐘）使區間重疊 90 分鐘，系統誤判為「同步教學」
- Non-primary session 被扣除 `base_rate × 重疊時長`，導致薪資過低（每位受影響老師每日低薪 350～525 元）
- Ruth 蔣的 session 恰好都是「完全相同開始時間」的真正 group class，公式對她正確

生產資料確認（campus_id=17，2026-04 月）：
- 游靜鈴：09:30 + 10:00（差 30 分鐘，重疊 90 分鐘）→ 誤扣 525 元/次
- 游靜鈴：17:30 + 18:30（差 60 分鐘，重疊 60 分鐘）→ 誤扣 350 元/次
- 黃芝琳：18:00 + 19:00（差 60 分鐘，重疊 60 分鐘）→ 誤扣 350 元/次

**Bug B — 調課按鈕無法點擊**

主任反應調課按鈕「無法點擊」。

根本原因：課程管理頁面的 session chip 資料來源有兩種：
1. 真實 ClassSession 行（有 id）→ 可開啟 SessionEditModal → 可調課
2. 合成物件（`_synthetic: true`，無 id，ClassSession 未載入時 fallback）→ 點擊後靜默結束，SessionEditModal 無法開啟

主任點擊合成 chip，完全沒有反應（無錯誤訊息、無 modal），因此無法進入調課流程。

### 業務價值

- Bug A 修正：老師薪資正確計算，主任信任薪資系統，降低人工核對成本
- Bug B 修正：主任調課操作路徑完整，消除「按了沒反應」的困惑體驗

### KPI

- 修正後，興隆分校 2026-04 月游靜鈴、黃芝琳等受影響老師的計算薪資，與主任人工計算一致（差異 0 元）
- Ruth 蔣薪資計算結果不受影響
- 主任點擊課程管理任一 session chip，一律有明確回饋（開啟 modal 或顯示提示），不再靜默失敗

## 5. User Stories

> **As a** 主任，**I want** 兼職老師的薪資按照實際教學安排正確計算，**so that** 我不需要在系統外人工校正數字，也不會造成老師薪資糾紛。
>
> Acceptance Criteria：
> - 系統應將「開始時間差距超過 15 分鐘的兩堂課」視為獨立排課，各自全額計薪
> - 系統應將「開始時間完全相同或差距在 15 分鐘以內的兩堂課」視為真正的 group 教學，依 v1.4 併堂公式計算
> - Ruth 蔣的 group class 薪資結果應與修正前完全一致

> **As a** 主任，**I want** 在課程管理頁面點擊任何 session chip 都有明確回饋，**so that** 我能順利進入調課流程，不會因為「點了沒反應」而困惑。
>
> Acceptance Criteria：
> - 當 ClassSession 資料已載入：chip 可點擊 → 開啟 SessionEditModal → 可執行調課
> - 當 ClassSession 資料未載入（合成物件）：chip 顯示灰色不可點樣式，hover 顯示「資料載入中，請重新整理後再試」tooltip；若透過其他路徑觸發 openSessionEdit 找不到 row，顯示 toast 說明原因

## 6. 功能需求（FR）

- **FR-001**：薪資計算 — 系統應在 `buildConcurrencyBonusMap` 中，對同一老師同一天的多個 session 建立 interval 時，加入 start time 容忍度（預設 15 分鐘）。兩個 session 的 start time 差距 > 15 分鐘者，不納入同一 concurrent segment 計算。
- **FR-002**：薪資計算 — 容忍度門檻應以 PHP class constant（`CONCURRENCY_START_TOLERANCE_MINUTES = 15`）定義，方便日後調整，不得 hard-code 數字散落程式碼。
- **FR-003**：薪資計算 — 修正後，現有 8 個 `PayrollConcurrencyTest` 守護測試須全部維持通過（Ruth 蔣 n=3、n=2 same level、partial overlap、不同層級等）。
- **FR-004**：課程管理 chip — 系統應為合成 session chip（`_synthetic: true`）套用灰化視覺樣式，不套用 `date-chip-clickable` class，且不綁定 `@click` 事件。
- **FR-005**：課程管理 chip — 合成 chip 的 `title` 屬性應顯示「此堂次資料載入中，請重新整理後再試」。
- **FR-006**：課程管理 — `openSessionEdit` 在找不到對應 session row 時，應以 toast 或 alert 顯示說明訊息，不得靜默結束。

## 7. 非功能需求（NFR）

- `GET /api/v1/finance/parttime-payroll` API 回應時間不得因本次修正增加超過 50ms（並行 session 數量有限，容忍度 guard 運算量極小）
- 前端改動不影響現有 session chip 的正常點擊流程（已載入 chip 的 UX 完全不變）
- 若 `classSessionsByCourse` API 失敗，合成 chip 的灰化提示能正確引導主任重新整理，而非直接出錯

## 8. 技術方向（給 CTO）

### 受影響範圍

| 層 | 檔案 / API |
|---|---|
| 後端計算 | `FinanceController`（`buildConcurrencyBonusMap` 方法） |
| 後端測試 | `PayrollConcurrencyTest`（新增 2 條測試） |
| 前端課程管理 | `CourseManagement.vue`（chip template） |
| 前端 composable | `useSessionEditFlow.js`（`openSessionEdit` guard） |
| 不異動 | `buildSessionRow`、`buildRateMap`、`resolvePayrollRule`、`SmartCalendar.vue`、payroll API 路由 |

### 架構選擇理由

- **選「start time 容忍度」而非「只允許完全相同 start time」**：允許 10 分鐘內的記錄誤差（如 09:00 vs 09:05 的 group class），避免未來真正的 group class 因輕微時間差無法觸發 concurrency。
- **選「15 分鐘」門檻**：兼顧「30 分鐘錯開（實務上為連續課）不誤判」與「10 分鐘以內誤差（同一堂）仍判為 concurrent」。門檻以 class constant 定義，可由 CTO 在 code review 時調整。
- **選「合成 chip 移除 clickable」而非「點擊時動態載入」**：動態載入需額外 API call + loading 狀態設計，複雜度高且易引入 race condition；合成 chip 本身代表「schedule 計算結果，ClassSession 尚未產生」，語意上本就不可操作。
