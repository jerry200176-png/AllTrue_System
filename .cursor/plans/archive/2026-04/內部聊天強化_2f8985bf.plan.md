## 2. 目標與業務背景

**痛點**

1. **Bug**：老師打開「內部聊天」點「新對話」，始終看到「載入聯絡人失敗，請確認網路後重試」，即使網路完全正常。根本原因：`AttachAuthUser` middleware 僅從 `UserCampus` 表取得校區清單；部分老師帳號只在 `teacher_branches` 表有校區紀錄，導致 `auth_has_campus = false`，`require_campus` middleware 攔截並回 403，但 frontend toast 文案謊稱是「網路錯誤」，老師無從判斷。
2. **功能落差**：現有聊天缺乏已讀回執、打字中指示、訊息搜尋等 LINE/微信基本功能，老師完成傳訊後不知道對方是否已看到。
3. **發現問題**：老師首頁（TeacherHomePage）沒有任何指向聊天的入口；行動版底部導覽把聊天藏在「更多」，第一次使用者不知道此功能存在。

**業務價值**

- 消除老師使用聊天功能的技術障礙（Bug fix → 立即可用）。
- 聊天體驗升級 → 增加活躍使用率，逐步取代私人 LINE 群組作為校務溝通管道。
- 提升老師工作效率（知道訊息已讀、即時看到對方打字）。

**成功 KPI**

- Bug 修正後：老師帳號聯絡人載入成功率 100%。
- 30 天後：老師每週聊天活躍率（至少送一則訊息）從現況提升 ≥ 30%。
- 已讀回執使用率：傳送訊息後 ≥ 50% 在 24h 內看到「已讀」標示。

## 5. User Stories

**US-001（Bug Fix，老師）**
> As a 老師，I want 打開「新對話」時能看到同校聯絡人清單，so that 我可以直接開始對話，不需要先排查網路問題。
>
> AC:
> - [ ] 老師帳號（僅有 `teacher_branches` 紀錄，無 `UserCampus` 紀錄）可成功載入聯絡人清單
> - [ ] 回傳的聯絡人以老師所在校區過濾，不洩漏其他校區人員
> - [ ] 若確實是 403（校區未設定）或 401（token 失效），Toast 顯示具體原因，不說「請確認網路」

**US-002（已讀回執）**
> As a 老師/主任，I want 傳訊後看到「已讀」狀態，so that 知道對方確認了我的訊息，不需要私下再追問。
>
> AC:
> - [ ] DM：訊息被對方讀取後，發送者訊息右下角出現「已讀」文字（LINE 風格，灰色）
> - [ ] 群組：訊息右下角顯示「已讀 N」，N = 讀過此訊息的其他成員數（排除自己）
> - [ ] 已讀狀態在頁面重新載入後仍保持正確（基於後端 `last_read_message_id`）
> - [ ] 自己的訊息未被讀取時不顯示「已讀」（而非顯示「未讀」文字）

**US-003（打字中指示）**
> As a 老師/主任，I want 看到對方「正在輸入…」提示，so that 知道不必重複追問，對方正在回覆。
>
> AC:
> - [ ] 對方在輸入框有文字時，對話視窗底部出現「XXX 正在輸入…」+ 動態三點
> - [ ] 停止打字 3 秒或送出訊息後，提示消失
> - [ ] 不在資料庫儲存任何打字狀態（純 WebSocket，減少 DB 壓力）
> - [ ] 對方離線或 WS 斷線時，提示消失（不卡在畫面）

**US-004（老師發現入口）**
> As a 老師，I want 進入教學工作台時即看到聊天功能的入口，so that 第一次登入就知道此功能的存在。
>
> AC:
> - [ ] TeacherHomePage 有「內部聊天」卡片，顯示未讀訊息數（badge）
> - [ ] 點擊後導航到聊天頁
> - [ ] 行動版底部導覽把「聊天」從「更多」移至主要 tab（取代較少用的項目）

**US-005（對話內搜尋）**
> As a 老師/主任，I want 在對話視窗內搜尋關鍵字，so that 快速找到之前討論的資訊。
>
> AC:
> - [ ] 訊息視窗右上角有搜尋按鈕
> - [ ] 輸入關鍵字後，符合的訊息以高亮顯示，並自動滾動到最近一筆
> - [ ] 搜尋範圍限於本對話目前已載入的訊息（前端 filter，不需額外 API）
> - [ ] 清空搜尋後恢復正常視圖

## 6. 功能需求（FR）

- **FR-001**：`AttachAuthUser` middleware 對 type=`T` 的使用者，若 `UserCampus` 無紀錄，則改查 `teacher_branches` 補設 `auth_campus_ids` 與 `auth_has_campus = true`，使 `require_campus` 正常放行。
- **FR-002**：`GET /api/v1/profiles` 錯誤回應在 frontend `loadStaff` 依 HTTP status 分類顯示 Toast：403 無校區→「您的帳號尚未設定校區，請聯絡主任」；403 其他→「無存取權限」；401→「登入逾期，請重新登入」；5xx/網路→「伺服器或網路異常，請稍後重試」。
- **FR-003**：訊息傳送後，系統根據 thread 成員的 `last_read_message_id` 計算已讀人數，並在 `GET /api/v1/chat/threads/{id}/messages` 回應中附帶每則訊息的 `read_count`（排除自己）。
- **FR-004**：WebSocket 新增 `typing.start` / `typing.stop` 事件（`POST /api/v1/chat/threads/{id}/typing`），Backend 廣播至同 private channel；訊息送出後自動觸發 `typing.stop`。
- **FR-005**：TeacherHomePage 聊天入口卡片從 `GET /api/v1/chat/unread-count` 取得未讀數並顯示。
- **FR-006**：訊息搜尋為前端 filter（不新增 API），關鍵字 highlight 已載入訊息，並自動滾動至最近一筆。
- **FR-007**：行動版底部導覽主要 tab 包含「聊天」（icon: `forum`），無需進入「更多」。

## 7. 非功能需求（NFR）

- **效能**：`AttachAuthUser` 新增 `teacher_branches` 查詢需加 index `teacher_id`（`teacher_branches` 已有此索引，確認即可），整體 middleware latency 增加 < 5ms。
- **即時性**：typing 事件 WebSocket 廣播 < 200ms 延遲（現有 Pusher/Echo 基礎架構）；已讀狀態更新在下次 `loadMessages` poll 時刷新（最多 8 秒延遲），可接受。
- **降級**：WebSocket 不通時，打字指示功能靜默關閉（不顯示 typing bar）；已讀回執降級為每 8 秒 poll 更新，不影響訊息收發。
- **DB**：不新增資料表；已讀狀態利用既有 `chat_thread_members.last_read_message_id`；typing 事件純 WebSocket，無持久化。

## 9. 資安與存取控制

- **攻擊面**：`AttachAuthUser` 補查 `teacher_branches` — 確保只在 `type = 'T'` 且 `UserCampus` 確實為空時觸發，防止非老師帳號以此路徑繞過校區限制。
- **Typing 廣播端點**：`POST /api/v1/chat/threads/{id}/typing` 需 `role:director,teacher` + `require_campus`；後端驗證 user 是該 thread 的成員（否則 403），防止任意廣播到他人對話。
- **已讀計算**：`read_count` 僅暴露數字（不暴露哪些人已讀），降低 PII 風險。
- **PII**：聯絡人清單已透過 `ProfileController` 限定校區；此次修正不增加暴露範圍，只是讓合法老師通過 middleware。
- **STRIDE 快評**：
  - Spoofing：無新 token/session 機制，風險不變。
  - Tampering：typing 事件廣播對象已驗證為 thread 成員，無法偽造到其他 thread。
  - Info Disclosure：`read_count` 不洩漏具體成員；聯絡人仍受校區隔離。
  - DoS：typing 事件需前端 debounce + 後端速率（可考慮每 thread 每秒 1 次廣播上限）。
  - Elevation：無新權限提升路徑。

## 13. 風險、假設、開放問題

### 風險

#### R-001 多租戶 Middleware 資料來源不一致（高）

**描述**：`AttachAuthUser` 以 `UserCampus` 為唯一校區資料來源，但 `ProfileController` 早已認知 `teacher_branches` 的存在並做 fallback；兩層之間形成隱性契約，未來有人修改任一層時容易再次斷開。

**業界做法**（參考 Laravel Multi-Tenant 2026 最佳實踐）：Multi-tenant 系統應讓「Tenant 身份解析」集中在單一 Middleware，所有下游 Controller 共享同一個 `auth_campus_ids` 屬性；不應讓個別 Controller 另行查詢 tenant 邊界。Spatie 多租戶方案的核心原則是「在 Request 生命週期最早期即完成 tenant 解析，並以 global scope 傳遞，消除 ~80% 的資料洩漏風險」。

**緩解**：
1. 此次修正在 `AttachAuthUser` 補查 `teacher_branches`，讓後端只有一個 tenant 解析入口。
2. 在 `docs/AI_REGRESSION_LESSONS.md` 新增禁止回歸項：「`AttachAuthUser` 是唯一合法的 campus 解析點，Controller 不得自行再查校區」。
3. 確認 `teacher_branches(teacher_id)` 有 DB index（每次請求增加 ≤ 5ms）。

---

#### R-002 Typing 事件廣播量過大（中）

**描述**：若老師同時在多個對話打字，每個按鍵都觸發 WebSocket 廣播，可能造成 Pi 上 Laravel Echo Server 連線數增加、CPU 升高。

**業界做法**（參考 WhatsApp/OneUptime 實踐）：業界標準是「節流（throttle）+ 去抖（debounce）雙層保護」：
- **前端 throttle**：每 **300ms** 最多送出 1 次 `typing.start` 事件（WhatsApp 採用此區間；使用者感知延遲不超過 300ms）。
- **前端 debounce**：使用者停止輸入 **2 秒**後自動送出 `typing.stop`（業界通用值；避免 `typing → online → typing` 反覆閃爍）。
- **後端選用 Redis TTL**（OneUptime 2026 方案）：若未來升級到 Redis，可設 key TTL = 5 秒，自動過期代替 `typing.stop` 事件，省去顯式清除的複雜度。

**緩解**：此次前端改為 throttle 300ms + debounce 2s（原計畫 debounce 100ms 不足）；後端可選加每 thread 每秒 1 次廣播上限作為防守。

---

#### R-003 單一 WebSocket Server 可靠性（中）

**描述**：Pi 上的 Laravel Echo Server 為單點，重啟或崩潰時所有 WebSocket 連線中斷，打字指示和即時訊息依賴的 WS 也一起失效。

**業界做法**（Laravel Reverb + Beyond Code 文件）：
- 單台伺服器使用 WebSocket 時，業界建議確保 **sticky routing**（同一使用者的 WS 連線固定到同一 process），否則多 process 部署下「每 2 次廣播只有 1 次送達」。
- 小規模部署（如 Pi 單機）的最佳實踐：保持 **單 WS process + 8 秒 thread poll 作為雙軌保底**（現有系統已有此機制）。
- 若未來擴充為多台：採用 Redis Pub/Sub 讓跨 server 廣播，而非直接 socket broadcast。

**緩解**：現有系統的 8 秒 thread poll 已提供 WS 斷線時的降級保底；此次新功能（typing、已讀）均設計為 WS 可用時啟用、WS 不通時靜默降級，符合此原則。

---

#### R-004 已讀回執：游標方案 vs 逐則追蹤的精確性（低）

**描述**：以 `last_read_message_id` 推算已讀人數屬於「聚合游標模型」，無法精確知道某則舊訊息是否被特定成員讀過（僅知「某人讀到第 N 則以後」）。

**業界做法**（Signal、Telegram、Slack 設計對比）：
- **Signal 游標模型**：每個對話存 `last_read_cursor`；使用者重新上線時批量確認游標以前的訊息，避免大量寫入，防止離線同步造成的未讀標示閃爍。
- **Telegram 混合模型**：DM 即時逐則追蹤；群組改用 Redis counter，每 10 秒 flush 到 PostgreSQL（避免「1,000 人讀同一訊息 = 1,000 次 DB 寫入」的 Write Amplification 問題）。
- **補習班場景判斷**：對話參與者少（DM 2 人、群組通常 < 10 人），游標模型已足夠精確，且無 Write Amplification 問題；不需要 Telegram 的分散式 counter。

**緩解**：此版本維持游標模型，不新增 `chat_message_reads` 表；若未來有「精確知道哪個人讀了哪一則」的需求（例如重要通知確認），再以新 migration 擴充，不影響現有資料。

---

#### R-005 老師功能發現率低（中）

**描述**：即使修好 Bug，若老師不知道有聊天功能或不習慣使用，活躍率仍難提升。

**業界做法**（Zenzap / Slack onboarding 研究）：
- 「功能在需要時出現，永遠不早、也不晚」——有效的 onboarding 是在使用者**進行相關操作的當下**展示功能，而非在第一次登入就炸出全部引導。
- Remind Hub（補習班 / 學校通訊工具）的推廣策略：先確保管理員帳號能正常使用 → 訓練主任 → 主任帶動老師。
- 研究顯示，onboarding 體驗差的員工有 2 倍機率尋找替代方案；補習班場景的「替代方案」就是繼續用個人 LINE 群。

**緩解**：
1. 此次在 TeacherHomePage 新增聊天入口卡片（功能在工作台首頁即可見）。
2. 主任首次發訊給老師時，老師 TeacherHome 的 badge 即亮起，形成「被拉進去」的自然引導（push 而非 pull）。
3. `?` FAB 頁面導覽在聊天頁已有 3 步驟指引，確保首次打開有 contextual tips。
