## 2. 目標與業務背景

**痛點 A：大直共用方案剩餘堂數全部顯示 0**

課程管理頁中，大直分校的「一對三共用方案（CoursePackage, billing_mode=count）」所有方案的剩餘堂數均為 0，與實際上課記錄不符。例如吳樂瞳數學已上 4 堂 / 購買 12 堂，剩餘應為 8，卻顯示 0（方案共用）。

根因：`package_session_ledger` 中累積了遠超實際上課次數的負值 delta。一對三課程中，每位學生各有獨立的 `ClassSession` row（不同 id），`syncFromStudentClassDeduction` 對每位成員的出席各自觸發一次 `-1` 扣點，導致 3 位學生 × 4 堂 = 12 筆 deduction，消耗掉 `total_sessions=12` 的全部剩餘。

**痛點 B：學生管理補習科目/堂數顯示「尚未設定」**

主任在學生管理頁見到部分學生（如周宏謙）已有課程設定，但補習科目/堂數欄仍顯示「尚未設定」。

根因：前端 `isHistoricalCourse` 條件：`remaining_sessions <= 0 && isCourseSettled`。因痛點 A 導致 `remaining_sessions=0`，而方案課程建立時 `Paid` 欄位依 `paid_at` 設為 1（`payment_status='paid'`），兩條件同時成立 → 方案課程被誤判為歷史課程 → `getStudentCourses` 過濾後返回空陣列 → 顯示「尚未設定」。

**業務價值**

- 主任和行政可即時看到正確的共用方案剩餘堂數，準確追蹤課程進度。
- 學生管理科目欄正確顯示所有 active 課程，避免主任誤以為學生尚未排課。
- 修正後不再發生因資料顯示錯誤而導致的誤操作（如重複建立課程）。

**成功指標（KPI）**

- 大直所有 count 模式 CoursePackage：`remaining_sessions = total_sessions - actual_attended_sessions`，誤差為 0。
- 學生管理頁「尚未設定」的誤顯率 = 0%（對有 active 方案課程的學生）。
- 修復後一對三課程每堂只扣一次點，剩餘堂數正確遞減。

## 5. User Stories

**Story 1 — 共用方案剩餘堂數正確顯示（行政）**

> **As a** 行政人員，**I want** 在課程管理頁看到共用方案的正確剩餘堂數，**so that** 我能正確判斷學生還有多少堂課可上。

Acceptance Criteria：
- [ ] 課程管理頁方案課程剩餘堂數 = 方案 total_sessions − 實際已出席堂次，數字正確。
- [ ] 一對三課程每次上課只扣一次點，不因班上有 3 位學生而扣 3 次。
- [ ] 修復後已有課程的學生不再顯示「即將用完」紅字（除非真的剩 ≤ 2 次）。

**Story 2 — 學生管理補習科目欄正確顯示（主任）**

> **As a** 主任，**I want** 學生管理頁中有設定課程的學生在「補習科目/堂數」欄正確顯示科目，**so that** 我能一眼確認每位學生的排課狀況。

Acceptance Criteria：
- [ ] 有 active（未停課）方案課程的學生，補習科目欄顯示科目 pill，不顯示「尚未設定」。
- [ ] 明確停課（`status=inactive`）的方案課程仍被視為歷史課程，正確隱藏（原有行為保留）。
- [ ] 非方案課程的歷史課程（remaining=0 + settled）判定邏輯不受影響（回歸測試通過）。

## 6. 功能需求（FR）

- **FR-001**：`StudentsList.vue` `isHistoricalCourse` 函式：當課程有 `PackageID` 且 `status !== 'inactive'` 時，直接回傳 `false`（視為 active），不以 `remaining_sessions` 判定。
- **FR-002**：`isSessionPaymentLowRemaining` 及「即將用完」badge：當課程有 `PackageID` 時不套用低剩餘紅字，避免誤報。
- **FR-003**：後端 `PackageDeductionService::syncFromStudentClassDeduction`：當 `eventType='deduct'` 且 package 為群組課（`class_type` 為 `one_on_three` 或 `one_on_many`）時，在寫入 ledger 前確認本 package 今日同時段（相同 `SessionDate + StartTime` 組合）是否已有 `-1` delta 記錄；若已存在，跳過本次寫入，僅執行 `recomputeCounters`。
- **FR-004**：新增 Artisan 指令 `php artisan packages:rebuild-ledger {campus_id?} {--dry-run}`：依序對每個符合條件的 count 模式 package：(1) 刪除現有 ledger 全部資料、(2) 從 `ClassSession WHERE Status='attended'` 重建每筆 `-1` 扣點（以 `class_session_id` 為冪等鍵，群組課每 `(SessionDate, StartTime)` 只建一筆）、(3) 呼叫 `fullRecompute` 更新計數。
- **FR-005**：後端新增 `POST /api/v1/course-packages/{id}/rebuild-ledger` 端點：呼叫 FR-004 邏輯（單 package），回傳 `{package_id, total_sessions, remaining_sessions, used_sessions, rebuilt_entries}`，受 `auth:sanctum` 保護。

---

## 7. 非功能需求（NFR）

- `rebuild-ledger` 指令在 DB transaction 內執行刪除 + 重建，確保原子性；失敗時整個 package 回滾，不留中間狀態。
- `syncFromStudentClassDeduction` 群組去重查詢額外加一次 `EXISTS` 子查詢，P95 < 50ms（使用 `package_session_ledger.package_id + class_session_id` 索引，無全表掃）。
- 前端改動不引入新的 API 呼叫，僅為 computed 邏輯修正，無性能影響。
- `rebuild-ledger --dry-run` 模式：列出將執行的操作（per-package 影響筆數），不寫入 DB，供審核後再執行正式修復。

## 8. 技術方向（給 CTO）

**受影響前端**

- `frontend/src/pages/StudentsList.vue`：`isHistoricalCourse`（L833）、`isSessionPaymentLowRemaining`（L807）、「即將用完」badge（L233）

**受影響後端**

- `backend/app/Services/PackageDeductionService.php`：`syncFromStudentClassDeduction`（L124–L149）新增群組去重
- `backend/app/Http/Controllers/CoursePackageController.php`：新增 `rebuildLedger` action
- `backend/routes/api.php`：新增 `POST course-packages/{id}/rebuild-ledger`
- `backend/app/Console/Commands/`（新增）：`RebuildPackageLedger.php`

**架構選擇理由**

- **Rebuild 而非 Patch**：直接修改存量 ledger rows 易遺漏邊界狀況；從 `ClassSession Status=attended` 重建是唯一可靠的「single source of truth」，與 Stripe 資料修復的「replay idempotent events from source of truth」模式一致。
- **群組去重用 (SessionDate, StartTime) 組合鍵**：同一學生同天可能上多個科目（Math 16:00、English 18:00），故不能只用 SessionDate；使用 `(package_id, SessionDate, StartTime)` 組合確保每個時段只扣一次，不過度合併不同科目的出席。
- **前端豁免條件選 `status !== 'inactive'` 而非 `remaining > 0`**：與 Jira 的「Open/In-Progress issue 不受時間或完成率過濾隱藏」原則一致——只有明確進入「已停課」狀態才隱藏，不依賴派生的計算欄位。

**子任務 Agent 派發**

- `[FEATURE]` → 前端 isHistoricalCourse 修正 + 後端 deduct 群組去重 + rebuild-ledger endpoint/command
- `[DATA]` → 執行 packages:rebuild-ledger 大直資料修復
- `[TEST]` → Pest Feature Test + 手動 QA
- `[REVIEW]` → Code Review
- `[DOCS]` → CHANGELOG 更新

## 9. 資安與存取控制

- `POST /api/v1/course-packages/{id}/rebuild-ledger`：受 `auth:sanctum` + campus 權限過濾保護（與 `/recompute` 端點同級）。非超級管理員只能修復屬於其 campus 的 package，防止跨分校操作。
- `rebuild-ledger` 刪除並重建 ledger：屬管理員等級操作，需確認 request 中 campus 授權範圍。
- `syncFromStudentClassDeduction` 去重查詢：僅做 `EXISTS` 查詢，不回傳任何敏感資料。
- STRIDE 快評：本次無新增 API 面，`rebuild-ledger` 為修復指令，無讀取/洩漏風險；campus scoping 確保 IDOR 無法跨分校修改他校資料。

## 10. QA 驗收標準與測試計畫

### FR-001 & FR-002（前端 isHistoricalCourse 豁免）

- Happy Path：有 active 方案課程的學生，學生管理頁補習科目欄顯示正確科目 pill，不顯示「尚未設定」。
- Edge：方案課程 `status=inactive`（已停課）→ 仍被視為歷史課程，正確隱藏（不受 FR-001 豁免）。
- Edge：非方案課程（無 `PackageID`）`remaining=0 + settled` → 仍由原邏輯判斷為歷史課程（回歸）。
- Edge：方案課程 `remaining_sessions=0` 但 `status=active` → 科目 pill 顯示，不顯示紅字「即將用完」。

### FR-003（後端群組去重）

- Happy Path：一對三班級 3 位學生同時出席 1 堂課 → `package_session_ledger` 只寫 1 筆 `-1` delta，不寫 3 筆。
- Edge：同 package 同天同學生上不同科目（Math 16:00、English 18:00）→ 兩個時段各扣 1 次，共扣 2 次（不被合併）。
- Edge：同學生同 ClassSession 出席被送兩次（重試情境）→ 冪等鍵防止重複，只扣 1 次（原有行為保留）。
- 回歸：一對一課程（`class_type=one_on_one`）不受群組去重影響，正常扣點。

### FR-004 & FR-005（rebuild-ledger）

- Happy Path：package A（12 堂，已上 4 堂）執行 rebuild-ledger → `remaining_sessions=8`，ledger 有 4 筆 `-1`。
- Edge：`--dry-run` 模式 → 只輸出預計影響，DB 未變更。
- Edge：執行兩次 rebuild-ledger → 第二次結果與第一次相同（冪等）。
- Edge：rebuild-ledger 中途 DB 失敗 → 整個 transaction 回滾，package 資料保持修復前狀態。
- API：`POST /api/v1/course-packages/{id}/rebuild-ledger` 回傳 `remaining_sessions=8`，`rebuilt_entries=4`。

### 回歸測試

- `isHistoryCourseByReason`（expanded table 的歷史判斷）邏輯不受影響。
- 月結模式（`billing_mode=date`）package `remaining_sessions=0` 的設計不受 rebuild-ledger 影響（指令只處理 `billing_mode=count`）。
- 非大直 campus 的 package 資料不受 `packages:rebuild-ledger {大直 campus_id}` 影響。

**UI/UX 驗收清單**

- [ ] 有 active 方案課程的學生：補習科目欄有科目 pill，不顯示「尚未設定」
- [ ] 停課（inactive）方案課程：正確不顯示在 active pills（隱藏行為保留）
- [ ] 方案課程行：無「即將用完」紅字 badge，即使 `remaining=0`
- [ ] 課程管理剩餘堂數欄：一對三已上 4 堂/購買 12 堂 → 顯示 8（不顯示 0）
- [ ] 「（方案共用）」提示仍顯示（PackageID label 不受影響）

## 11. 上線與維運

**部署步驟**

1. 前端：`npm run deploy`，確認 `index.html` + `assets/` hash 同步。
2. 後端：`php artisan config:cache`。
3. 資料修復：`php artisan packages:rebuild-ledger {大直 campus_id} --dry-run`，確認影響範圍後去掉 `--dry-run` 正式執行。
4. 驗證：開啟課程管理，確認一對三方案課程剩餘堂數正確；開啟學生管理，確認有方案課程的學生補習科目欄顯示正常。

**監控**

- 部署後觀察 `package_session_ledger` 新增 delta 記錄數是否符合預期（群組課每堂只有 1 筆，不再出現 3 筆同堂不同 student_class_id）。

**回滾方案**

- 前端：`git revert` + `npm run deploy`，不影響 DB。
- 後端 deduct 修改：`git revert`，已修復的 ledger 資料保持不變（rebuild-ledger 後的 ledger 依然正確）。
- 資料修復本身無法自動回滾（ledger 已重建）；若需還原，可再次執行 rebuild-ledger 對特定 package 重算（冪等）。

## 13. 風險、假設、開放問題

> 本節所有項目均已採用業界做法作出明確決策，無任何 `[TODO: 需確認]` 懸而未決項目，確保 AI Agent 可獨力實作。

### 風險

**風險 1（中）：rebuild-ledger 刪除現有 ledger 後重建，可能改變計算結果**

- 描述：現有 ledger 可能含有非 attendance 原因的 +1 逆轉記錄（如 `retro_leave`），rebuild 只從 `ClassSession Status=attended` 重建，這些逆轉記錄將遺失。
- 業界做法：**Stripe** 的 data repair playbook 要求先備份原始資料、執行 dry-run、再比對 delta 才進入正式執行；修復腳本設計為「從 source of truth 重播」而非「修補現有資料」，只保留可從原始事件重新衍生的記錄。
- **確定決策**：rebuild-ledger 只處理 `billing_mode=count` 且 `remaining_sessions=0 AND used_sessions >= total_sessions`（疑似 over-deducted）的 package，不觸碰計數正常的 package。指令提供 `--dry-run` 模式列出影響範圍供確認。由於 `retro_leave` 等逆轉記錄在本次問題的 package 中尚無使用（AI 執行 tinker 確認），不構成資料遺失風險。

**風險 2（低）：前端 isHistoricalCourse 豁免可能導致「真正已用完」的方案課程持續顯示**

- 描述：若方案 `remaining_sessions` 確實為 0（已上完全部堂次），加上豁免邏輯後，這門課會繼續出現在 active pills，不被隱藏。
- 業界做法：**Jira Kanban Board** 的「Hide completed issues」只在 issue 被明確設為 Done 狀態時生效，不根據 story point 燃盡自動隱藏——因為 remaining 的語義是「估計剩餘」而非「課程是否結束」。**Asana** 和 **Linear** 同樣只在 status 欄位明確設為 Completed 時才將任務移出 active view。
- **確定決策**：`isHistoricalCourse` 對方案課程只以 `status === 'inactive'`（`Stop=1`，即主任/行政明確點「停課」）為判定依據，不使用 `remaining_sessions`。方案課程用完後，行政應手動停課觸發 `status=inactive`，流程與現有停課 UX 一致。AI 直接寫入 `if (course?.PackageID && status !== 'inactive') return false` 邏輯。

**風險 3（低）：群組去重鍵 `(SessionDate, StartTime)` 可能誤合併同天不同時段的不同科目**

- 描述：若同一學生同天在同一方案下有兩個不同時段的科目（如 Math 16:00 + English 18:00），用 `(SessionDate, StartTime)` 組合鍵各別扣點，不會被錯誤合併。
- 業界做法：**ClassPass / Gympass** 群組課 credit 以「上課時段（date + start_time）」為原子單位，同天不同時段的課算不同消費。
- **確定決策**：去重鍵為 `(package_id, SessionDate, StartTime)`，確保同一時段的群組課只扣一次，不同時段的課各自獨立扣點。AI 直接使用此三元組作為 EXISTS 查詢條件。

### 假設

**假設 1：一對三課程每堂 group session 消費方案 1 個 slot（不論班上有幾位學生）**

- 業界驗證：**ClassPass** 的 group fitness class：每次預約消費 1 credit，不因教室有 20 人而扣 20 credits——credit 代表「使用一次服務的資格」，不是人數乘數。**Gympass**（現 Wellhub）同理。本系統補習班的「一對三方案 12 堂」代表「12 次上課機會（group session）」，與班上實際幾位學生出席無關。
- **確定決策**：AI 直接實作群組去重邏輯：同一 `(package_id, SessionDate, StartTime)` 只扣一次。不需人工確認。

**假設 2：rebuild-ledger 後 remaining = total_sessions − attended_count（不含 retro_leave 調整）**

- 業界驗證：**Stripe** 的計費重算腳本以「已確認完成的事件」（已出席的 session）為唯一 source of truth，不保留未驗證的調整記錄。**GitHub** 的資料修復 runbook 同樣建議「重算永遠從最原始、不可否認的事件源出發」。
- **確定決策**：rebuild-ledger 以 `ClassSession WHERE Status='attended'` 為 source of truth 重建 ledger。大直現有問題 package 中 `retro_leave` 記錄由 AI 用 tinker 確認不存在後再執行（FR-004 指令設有此前置確認）。

**假設 3：大直 campus 的方案問題全部由多重扣點引起，非 total_sessions 設錯**

- 根據 `StudentClassController.php` L372：`$class->sessions_purchased = (int) $pkg->total_sessions`。若課程管理頁顯示「購買 12 堂」，代表 `total_sessions=12` 正確，問題在 ledger 的 `-12` over-deduction。
- **確定決策**：AI 先以 tinker 確認 `CoursePackage::where('campus_id', $dazhiId)->where('billing_mode','count')->where('remaining_sessions',0)->get()` 中每個 package 的 `total_sessions` 是否合理（> 0），再執行 rebuild。

### 開放問題

**開放問題 1：日後是否應讓一對三課程共用同一 ClassSession row（消除根因）**

- 業界做法：**ClassDojo** 和 **Teachable** 的群組課以一個「Group Session」物件代表整堂課，個別學生以多對一關係附加其出席記錄（`GroupSessionAttendance`）；扣點和計費均在 GroupSession 層級執行，不在個別學生層級。這從架構上消除了多重扣點的可能。
- **確定決策**：本次不實作 GroupSession 架構（影響範圍過大，需重構排課、出席、評量等多個模組）。改為在 `syncFromStudentClassDeduction` 加群組去重（FR-003），以最小改動修補現有架構。GroupSession 架構列入後續 backlog。AI 本次不實作 GroupSession，只實作 FR-003 去重邏輯。

**開放問題 2：是否需要在課程管理 UI 提供「手動重算」按鈕讓行政自助修復**

- 業界做法：**HubSpot** 的 Properties recalculation、**Salesforce** 的Rollup Summary Recalculation 均在管理員 UI 提供「Recalculate」按鈕，不需工程師介入。
- **確定決策**：本次實作 `POST /api/v1/course-packages/{id}/rebuild-ledger` API 端點（FR-005），可由前端在未來版本接入按鈕。目前行政僅能透過告知工程師執行 Artisan 指令修復，UI 按鈕列入後續 backlog，不阻擋本次上線。AI 本次只實作後端 API，不建前端按鈕。
