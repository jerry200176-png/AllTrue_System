## 2. 業務背景與影響

**痛點**：老師從「出勤點名」或「課表工作台」回報課表出入後，主任在「課表回報管理」頁面完全看不到新回報，誤以為功能壞掉。

**實際根因**：後端 API 正常（curl 驗證 200 + 資料），問題在前端頁面不自動刷新。

**修復後預期行為**：
1. 主任開著頁面時，30 秒內自動顯示新增的 `pending` 回報（page-level polling）
2. 主任在其他頁面時，Nav Badge 最遲 60 秒顯示待處理筆數，引導主任點入查看

---

## 3. 範圍

### In Scope
- `frontend/src/pages/ScheduleDiscrepancyPage.vue`：`pending` tab 開啟時加入 30 秒頁面輪詢（使用 `setInterval` + `document.visibilityState` 守護）
- `frontend/src/App.vue`：在 `chatBadgePollingTimer` 的 `setInterval` 回呼中補上 `mergeScheduleDiscrepancyBadge()`

### Out of Scope
- 後端不做任何更改（API / routes / Controller / DB 完全不動）
- SSE / WebSocket（架構過重，本 Pi 部署環境不支援；業界建議 30s+ 更新用 polling 已足夠）
- `LearningRecordsPage`（評量表）不在本次範圍
- `AttendancePage`、`TeacherHomePage` 送出邏輯不在本次範圍
- 其他 Nav Badge 的輪詢頻率不在本次範圍

## 5. Acceptance Criteria

### AC-001：頁面自動刷新
- AC-001-a：主任在「課表回報管理」切換至「待處理」tab 後，頁面每 30 秒自動呼叫一次 `load()`，無需手動點選「重新整理」。
- AC-001-b：頁面隱藏（`document.visibilityState !== 'visible'`）時，輪詢暫停，頁面重新可見後恢復。
- AC-001-c：主任離開「課表回報管理」頁面（元件 unmount）時，輪詢計時器被清除，不發生 memory leak。
- AC-001-d：老師送出回報後，主任最多等待 30 秒即可在頁面看到新回報，無需手動刷新。

### AC-002：Nav Badge 定期更新
- AC-002-a：`chatBadgePollingTimer`（每 60 秒）的 callback 中包含 `mergeScheduleDiscrepancyBadge()` 呼叫。
- AC-002-b：老師送出回報後，主任左側 Nav「課表回報管理」最遲 60 秒出現 badge 計數。
- AC-002-c：badge 更新邏輯仍遵守 `pauseOnHidden` 與 `_badgePollingPaused` 兩個守護旗標。

## 8. 技術方向

### 涉及檔案與方法

**`frontend/src/pages/ScheduleDiscrepancyPage.vue`**
- 新增 import：`onBeforeUnmount`（Vue 3）
- 新增一個 `pagePollingTimer` 變數（`let`，頂層 script）
- 新增 `startPagePolling()` / `stopPagePolling()` helper：
  - `pending` tab → 30000ms interval；其他 tab → 60000ms
  - callback 內部：`if (!hasBranch.value || document.visibilityState !== 'visible') return; load();`
- 在 `setTab()` 中：先 `stopPagePolling()`，再 `load()`，再 `startPagePolling()`
- 在 `onMounted` 後加 `startPagePolling()`
- 在 `onBeforeUnmount` 加 `stopPagePolling()`
- 在 `document.visibilitychange` 事件加入回呼（visible → `load()`，否則 noop）

**`frontend/src/App.vue`**
- 在 `chatBadgePollingTimer` setInterval callback 中，於 `mergeDirectorPendingBadge()` 之後補上 `mergeScheduleDiscrepancyBadge()`

### 架構取捨理由

| 方案 | 選擇 | 理由 |
|------|------|------|
| `setInterval` polling | ✅ 選擇 | Pi 環境簡單部署，無 WebSocket/SSE 基礎設施，更新頻率 30s 足夠；業界建議 30s+ 間隔用 polling |
| SSE / WebSocket | ❌ 不選 | 需 event stream 長連線、Apache 設定、Pub/Sub 佇列，架構過重 |
| `watch` on `rows` 深比較 | ❌ 不選 | 資料從 API 來，Vue 無法感知伺服器端新增 |

## 10. QA 驗收

## 13. 風險 / 假設 / 開放問題

> 已執行 WebSearch（2026-04-21）：「Vue 3 polling auto-refresh setInterval vs SSE 2026」

| 類型 | 描述 | 緩解方式 |
|------|------|---------|
| 風險 | Pi 低功耗環境多主任同時輪詢可能增加 DB 負載 | 30s interval 每次只查 1 個分校，DB 負載極低；可透過 `.env` `BADGE_POLL_INTERVAL` 動態調整 |
| 假設 | 業界共識（WebSearch 確認）：更新頻率 >30s 用 polling 即可，無需 SSE/WS | 若未來需求要求 <10s 即時性，再升級為 SSE |
| 開放問題 | `acknowleded` / `resolved` tab 是否也需要自動刷新？ | 本計畫先做 60s（其他 tab），需求確認後可調整 |
