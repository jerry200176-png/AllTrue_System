# 備份失敗告警 — Bug Fix Plan

## 0. 根因確認（Root Cause）

| 欄位 | 內容 |
|---|---|
| 嚴重度 | P1 |
| 根因類型 | 功能缺失（Missing Feature as Defect） |
| 根因摘要 | `nightly-backup.sh` 與 `sixhour-backup.sh` 均以 `set -euo pipefail` 執行，任何子命令失敗即靜默退出，但兩支腳本均未設定 EXIT trap，導致備份結果（成功或失敗）完全不可觀測 |
| 錯誤行為 | mysqldump 失敗、git push 失敗等任何步驟出錯時，腳本靜默退出，管理者無任何通知 |
| 預期行為 | 腳本不論成功（exit 0）或失敗（exit 非 0），均於退出時向 Telegram 監控群發送含腳本名稱、時間戳、結果的通知 |
| 影響範圍 | cron 排程的備份任務（01:00 nightly、05/11/17/23 sixhour）；管理員無法即時得知備份狀態 |
| B1 偵查來源 | 本計畫整合 B1 內容（直接閱讀腳本原始碼確認） |

## 2. 業務背景與影響

**痛點**：備份是資料保全最後防線，任何 mysqldump 失敗、git push 中斷或磁碟滿載，均會導致腳本以非零 exit code 退出，但目前靜默失敗。管理員只能事後翻 log 才知道出問題，可能已錯過還原視窗。

**修復後預期行為**：
- 備份成功 → Telegram 群組收到「✅ 備份成功」含腳本名稱與時間
- 備份失敗 → Telegram 群組收到「🚨 備份失敗」含腳本名稱、exit code 與時間
- `.env.monitor` 不存在或 Token 未填寫 → 腳本仍正常執行（通知靜默降級），不影響備份本身

## 3. 範圍

**In Scope**
- 修改 [`scripts/nightly-backup.sh`](scripts/nightly-backup.sh)：加入 `on_exit()` 函式與 `trap 'on_exit $?' EXIT`
- 修改 [`scripts/sixhour-backup.sh`](scripts/sixhour-backup.sh)：同上

**Out of Scope**
- [`scripts/monitor-alert.sh`](scripts/monitor-alert.sh) 的現有 `send_notify()`、`check_resources()`、`daily_report()` 邏輯 — 完全不動
- [`.env.monitor`](.env.monitor) 的內容與格式 — 只讀取，不修改
- cron 排程設定 — 不異動
- `scripts/git-sync.sh` — 不異動

## 5. Acceptance Criteria

### AC-001：備份成功通知
- AC-001-a：手動執行 `bash scripts/sixhour-backup.sh`，全程無錯誤，Telegram 群組於腳本結束後收到含「✅」與「6h-backup」字樣的訊息
- AC-001-b：手動執行 `bash scripts/nightly-backup.sh`（或以 dry-run 模擬），成功後收到含「✅」與「nightly-backup」字樣的訊息

### AC-002：備份失敗通知
- AC-002-a：使腳本中某步驟失敗（如臨時改壞 DB_HOST），腳本因 `set -euo pipefail` 退出，Telegram 收到含「🚨」與非零 exit code 的訊息
- AC-002-b：失敗通知不包含任何認證憑證（`DB_PASSWORD`、`TELEGRAM_BOT_TOKEN` 等敏感字串）

### AC-003：通知降級不破壞備份
- AC-003-a：`.env.monitor` 不存在時，腳本仍能完整執行備份，僅通知不發送（exit 0）
- AC-003-b：`TELEGRAM_BOT_TOKEN` 為空時，腳本行為同 AC-003-a

## 6. 功能需求 FR

- **FR-001**：兩支腳本均應在 `set -euo pipefail` 之後、所有主要邏輯之前，定義 `on_exit()` 函式並設定 `trap 'on_exit $?' EXIT`
- **FR-002**：`on_exit()` 應讀取 `/home/admin/.env.monitor`（`[ -f ]` 保護），取出 `TELEGRAM_BOT_TOKEN` 與 `TELEGRAM_CHAT_ID` 至 local 變數，避免污染腳本全局命名空間
- **FR-003**：exit code 為 0 時發送成功訊息；非 0 時發送失敗訊息並包含 exit code
- **FR-004**：訊息格式應包含：腳本識別符（`nightly-backup` 或 `6h-backup`）、結果圖示（✅ / 🚨）、時間戳（`YYYY-MM-DD HH:MM`）
- **FR-005**：`TELEGRAM_BOT_TOKEN` 或 `TELEGRAM_CHAT_ID` 任一為空時，`on_exit()` 直接 return，不呼叫 curl
- **FR-006**：Telegram API 呼叫採用與 `monitor-alert.sh` 相同的 curl + python3 JSON 編碼方式，保持一致性

## 7. 非功能需求 NFR

不適用。本修復屬純邏輯補足（加 EXIT trap），無效能影響，`on_exit()` 僅在腳本退出時執行一次，curl 呼叫為非阻塞背景行為，不影響備份主流程執行時間。

## 8. 技術方向

**涉及檔案**
- [`scripts/nightly-backup.sh`](scripts/nightly-backup.sh)：在 `KEEP_TAGS=60` 常數區塊之後加入 `on_exit()` 函式定義與 trap 設定，腳本識別符用 `nightly-backup`
- [`scripts/sixhour-backup.sh`](scripts/sixhour-backup.sh)：在 `KEEP=8` 常數之後加入相同結構，腳本識別符用 `6h-backup`

**方法與結構**
- 函式名稱：`on_exit()`，接受 `$1`（exit code）
- Trap 設定：`trap 'on_exit $?' EXIT`（必須在函式定義後立即設定）
- `.env.monitor` 讀取：用 `source` 但以 `[ -f ]` 包裹，並將 token/chat_id 存為 local 變數
- Telegram curl 呼叫：仿照 `monitor-alert.sh` 第 34-37 行的 python3 JSON 編碼方式

**架構取捨**
- 選擇「inline 函式」而非「呼叫 monitor-alert.sh」：Out of Scope 明定不動 `monitor-alert.sh`，且 inline 較少外部依賴
- 選擇「source .env.monitor 進 local 變數」而非「grep 逐行解析」：與 `monitor-alert.sh` 既有做法一致，且 local 變數在函式結束後自動清除

## 13. 風險 / 假設 / 開放問題

**業界解法（WebSearch 已確認）**

業界標準做法（參考 restic + Telegram gist、percona-backup-notify）一致採用：
- `trap 'handler $?' EXIT` 搭配 exit code 判斷
- credentials 存於獨立 secrets 檔（chmod 600），讀取進 local 變數
- curl Telegram API，JSON payload 由 python3/jq 編碼

**風險**
- `python3` 在 Pi 環境不存在：已確認 `monitor-alert.sh` 現有邏輯使用 `python3`，Pi 上已有安裝，風險低
- `on_exit` 內的 `source .env.monitor` 若 `.env` 語法有誤（如含 bash 特殊字元），可能造成 parse error：低風險（`.env.monitor` 目前內容簡單）

**假設**
- `.env.monitor` 的 `TELEGRAM_BOT_TOKEN` 與 `TELEGRAM_CHAT_ID` 值在 cron 執行時有效

**開放問題**：無
