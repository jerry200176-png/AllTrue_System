# PRD：代課與調課組合操作後課程管理顯示錯誤老師

## 1. 文件資訊

| 欄位 | 內容 |
|---|---|
| 功能名稱 | 代課 + 調課組合操作授課老師顯示修正 |
| 版本 / 日期 | v1.0 / 2026-04-18 |
| 狀態 | Draft |
| 目標角色 | 主任（課程管理點名）、老師（點名查詢授課老師）、代課老師（確認自己的授課記錄） |

---

## 2. 目標與業務背景

### 痛點

當一堂課發生「老師請假或代課 + 同時更換上課時間（調課）」時，無論操作順序為何，**課程管理頁面的「授課老師」欄（含 tooltip 點名人）始終顯示原任老師姓名，而非實際代課老師**。

具體例子：
- 游家豫數學課 4/22，主任先指定陳章華代課，再透過智慧排課調至週三 → 課程管理顯示鄭翔祐（原任老師）
- 若操作順序相反（先調課再代課），同樣易出現資料不一致

此問題在「老師請假、學生需換老師又換時間」的情境下**必然發生**，影響：
1. 主任無法確認實際授課老師
2. 點名記錄歸屬錯誤
3. 科目數統計可能錯算老師工時

### 業務價值

修正後，主任可信任課程管理的老師欄位，代課安排操作順序不再影響最終顯示結果。

### 成功指標（KPI）

- 代課 + 調課（任意順序）操作後，課程管理顯示代課老師正確率達 100%
- `schedules` 表中同一 (student_course_id, schedule_date, start_time, original_schedule_id) 不存在兩筆以上 `status=scheduled` 的行

## 6. 功能需求（FR）

### FR-001：前端 submitReschedule 代課行衝突防護

系統應在 `SmartCalendar.vue` 的 `submitReschedule` 執行時，於取得既有 `rescheduled` 行 ID（originalId）後，檢查目前已載入的 `exceptions` 是否存在 `status='scheduled'` 且 `original_schedule_id === originalId` 的代課行。若存在，系統**不得**對 `schedules` 表插入第二筆 `status=scheduled` 的行（payload2）；應直接進入後端 `reschedule-session` 呼叫，由後端 `syncSchedulesForRescheduledSession` 將既有代課行移動至新日期。

- 觸發條件：`alreadyRescheduled = true` 且 `exceptions` 中存在對應代課 scheduled 行
- 排除條件：無代課的純調課（`alreadyRescheduled = true` 但無對應 scheduled 行），此時應正常插入 payload2

### FR-002：後端 syncSchedulesForRescheduledSession 去重清理

系統應在 `LearningRecordController::syncSchedulesForRescheduledSession` 將代課 scheduled 行移動至新日期後，刪除同一 (student_course_id, new_date, original_schedule_id) 下**未在本次更新集合中**的其他 `status=scheduled` 行。此機制作為防禦性清理，處理前端在後端執行前已插入重複行的競態情況。

- 觸發條件：移動代課行後，新日期上存在同 original_schedule_id 的重複行
- 保留目標：本次 update 集合中的代課行（已更新至正確 teacher_id）
- 刪除目標：非本次 update 集合、同 original_schedule_id 的其他 scheduled 行

### FR-003：現有資料熱修正

系統資料庫中游家豫（StudentClass=143）4/22 的 stale scheduled 行（schedules id=606，teacher=鄭翔祐）應被刪除，使課程管理正確顯示陳章華。

## 7. 非功能需求（NFR）

- **效能**：FR-002 的去重刪除操作在 `syncSchedulesForRescheduledSession` 同一 transaction 內完成，不額外增加 API 回應時間超過 50ms
- **錯誤處理**：FR-001 的代課行偵測失敗（`exceptions` 尚未載入）時，系統應 fallback 為原本行為（插入 payload2），而非阻止調課操作
- **降級策略**：若 FR-001 前端 guard 未觸發（例如 `exceptions` 未含 `original_schedule_id` 欄位），FR-002 後端清理仍可獨立清除重複行，保障資料最終一致性
- **資料一致性**：修正後，同一 (student_course_id, schedule_date, start_time, original_schedule_id) 組合下，`status=scheduled` 的行至多一筆

## 8. 技術方向（給 CTO）

### 受影響頁面 / API / 資料表

- **前端頁面**：`SmartCalendar.vue`
- **後端 API**：`POST /api/v1/learning-records/reschedule-session`（`LearningRecordController`）
- **資料表**：`schedules`

### 架構選擇

**雙層防護設計**：前端 guard（FR-001）+ 後端去重清理（FR-002）分別作為第一道和第二道防線。

- 選擇前端 guard 而非只依賴後端：因前端先寫 Supabase、再呼叫後端，競態窗口存在；guard 從根本消除多數情況下的重複寫入
- 選擇後端去重清理而非只依賴前端：前端狀態（`exceptions.value`）可能因載入時序而不含最新代課行；後端清理確保最終一致性
- 不修改 `ClassSessionController::index` 的 MAX(id) 子查詢：現有邏輯在資料正確時運作正常，修改風險大；治本策略為防止重複行產生

### 是否需要 Migration

不需要。修正為邏輯層修正，不新增欄位或索引。

## 9. 資安與存取控制

- **存取控制**：`POST /api/v1/learning-records/reschedule-session` 受 `require_campus` middleware 限制，僅限已認證使用者操作自己分校的資料；FR-002 去重刪除以 `student_course_id` 為 scope，不跨課程或跨分校
- **PII**：`schedules` 表含 `student_id`、`teacher_id`，操作均在認證 session 內執行，無新增暴露
- **稽核 log**：`syncSchedulesForRescheduledSession` 已有 `Log::info('reschedule_session.substitute_schedules_synced', ...)` 記錄，建議在去重刪除後補一筆 `Log::info('reschedule_session.duplicate_scheduled_rows_deleted', ['deleted_ids' => ...])` 供事後稽核
- **STRIDE 快評**：
  - Tampering：去重刪除 scope 限定 student_course_id，無法藉此刪除他課資料，風險低
  - Information Disclosure：無新增 API 回應欄位，無風險
  - 其他 STRIDE 項目：無新增攻擊面
